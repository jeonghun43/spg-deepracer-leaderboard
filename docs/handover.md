## 1. 5분 요약 — 이게 뭐하는 물건인가

사내 DeepRacer 대회의 **온라인 예선 플랫폼**이다. 참가팀이 직접 학습시킨 자율주행 모델을 웹에
올리면, 서버가 시뮬레이터로 자동 평가해 랩타임을 재고 리더보드에 순위를 매긴다. 사람이 채점하지
않는다.

**핵심 규칙** (바꾸려면 코드 수정이 필요하다)
- 팀당 하루 5회 제출. 평가가 끝까지 실행된 것만 카운트하고, 오류로 끝난 건 카운트하지 않는다.
- 한 팀은 대기/평가중 제출을 동시에 1건만 가질 수 있다. 결과가 나와야 다음 것을 올린다.
- 리더보드는 팀별 **최고기록만** 표시하고, 랩타임이 빠른 팀이 위다.
- 기록은 **3바퀴 합계 시간**이다(바퀴당 평균이 아니다). 3바퀴를 모두 완주해야 기록으로 인정된다.
- 참가자에게 알림은 가지 않는다. 새로고침해서 확인하는 방식이다.

> ⚠️ **평가 체크포인트 규칙 — 저장소 밖 설정이라 특히 주의**
>
> 참가자의 압축 파일에는 학습 중 만들어진 체크포인트가 여러 개 들어 있고, 그중 무엇을 평가할지는
> **DRFC의 `~/deepracer-for-cloud/run.env`** 에 있는 `DR_EVAL_CHECKPOINT`가 정한다.
>
> - **이 대회는 `best`로 운영한다** (2026-07-30 결정). 참가자가 학습 중 가장 성적이 좋았던 체크포인트로 평가한다.
> - DRFC 기본값은 `last`(마지막 체크포인트)다. **평가 서버를 새로 세팅하면 기본값으로 돌아가므로 반드시 다시 `best`로 바꿔야 한다.** 안 바꾸면 아무도 모르게 다른 기준으로 채점된다.
> - 이 값은 우리 저장소가 아니라 DRFC 쪽 파일에 있어서 코드 배포로 따라오지 않는다.
> - 확인: `grep DR_EVAL_CHECKPOINT ~/deepracer-for-cloud/run.env`
> - 워커 재시작은 필요 없다. 평가할 때마다 이 파일을 다시 읽는다.

### 무엇으로 이루어져 있나

**시스템은 두 대에 나뉘어 있다** (2026-07-30 이후).

```
[참가자 브라우저]
      │  https://spg-deepracer.doublejeong.com
      ▼
┌─ 클라우드 서버 (AWS Lightsail 서울, 24시간 가동) ──────────┐
│  Caddy(HTTPS) → 웹 → PostgreSQL   ← 시즌·팀·계정·기록      │
│                    └ storage/     ← 제출 모델, 평가 영상    │
└────────────────────────────────────────────────────────────┘
      ↑ Tailscale 사설망(DB 접속) + HTTPS(모델·영상 전송)
      │
┌─ 운영자 노트북 (켜져 있을 때만) ───────────────────────────┐
│  평가 워커 → DRFC(시뮬레이터) → MinIO(결과 저장소)         │
└────────────────────────────────────────────────────────────┘
```

- **클라우드 서버**: 참가자가 보는 화면 전부. **노트북과 무관하게 24시간 살아 있다.**
- **평가 워커**: 노트북에서 도는 별도 프로그램. 5초마다 클라우드 DB를 보고 "대기" 제출을 하나씩 집어 평가한다.
- **DRFC**: AWS DeepRacer 커뮤니티가 만든 시뮬레이터. **이 시스템에서 가장 설치가 까다로운 부분**이라 노트북에 남아 있다(클라우드 서버 2GB로는 못 돌린다 — 시뮬레이터 하나가 2.26GB를 쓴다).

**중요**: 노트북이 꺼져 있어도 **리더보드 조회·로그인·제출은 계속 된다.** 평가만 대기열에 쌓이고,
화면에 "평가 서버가 잠시 중지되어 있습니다"가 뜬다. 노트북을 켜면 밀린 것부터 순서대로 처리한다.

서버에 직접 들어가 상태를 보는 방법은 [server-access.md](server-access.md)에 있다.

## 2. 대회 한 번 여는 체크리스트

### ① 준비 (대회 2~3주 전)
- [ ] **리허설을 한다.** 이 문서만 보고 시스템을 처음부터 띄워본다. 1년 방치된 시스템은 어딘가
      반드시 썩어 있다(도메인 만료, 요금 미납, 패키지 비호환 등). 대회 직전에 알면 늦는다.
- [ ] 서버·워커를 기동하고 [operations.md](operations.md)의 절차대로 접속되는지 확인
- [ ] **본인 계정으로 테스트 팀을 만들어 실제로 모델을 한 번 제출해본다.** 평가가 끝까지 돌고
      리더보드에 뜨는 것까지 확인. 여기까지 되면 시스템은 정상이다.

### ② 시즌 생성
- [ ] 관리자 화면(`/admin`) 로그인 → **새 시즌 만들기**
- [ ] 이름·트랙·기간 입력. 시즌은 **준비중** 상태로 생성된다(아직 제출 못 받음)
- [ ] ⚠️ 시즌 이름은 참가자에게 그대로 보인다. "테스트 시즌" 같은 이름으로 두지 말 것

### ③ 팀 등록과 계정 배포
- [ ] 시즌 관리 화면에서 팀 이름을 **한 줄에 하나씩** 붙여넣고 일괄 등록 (한 번에 최대 50팀)
- [ ] 발급된 아이디/비밀번호가 표로 뜬다 → **CSV 다운로드 버튼으로 즉시 저장**
- [ ] ⚠️ **비밀번호는 이 화면을 벗어나면 다시 볼 수 없다.** 암호화가 아니라 단방향 해시로
      저장되기 때문이다. 잃어버리면 해당 팀 줄의 **재발급** 버튼으로 새로 발급해야 한다
- [ ] 각 팀에 아이디/비밀번호와 접속 주소를 전달

### ④ 대회 시작
- [ ] 시즌 관리 화면에서 **진행중으로 전환** → 이때부터 제출을 받는다
- [ ] 워커가 돌고 있는지 확인 (리더보드에 "평가 서버가 잠시 중지" 배너가 없으면 정상)

### ⑤ 대회 기간 중 (매일)
- [ ] 리더보드 접속 확인 — 안 되면 §3
- [ ] 대기 배너가 떠 있지 않은지 확인 — 떠 있으면 워커가 죽은 것
- [ ] **백업이 도는지 확인** — `C:\Users\jjh03\drleader-backup\STATUS` 파일이 `OK`로 시작하고
      날짜가 최근인지 본다. `FAILED`면 §6
- [ ] 관리자 화면에서 최근 제출의 **오류 건**을 훑어본다. 같은 오류가 반복되면 참가자가 모델을
      잘못 만들고 있는 것이므로 안내해준다 (자주 나오는 오류는 §3-C)

### ⑥ 마감과 정리
- [ ] 마감 시각이 되면 **마감으로 전환** → 제출이 닫히고 순위가 확정된다
- [ ] 순위를 발표하고 본선 진출 팀을 정한다
- [ ] 충분히 시간이 지난 뒤 **아카이브로 전환** → 최고기록 외 파일과 팀 계정이 삭제된다.
      리더보드 기록과 최고기록 영상은 계속 남는다. **되돌릴 수 없으니 서두르지 말 것**

## 3. 문제가 생겼을 때

### A. 참가자가 "사이트에 접속이 안 된다"고 한다

**노트북과는 무관하다.** 웹은 클라우드 서버에서 돈다.

1. 밖에서 되는지 확인
   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" https://spg-deepracer.doublejeong.com/healthz
   ```
   `200`이면 서비스는 정상 — 참가자의 네트워크 문제일 수 있다.
2. 안 되면 서버에 들어가 컨테이너 상태를 본다 ([server-access.md](server-access.md) §1·§2)
   ```bash
   cd ~/drleader && docker compose -f docker-compose.prod.yml ps
   ```
3. 대부분은 이 한 줄로 복구된다
   ```bash
   cd ~/drleader && docker compose -f docker-compose.prod.yml up -d
   ```
4. 그래도 안 되면 확인할 것 — **도메인 만료**(자동 갱신 확인), **AWS 결제 실패로 인스턴스 정지**,
   HTTPS 인증서 갱신 실패(`docker compose -f docker-compose.prod.yml logs caddy`)

### B. 제출은 되는데 결과가 안 나온다
1. 워커가 살아 있는지: `pgrep -af '[w]orker.run'` → 아무것도 안 나오면 죽은 것
2. 로그 확인: `tail -50 /tmp/worker.log`
3. 다시 띄우기: [operations.md](operations.md) "평가 워커 기동"
4. 평가 1건은 **10분 안팎** 걸린다. 앞에 대기가 있으면 그만큼 더 걸린다 — 정상이다

### C. 특정 팀만 계속 오류가 난다 (참가자 안내용)
관리자 화면의 오류 메시지를 보고 판단한다. 대부분 참가자의 모델 압축 방식 문제다.
- `model_metadata.json을 찾을 수 없습니다` → 학습 결과의 `model/` 폴더 내용을 압축해야 하는데
  엉뚱한 폴더를 압축한 경우
- `MinIO의 내부 저장 폴더를 그대로 압축한 것으로 보입니다` → 오류 메시지에 적힌 `aws s3 sync`
  명령으로 정상 내보내기 후 압축하도록 안내
- 이런 오류는 **하루 제출 한도에서 제외**되므로 다시 올려도 손해가 없다고 알려주면 된다

### D. 리더보드에 영상이 "—"로만 나온다
평가는 됐지만 영상 수집이 안 된 경우다. 순위에는 영향이 없다. 워커 로그에서
`쓸 만한 평가 영상을 찾지 못했습니다`를 확인한다. DRFC가 카메라 앵글 3종 중 일부만 정상 생성하는
경우가 있어 우리 워커는 정상 크기인 앵글을 골라 받도록 되어 있다.

### E. 디스크가 가득 찼다
제출 모델 1건이 약 250MB다. 평가가 끝나면 팀별 최고기록 외 파일은 자동 삭제되지만, 그래도
부족하면 `storage/eval_logs/`(시뮬레이션 로그)를 지워도 된다. `storage/work/`에 남은 폴더도
평가가 돌고 있지 않다면 지워도 안전하다.

## 4. 절대 하면 안 되는 것

| 하지 말 것 | 이유 |
|---|---|
| `pkill -f 'worker.run'` | 그 명령을 실행한 셸까지 함께 죽는다. `kill $(pgrep -f '[w]orker.run')`을 쓸 것 |
| 워커를 2개 이상 실행 | 평가 영상이 S3의 같은 경로에 덮어써져 팀끼리 영상이 섞인다 |
| 대회 중 `SESSION_SECRET` 변경 | 접속 중인 참가자·관리자가 전부 로그아웃된다 |
| 평가가 도는 중에 워커 강제 종료 | 해당 제출이 "평가중"에 멈춘다(30분 뒤 자동 복구되지만 그동안 그 팀은 제출 불가) |
| 아카이브 전환을 서두르는 것 | 최고기록 외 파일과 팀 계정이 **되돌릴 수 없게** 삭제된다 |
| `wsl --unregister` | **DB가 통째로 사라진다.** DB는 Windows 폴더가 아니라 WSL 내부 Docker 볼륨에 있다 |

- [ ] **Tailscale 계정** — 서버와 노트북을 잇는 사설망. 이게 끊기면 평가가 멈춘다
- [ ] **서버 SSH 키** — 노트북 WSL의 `~/.ssh/id_ed25519`. 새 PC에서 접속하려면

- [ ] **코드 저장소** — GitHub 접근 권한 (개인 계정이면 동아리 공용 계정으로 옮기는 것을 권장)
- [ ] **관리자 계정** — 지금은 관리자 계정이 1개뿐이고 화면에서 추가할 수 없다.
      새 계정 생성: `docker compose exec web python -m app.seed <아이디> <비밀번호>`
      후임 계정을 만든 뒤 전임 계정을 DB에서 지우는 것이 깔끔하다
- [ ] **`.env` 파일** — 저장소에 없다(비밀값). 별도로 전달해야 한다
- [ ] **평가 서버 하드웨어** — 개인 노트북이면 그 노트북을 넘기거나 DRFC를 재설치해야 한다.
      **동아리 소유 PC 1대를 확보하는 것이 가장 확실한 대책이다**
- [ ] **DRFC 환경** — `~/deepracer-for-cloud`. 설치가 이 시스템에서 가장 어려운 부분이다
- [ ] **도메인·클라우드 계정과 결제수단** — 개인 카드면 회장이 바뀌는 순간 서비스가 죽는다.
      동아리 공용 이메일 + 회비/법인 결제로 옮길 것
- [ ] **데이터** — DB 덤프와 `storage/` (§6)

## 6. 백업과 복구

백업은 **자동화되어 있다.** 매일 새벽 4시에 노트북에서 `scripts/backup.sh`가 돌아
**클라우드 서버의** DB와 `storage/`를 SSH로 끌어와 `C:\Users\jjh03\drleader-backup`에 저장하고,
최근 14벌만 남긴다. 노트북이 꺼져 있어 걸렀던 실행은 다음 부팅 직후 따라잡는다.

데이터가 **서버 → 노트북 → Google Drive** 세 곳에 있게 되므로, 서버가 통째로 사라져도
(계정 정지·인스턴스 삭제·결제 실패) 복구할 수 있다. 백업본을 서버 안에 두면 그 순간 함께
사라지기 때문에 일부러 이렇게 구성했다.

### 회장이 해야 할 일은 두 가지뿐이다

**① 가끔 상태를 확인한다** — 백업 폴더의 `STATUS` 파일을 열어본다.

```
OK 2026-07-27 11:32:28  db=8.0K storage=156K 보관=1벌
```

`FAILED`로 시작하면 백업이 실패한 것이다. 실패 사유가 함께 적혀 있고, 자세한 이력은 같은
폴더의 `backup.log`에 있다. 가장 흔한 원인은 **DB 컨테이너가 안 떠 있는 것**이다
(`docker compose up -d`로 해결).

**② 백업본이 노트북 밖에도 있게 한다** — Google Drive 데스크톱 설정 → **내 컴퓨터** →
폴더 추가 → `C:\Users\jjh03\drleader-backup`를 **"Google Drive에 백업"**으로 지정.
이걸 안 하면 노트북이 죽을 때 백업도 같이 죽는다. **백업의 존재 이유가 사라진다.**

### 알아둘 것

- **제출 모델 파일은 백업에 들어가지 않는다** (건당 250MB라 제외). 참가자가 원본을 갖고 있어
  재업로드가 가능하다. 꼭 필요하면 `BACKUP_INCLUDE_MODELS=true bash scripts/backup.sh`.
- **DB와 `storage/`는 반드시 같은 날짜 것을 함께 복원한다.** 한쪽만 복원하면 리더보드 기록과
  실제 영상 파일이 어긋난다.
- **운영 DB에 바로 덮어쓰지 말고 별도 DB에 먼저 복원해 확인한다.** 절차는
  [operations.md](operations.md) "복원 절차"에 단계별로 있다.
- 백업 파일에는 팀 계정 비밀번호 해시가 들어 있다. 이 폴더를 공유 링크로 열지 말 것.
