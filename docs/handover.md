## 1. 5분 요약 — 이게 뭐하는 물건인가

사내 DeepRacer 대회의 **온라인 예선 플랫폼**이다. 참가팀이 직접 학습시킨 자율주행 모델을 웹에
올리면, 서버가 시뮬레이터로 자동 평가해 랩타임을 재고 리더보드에 순위를 매긴다. 사람이 채점하지
않는다.

**핵심 규칙** (바꾸려면 코드 수정이 필요하다)
- 팀당 하루 5회 제출. 평가가 끝까지 실행된 것만 카운트하고, 오류로 끝난 건 카운트하지 않는다.
- 한 팀은 대기/평가중 제출을 동시에 1건만 가질 수 있다. 결과가 나와야 다음 것을 올린다.
- 리더보드는 팀별 **최고기록만** 표시하고, 랩타임이 빠른 팀이 위다.
- 기록은 **3바퀴 합계 시간**이다(바퀴당 평균이 아니다). 3바퀴를 모두 완주해야 기록으로 인정된다.
- 참가자에게 알림은 가지 않는다. 새로고침해서 확인하는 방식이다.

> ⚠️ **평가 체크포인트 규칙 — 저장소 밖 설정이라 특히 주의**
>
> 참가자의 압축 파일에는 학습 중 만들어진 체크포인트가 여러 개 들어 있고, 그중 무엇을 평가할지는
> **DRFC의 `~/deepracer-for-cloud/run.env`** 에 있는 `DR_EVAL_CHECKPOINT`가 정한다.
>
> - **이 대회는 `best`로 운영한다** (2026-07-30 결정). 참가자가 학습 중 가장 성적이 좋았던 체크포인트로 평가한다.
> - DRFC 기본값은 `last`(마지막 체크포인트)다. **평가 서버를 새로 세팅하면 기본값으로 돌아가므로 반드시 다시 `best`로 바꿔야 한다.** 안 바꾸면 아무도 모르게 다른 기준으로 채점된다.
> - 이 값은 우리 저장소가 아니라 DRFC 쪽 파일에 있어서 코드 배포로 따라오지 않는다.
> - 확인: `grep DR_EVAL_CHECKPOINT ~/deepracer-for-cloud/run.env`
> - 워커 재시작은 필요 없다. 평가할 때마다 이 파일을 다시 읽는다.

### 무엇으로 이루어져 있나

**시스템은 두 대에 나뉘어 있다** (2026-07-30 이후).

```
[참가자 브라우저]
      │  https://spg-deepracer.doublejeong.com
      ▼
┌─ 클라우드 서버 (AWS Lightsail 서울, 24시간 가동) ──────────┐
│  Caddy(HTTPS) → 웹 → PostgreSQL   ← 시즌·팀·계정·기록      │
│                    └ storage/     ← 제출 모델, 평가 영상    │
└────────────────────────────────────────────────────────────┘
      ↑ Tailscale 사설망(DB 접속) + HTTPS(모델·영상 전송)
      │
┌─ 평가 서버 (AWS EC2 스팟, 24시간) ─────────────────────────┐
│  평가 워커 → DRFC(시뮬레이터) → MinIO(결과 저장소)         │
└────────────────────────────────────────────────────────────┘
      ※ 운영자 노트북에도 같은 구성이 남아 있어 예비 워커로 켤 수 있다
```

- **클라우드 서버**: 참가자가 보는 화면 전부. Lightsail(서울)에서 24시간 돈다.
- **평가 서버**: AWS EC2 스팟 인스턴스(m7i.xlarge). 평가 워커가 5초마다 클라우드 DB를 보고 "대기" 제출을 하나씩 집어 평가한다. 워커는 systemd로 등록되어 있어 서버가 재시작돼도 자동으로 살아난다.
- **DRFC**: AWS DeepRacer 커뮤니티가 만든 시뮬레이터. **이 시스템에서 가장 설치가 까다로운 부분**이라 웹 서버와 분리해 두었다(Lightsail 2GB로는 못 돌린다 — 시뮬레이터 하나가 2.26GB를 쓴다).

**중요**: 평가 서버가 꺼져 있어도 **리더보드 조회·로그인·제출은 계속 된다.** 평가만 대기열에 쌓이고,
화면에 "평가 서버가 잠시 중지되어 있습니다"가 뜬다. 평가 서버를 켜면 밀린 것부터 순서대로 처리한다.

> 평가 서버의 접속·구축·비용 관리는 [worker-server-setup.md](worker-server-setup.md)에 전부 정리돼
> 있다. **대회 기간이 아닐 때는 인스턴스를 중지하거나 종료해 비용을 아낀다**(같은 문서 §9).

서버에 직접 들어가 상태를 보는 방법은 [server-access.md](server-access.md)에 있다.

### 관리자 화면에 어떻게 들어가나 (2026-08-03 변경)

**`/admin`으로 바로 가면 404가 뜬다. 고장이 아니다.**

참가자·관전자에게 관리자 진입점을 보이지 않게 하려고, 로그인 화면을 **`.env`에 적어둔
비밀 경로**로 옮겼다. 상단 메뉴의 "관리자" 링크도 로그인한 상태에서만 나타난다.

```
① 서버 .env의 ADMIN_LOGIN_PATH 값을 확인한다
     ssh ubuntu@15.164.198.36 "grep ADMIN_LOGIN_PATH ~/drleader/.env"

② 그 주소로 접속한다
     https://spg-deepracer.doublejeong.com<그 값>
     예) https://spg-deepracer.doublejeong.com/_ops/m7gk4jigoqynyx

③ 아이디/비밀번호를 입력한다  ← 여기는 예전과 똑같다

④ 로그인하면 상단 메뉴에 "관리자"가 나타난다. 그 세션 동안은 주소를 다시 칠 필요가 없다
```

**이 주소를 북마크해 둘 것.** 잊어버려도 ①로 다시 찾을 수 있으니 잠기는 일은 없다.

| 알아둘 것 | 설명 |
|---|---|
| 로그인 창을 5번 틀리면 | 15분간 잠긴다(무차별 대입 방어). 급하면 서버에서 `docker compose -f docker-compose.prod.yml restart web`으로 즉시 풀린다 |
| 세션이 만료된 뒤 `/admin` | **404가 정상이다.** 비밀 경로로 다시 들어와야 한다 |
| 비밀 경로가 유출된 것 같으면 | 서버 `.env`의 값을 바꾸고 `up -d`. 즉시 새 주소가 적용된다 |
| 후임에게 넘길 때 | **이 문서에 경로를 적지 말 것.** "`.env`의 `ADMIN_LOGIN_PATH`를 보라"고만 전한다 |

> 비밀 경로는 **인증이 아니라 은닉**이다. 진짜 방어선은 여전히 비밀번호이므로,
> 관리자 비밀번호를 초기값에서 반드시 바꿔둔다.
> 설계 배경: [admin-access-hardening.md](../specs/001-online-virtual-evaluation/admin-access-hardening.md)

## 2. 대회 한 번 여는 체크리스트

### ① 준비 (대회 2~3주 전)
- [ ] **리허설을 한다.** 이 문서만 보고 시스템을 처음부터 띄워본다. 1년 방치된 시스템은 어딘가
      반드시 썩어 있다(도메인 만료, 요금 미납, 패키지 비호환 등). 대회 직전에 알면 늦는다.
- [ ] 서버·워커를 기동하고 [operations.md](operations.md)의 절차대로 접속되는지 확인
- [ ] **본인 계정으로 테스트 팀을 만들어 실제로 모델을 한 번 제출해본다.** 평가가 끝까지 돌고
      리더보드에 뜨는 것까지 확인. 여기까지 되면 시스템은 정상이다.

### ② 시즌 생성
- [ ] **관리자 화면에 로그인** → **새 시즌 만들기**
      (들어가는 방법은 아래 "관리자 화면에 어떻게 들어가나" 참고 — `/admin`으로 바로 가면 404다)
- [ ] 이름·트랙·기간 입력. 시즌은 **준비중** 상태로 생성된다(아직 제출 못 받음)
- [ ] ⚠️ 시즌 이름은 참가자에게 그대로 보인다. "테스트 시즌" 같은 이름으로 두지 말 것

### ③ 팀 등록과 계정 배포
- [ ] 시즌 관리 화면에서 팀 이름을 **한 줄에 하나씩** 붙여넣고 일괄 등록 (한 번에 최대 50팀)
- [ ] 발급된 아이디/비밀번호가 표로 뜬다 → **CSV 다운로드 버튼으로 즉시 저장**
- [ ] ⚠️ **비밀번호는 이 화면을 벗어나면 다시 볼 수 없다.** 암호화가 아니라 단방향 해시로
      저장되기 때문이다. 잃어버리면 해당 팀 줄의 **재발급** 버튼으로 새로 발급해야 한다
- [ ] 각 팀에 아이디/비밀번호와 접속 주소를 전달
- [ ] ⚠️ **모델 제출 방법도 함께 공지한다.** 그대로 복사해 쓸 수 있는 공지문이
      [operations.md](operations.md)의 **"참가자 제출 형식 안내"** 절에 있다.
      압축 방법(`aws s3 sync`)을 안 알려주면 **거의 모든 팀이 첫 제출에서 실패한다** —
      MinIO 폴더를 그대로 압축하는 실수가 가장 흔하다(§3-C)

### ④ 대회 시작
- [ ] 시즌 관리 화면에서 **진행중으로 전환** → 이때부터 제출을 받는다
- [ ] 워커가 돌고 있는지 확인 (리더보드에 "평가 서버가 잠시 중지" 배너가 없으면 정상)

### ⑤ 대회 기간 중 (매일)
- [ ] 리더보드 접속 확인 — 안 되면 §3
- [ ] 대기 배너가 떠 있지 않은지 확인 — 떠 있으면 워커가 죽은 것
- [ ] **백업이 도는지 확인** — `C:\Users\<사용자>\drleader-backup\STATUS` 파일이 `OK`로 시작하고
      날짜가 최근인지 본다. `FAILED`면 §6
- [ ] 관리자 화면에서 최근 제출의 **오류 건**을 훑어본다. 같은 오류가 반복되면 참가자가 모델을
      잘못 만들고 있는 것이므로 안내해준다 (자주 나오는 오류는 §3-C)

### ⑥ 마감과 정리
- [ ] 마감 시각이 되면 **마감으로 전환** → 제출이 닫히고 순위가 확정된다
- [ ] 순위를 발표하고 본선 진출 팀을 정한다
- [ ] 충분히 시간이 지난 뒤 **아카이브로 전환** → 최고기록 외 파일과 팀 계정이 삭제된다.
      리더보드 기록과 최고기록 영상은 계속 남는다. **되돌릴 수 없으니 서두르지 말 것**

## 2-1. 코드를 고쳐 서버에 반영하기 (배포)

> **가장 많이 틀리는 절차다.** 이 문서를 쓴 사람도 2026-08-03에 여기서 막혔다.
> 상세는 [server-access.md](server-access.md) §5에 있고, 여기서는 **틀리는 지점**만 짚는다.

**세 단계이고, 순서를 지켜야 한다.**

**① `.env`에 새 설정이 필요한지 먼저 확인한다**

`.env`는 **서버로 전송되지 않는다**(비밀값을 실수로 덮어쓰지 않기 위해서다).
그래서 코드가 새 설정 키를 요구하면 **서버에서 컨테이너가 아예 안 뜬다.**
현재 필수 키: `POSTGRES_PASSWORD` · `SESSION_SECRET` · `SITE_DOMAIN` · `ADMIN_LOGIN_PATH`

```bash
ssh ubuntu@15.164.198.36 "grep -c ADMIN_LOGIN_PATH ~/drleader/.env"
```

`0`이 나오면 [server-access.md](server-access.md) §5의 안내대로 먼저 넣는다.

**② 코드를 서버로 전송한다 ← 여기를 빼먹는다**

**WSL 터미널에서** 실행한다 (PowerShell 아님).

```bash
cd /mnt/c/Users/<사용자>/spg_deepracer_leaderboard && tar czf - --exclude=.venv --exclude=storage --exclude=.env --exclude=__pycache__ --exclude=.git . | ssh ubuntu@15.164.198.36 "tar xzf - -C ~/drleader"
```

**③ 서버에서 다시 빌드·기동한다**

```bash
ssh ubuntu@15.164.198.36 "cd ~/drleader && docker compose -f docker-compose.prod.yml up -d --build"
```

### ⚠️ "다 했는데 그대로예요" — 이 함정을 반드시 알아둘 것

**②를 건너뛰고 ③만 하면 아무 일도 일어나지 않는다.** 서버에 있던 옛 소스로 다시 빌드될 뿐인데,
컨테이너는 정상적으로 새로 뜨고 사이트도 멀쩡히 돌아서 **"배포가 됐다"고 착각하게 된다.**
브라우저를 강력 새로고침해도 당연히 그대로다 — 서버가 옛 화면을 보내고 있으니까.

`.env`를 고쳤을 때도 똑같이 착각한다. `.env`만으로는 **코드가 안 바뀐다.**

### 반영됐는지 반드시 확인한다

배포 후 아래를 돌린다. **눈으로 사이트를 보는 것으로는 확인이 안 된다.**

```bash
ssh ubuntu@15.164.198.36 "ls -l --time-style=+%Y-%m-%d ~/drleader/app/config.py && cd ~/drleader && docker compose -f docker-compose.prod.yml ps"
```

`config.py`의 날짜가 **오늘이 아니면 ②가 안 된 것이다.** 그리고 `web`이 `Up`이어야 한다.
`web`이 없거나 `Exited`면 ③이 실패한 것이므로 로그를 본다:

```bash
ssh ubuntu@15.164.198.36 "cd ~/drleader && docker compose -f docker-compose.prod.yml logs --tail 30 web"
```

마지막으로 브라우저에서 **강력 새로고침**(`Ctrl`+`F5`). CSS·JS는 브라우저가 캐시하므로
그냥 새로고침하면 옛 파일이 보인다.

**워커도 다시 띄워야 하나?** `worker/` 아래를 고쳤을 때만 그렇다. 웹 화면(`app/`)만 고쳤다면
평가 서버는 건드리지 않아도 된다.

## 3. 문제가 생겼을 때

### A. 참가자가 "사이트에 접속이 안 된다"고 한다

**노트북과는 무관하다.** 웹은 클라우드 서버에서 돈다.

1. 밖에서 되는지 확인
   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" https://spg-deepracer.doublejeong.com/healthz
   ```
   `200`이면 서비스는 정상 — 참가자의 네트워크 문제일 수 있다.
2. 안 되면 서버에 들어가 컨테이너 상태를 본다 ([server-access.md](server-access.md) §1·§2)
   ```bash
   cd ~/drleader && docker compose -f docker-compose.prod.yml ps
   ```
3. 대부분은 이 한 줄로 복구된다
   ```bash
   cd ~/drleader && docker compose -f docker-compose.prod.yml up -d
   ```
4. 그래도 안 되면 확인할 것 — **도메인 만료**(자동 갱신 확인), **AWS 결제 실패로 인스턴스 정지**,
   HTTPS 인증서 갱신 실패(`docker compose -f docker-compose.prod.yml logs caddy`)

### B. 제출은 되는데 결과가 안 나온다
1. 평가 서버(EC2)에 접속: `ssh -i ~/.ssh/drfc-worker-key.pem ubuntu@100.93.165.104`
   → 접속이 안 되면 스팟이 회수된 것일 수 있다. AWS 콘솔에서 인스턴스 상태를 본다
2. 워커가 살아 있는지: `sudo systemctl status drfc-worker` → `active (running)`이어야 한다
3. 로그 확인: `journalctl -u drfc-worker -n 50 --no-pager`
   (노트북 예비 워커라면 `tail -50 /tmp/worker.log`)
4. 다시 띄우기: `sudo systemctl restart drfc-worker` — **평가 중이 아닐 때만** 한다
5. 큐에 뭐가 밀려 있는지: [server-access.md](server-access.md) "평가 대기열(큐) 조회"
6. 평가 1건은 **8분 안팎**(EC2 기준) 걸린다. 앞에 대기가 있으면 그만큼 더 걸린다 — 정상이다.
   완주하지 못하는 모델은 리셋을 소진할 때까지 돌아 더 오래 걸린다

### C. 특정 팀만 계속 오류가 난다 (참가자 안내용)
관리자 화면의 오류 메시지를 보고 판단한다. 대부분 참가자의 모델 압축 방식 문제다.
- `model_metadata.json을 찾을 수 없습니다` → 학습 결과의 `model/` 폴더 내용을 압축해야 하는데
  엉뚱한 폴더를 압축한 경우
- `MinIO의 내부 저장 폴더를 그대로 압축한 것으로 보입니다` → 오류 메시지에 적힌 `aws s3 sync`
  명령으로 정상 내보내기 후 압축하도록 안내
- 이런 오류는 **하루 제출 한도에서 제외**되므로 다시 올려도 손해가 없다고 알려주면 된다

### D. 리더보드에 영상이 "—"로만 나온다
평가는 됐지만 영상 수집이 안 된 경우다. 순위에는 영향이 없다. 워커 로그에서
`쓸 만한 평가 영상을 찾지 못했습니다`를 확인한다. DRFC가 카메라 앵글 3종 중 일부만 정상 생성하는
경우가 있어 우리 워커는 정상 크기인 앵글을 골라 받도록 되어 있다.

### E. 디스크가 가득 찼다
제출 모델 1건이 약 250MB다. 평가가 끝나면 팀별 최고기록 외 파일은 자동 삭제되지만, 그래도
부족하면 `storage/eval_logs/`(시뮬레이션 로그)를 지워도 된다. `storage/work/`에 남은 폴더도
평가가 돌고 있지 않다면 지워도 안전하다.

### F. 관리자 로그인이 "시도가 너무 많습니다"로 막힌다

비밀번호를 5번 틀리면 15분간 잠긴다. **기다리기 싫으면 서버에서 웹을 재시작하면 즉시 풀린다.**

```bash
ssh ubuntu@15.164.198.36 "cd ~/drleader && docker compose -f docker-compose.prod.yml restart web"
```

잠금 카운터는 웹 프로세스 메모리에만 있어서 재시작으로 사라진다. **참가자 쪽에는 영향이 없다** —
리더보드·로그인·제출은 몇 초 끊겼다 돌아온다. 다만 **업로드가 진행 중인 제출 1건은 실패할 수 있으니**
대회 기간이라면 먼저 대기열을 확인한다([server-access.md](server-access.md) §3의 큐 조회).

### G. 관리자 화면이 404가 뜬다

**대부분 고장이 아니다.** §1의 "관리자 화면에 어떻게 들어가나"를 보고 비밀 경로로 접속한다.
세션이 만료됐거나 `/admin`을 직접 친 경우 404가 정상 동작이다.

**진짜 문제인 경우**는 하나다 — 배포 후 `web` 컨테이너가 아예 안 떠서 사이트 전체가 502인 것.
그때는 `.env`에 `ADMIN_LOGIN_PATH`가 빠진 것이 원인일 수 있다
([server-access.md](server-access.md) §5).

```bash
ssh ubuntu@15.164.198.36 "cd ~/drleader && docker compose -f docker-compose.prod.yml ps"
```

## 4. 절대 하면 안 되는 것

| 하지 말 것 | 이유 |
|---|---|
| `pkill -f 'worker.run'` | 그 명령을 실행한 셸까지 함께 죽는다(2026-07-26 실제 발생 ×2). `pgrep -f -- '-m [w]orker\.run' \| xargs -r kill`을 쓸 것 |
| 워커를 2개 이상 실행 | 평가 영상이 S3의 같은 경로에 덮어써져 팀끼리 영상이 섞인다 |
| 대회 중 `SESSION_SECRET` 변경 | 접속 중인 참가자·관리자가 전부 로그아웃된다 |
| 평가가 도는 중에 워커 강제 종료 | 해당 제출이 "평가중"에 멈추고, 그동안 그 팀은 제출을 못 한다. **같은 기기에서 워커를 다시 켜면 즉시 대기열로 돌아가지만**(2026-08-01 수정), 그 기기를 안 켜면 계속 갇혀 있다. DRFC 평가 스택도 따로 남아 도니 `docker stack ls`로 확인하고 끌 것 |
| 아카이브 전환을 서두르는 것 | 최고기록 외 파일과 팀 계정이 **되돌릴 수 없게** 삭제된다 |
| `wsl --unregister` | **SSH 키 두 개(`id_ed25519`, `drfc-worker-key.pem`)와 DRFC 환경이 통째로 사라진다.** 키가 없으면 웹 서버·평가 서버 **어느 쪽에도 못 들어간다**. DRFC는 재설치가 이 시스템에서 가장 어려운 부분이다. 백업 systemd 타이머도 함께 사라진다 (2026-08-03 정정: 예전엔 "DB가 사라진다"고 적혀 있었으나, **DB는 이제 클라우드 서버에 있어 영향받지 않는다.** WSL에 남은 `db_data` 볼륨은 정지된 옛 것이다) |

- [ ] **클라우드 서버** — AWS Lightsail(서울) 인스턴스 `drleader`, 고정 IP `15.164.198.36`.
      AWS 계정 접근 권한이 넘어가야 한다. 계정 자체를 넘길 수 없다면 새 계정에 서버를 다시 만들고
      백업을 복원하는 방식으로 이사한다(30분~1시간, [server-access.md](server-access.md) §5 참고)
- [ ] **도메인** — `doublejeong.com` (가비아). 리더보드는 `spg-deepracer` 서브도메인을 쓴다.
      **자동 갱신이 켜져 있는지 확인.** 만료되면 서비스가 통째로 죽는다
- [ ] **Tailscale 계정** — 서버와 노트북을 잇는 사설망. 이게 끊기면 평가가 멈춘다
- [ ] **SSH 키 — 두 종류다. 둘 다 넘겨야 한다** ⚠️
      - **웹 서버(Lightsail)용**: 노트북 WSL의 `~/.ssh/id_ed25519`. 새 PC에서 접속하려면

      - **평가 서버(EC2)용**: `~/.ssh/drfc-worker-key.pem` (AWS 키 페어).

        분실했다면 인스턴스를 새 키로 다시 만드는 수밖에 없다

- [ ] **코드 저장소** — GitHub 접근 권한 (개인 계정이면 동아리 공용 계정으로 옮기는 것을 권장)
- [ ] **관리자 계정** — 지금은 관리자 계정이 1개뿐이고 화면에서 추가할 수 없다.

      후임 계정을 만든 뒤 전임 계정을 DB에서 지우는 것이 깔끔하다
- [ ] **`.env` 파일** — 저장소에 없다(비밀값). 별도로 전달해야 한다.

      후임은 관리자 화면에 들어갈 수 없다(서버 SSH가 있으면 직접 열어볼 수는 있다)
- [ ] **평가 서버 하드웨어** — 개인 노트북이면 그 노트북을 넘기거나 DRFC를 재설치해야 한다.

- [ ] **도메인·클라우드 계정과 결제수단** — 개인 카드면 회장이 바뀌는 순간 서비스가 죽는다.

## 6. 백업과 복구

백업은 **자동화되어 있다.** 매일 새벽 4시에 노트북에서 `scripts/backup.sh`가 돌아
**클라우드 서버의** DB와 `storage/`를 SSH로 끌어와 `C:\Users\<사용자>\drleader-backup`에 저장하고,
최근 14벌만 남긴다. 노트북이 꺼져 있어 걸렀던 실행은 다음 부팅 직후 따라잡는다.

데이터가 **서버 → 노트북 → Google Drive** 세 곳에 있게 되므로, 서버가 통째로 사라져도
(계정 정지·인스턴스 삭제·결제 실패) 복구할 수 있다. 백업본을 서버 안에 두면 그 순간 함께
사라지기 때문에 일부러 이렇게 구성했다.

### 회장이 해야 할 일은 두 가지뿐이다

**① 가끔 상태를 확인한다** — 백업 폴더의 `STATUS` 파일을 열어본다.

```
OK 2026-07-27 11:32:28  db=8.0K storage=156K 보관=1벌
```

`FAILED`로 시작하면 백업이 실패한 것이다. 실패 사유가 함께 적혀 있고, 자세한 이력은 같은
폴더의 `backup.log`에 있다. 가장 흔한 원인은 **DB 컨테이너가 안 떠 있는 것**이다
(`docker compose up -d`로 해결).

**② 백업본이 노트북 밖에도 있게 한다** — Google Drive 데스크톱 설정 → **내 컴퓨터** →
폴더 추가 → `C:\Users\<사용자>\drleader-backup`를 **"Google Drive에 백업"**으로 지정.
이걸 안 하면 노트북이 죽을 때 백업도 같이 죽는다. **백업의 존재 이유가 사라진다.**

### 알아둘 것

- **제출 모델 파일은 백업에 들어가지 않는다** (건당 250MB라 제외). 참가자가 원본을 갖고 있어
  재업로드가 가능하다. 꼭 필요하면 `BACKUP_INCLUDE_MODELS=true bash scripts/backup.sh`.
- **DB와 `storage/`는 반드시 같은 날짜 것을 함께 복원한다.** 한쪽만 복원하면 리더보드 기록과
  실제 영상 파일이 어긋난다.
- **운영 DB에 바로 덮어쓰지 말고 별도 DB에 먼저 복원해 확인한다.** 절차는
  [operations.md](operations.md) "복원 절차"에 단계별로 있다.
- 백업 파일에는 팀 계정 비밀번호 해시가 들어 있다. 이 폴더를 공유 링크로 열지 말 것.

| **백업이 노트북 의존** | 노트북이 오래 꺼져 있으면 백업도 멈춘다 | `STATUS` 확인을 일과에 넣거나 서버 쪽 이중 백업 |
| **웹 서버 배포가 tar 밀어넣기** | 로컬에서 **지운 파일이 서버에 남고**, 서버에 어떤 코드가 올라가 있는지 확인할 방법이 없다 | 대회 종료 후 git 방식으로 전환 — 절차는 [git-deploy-migration.md](git-deploy-migration.md) |
| **평가 기준이 저장소 밖 설정** | `DR_EVAL_CHECKPOINT=best`가 DRFC의 `run.env`에 있다 | 서버 재세팅 시 반드시 다시 설정 (§1 경고 참고) |
