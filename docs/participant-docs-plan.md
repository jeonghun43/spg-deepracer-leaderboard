# 참가자 문서 기획안 — 무엇을, 어떤 순서로 알려줄 것인가

이 문서는 **참가자에게 배포할 문서가 아니라, 그 문서를 만들기 위한 설계도**다.
배포 대상은 `docs/participants/` 아래에 놓는다.

목표 한 줄: **"이 폴더만 순서대로 읽으면, 강화학습을 처음 듣는 사람도 모델을 학습시켜
리더보드에 기록을 남기고, 오프라인 경주까지 갈 수 있다."**

---

## 1. 독자 정의

| 항목 | 설정 |
|---|---|
| 배경 | 전공/비전공 혼재. **강화학습을 처음 듣는 사람이 기준선** |
| 환경 | 개인 노트북(WSL2 + Docker), 일부는 GPU 없음 |
| 시간 | 대회 기간 중 짬을 내서 본다 → **한 문서 = 한 자리에서 읽을 분량** |
| 실패 지점 | ① 환경이 안 깔림 ② 학습은 되는데 기록이 안 나옴 ③ 제출이 실패함 |

②번(**기록이 안 나옴**)이 지금 문서에 통째로 빠져 있다. 이번 기획의 핵심이다.

## 3. 대회 규칙 — 문서에 반드시 들어가야 할 확정 사실

아래는 **추측이 아니라 현재 코드에서 확인한 값**이다. 참가자 문서 00번과 09번의 뼈대가 된다.

| 규칙 | 값 | 근거 |
|---|---|---|
| 평가 바퀴 수 | **3바퀴** | `app/config.py` `online_eval_laps=3` / `DR_EVAL_NUMBER_OF_TRIALS` |
| 완주 인정 조건 | **3바퀴가 전부 100% 완주**여야 기록으로 인정 | `worker/drfc.py:343` |
| 기록 = | 3바퀴 **합산 시간(초)**. 가장 빠른 한 바퀴가 아니다 | `worker/drfc.py:344` |
| 동률 처리 | 먼저 제출한 팀이 앞 | `app/records.py` |
| 미완주 시 | 순위에서 빠지고, **최고 진행률 + 실패 사유**가 표시됨 | `EvaluationResult.best_progress_percent`, `failure_reason` |
| 하루 제출 한도 | **3회** (KST 자정 리셋). **평가가 끝까지 돌아간 건만 카운트** — 서버 오류는 차감 안 됨. **제출한 시각의 날짜로 셈** — 자정 직전 제출이 자정 이후에 끝나도 그날 횟수 | `app/quota.py` |
| 동시 제출 | 팀당 **1건**. 앞 평가가 끝나야 다음 제출 가능 | `app/models.py:128` 부분 유니크 인덱스 |
| 파일 | `.tar.gz` 또는 `.zip`, **최대 500MB** | `app/config.py` |
| 평가 대기 | 대기열이 있고, 1건당 약 10분 | `eval_minutes_estimate` |

**이 표가 참가자 전략을 바꾼다.** "3바퀴 합산 + 전부 완주"라는 규칙은
*빠르지만 가끔 코스아웃하는 모델*보다 *조금 느려도 안정적인 모델*이 이긴다는 뜻이다.
지금 참가자들은 이 사실을 모른 채 속도만 올리고 있을 가능성이 크다.

## 5. 문서별 상세 기획

### 00. 대회 안내 — "5분 안에 판을 이해한다"

**목적**: 무엇을 만들어 어떻게 이기는지. 규칙을 모르고 튜닝하는 일을 막는다.

- 이 대회가 뭔가 — 가상 트랙에서 자율주행 모델을 학습시켜 랩타임을 겨룬다
- 전체 흐름 그림: `학습(내 노트북) → 제출(웹) → 자동 평가(평가 서버) → 리더보드 → 오프라인 본선`
- **순위 규칙** — §3 표 전체 (특히 "3바퀴 전부 완주 + 합산 시간")
- 하루 3회 / 동시 1건 / 500MB / 대기열
- 리더보드 화면 읽는 법 — 완주 기록, 미완주 시 진행률과 실패 사유
- 일정과 오프라인 본선의 관계, **"본선 갈 모델은 학습이 끝난 직후 반드시 받아둬야 한다"** 경고 (10번으로 링크)

### 01. 강화학습 개념 — "강아지 훈련으로 이해하기"

**목적**: 용어의 벽을 없앤다. 수식 없이.

- 지도학습과 뭐가 다른가 — 정답지가 없고 **점수(보상)만 있다**
- 5개 단어: 에이전트 / 환경 / 상태 / 행동 / 보상 → 딥레이서 대응표
  (자동차 / 트랙 / 카메라 이미지 / 조향·속도 / 보상함수가 돌려주는 값)
- 에피소드와 스텝 — 한 판, 한 순간
- **왜 시행착오가 필요한가** — 처음엔 아무렇게나 달린다. 그게 정상이다
- **지연 보상** — 지금 잘한 행동의 결과가 3초 뒤에 나온다
- **탐험 vs 활용** — 새 길을 시도할까, 아는 길로 갈까
- 흔한 오해 3가지: "보상을 크게 주면 빨리 배운다"(아님) / "코드가 차를 조종한다"(아님, 점수만 준다) / "오래 돌리면 항상 좋아진다"(아님)
- 마지막 한 줄: **"보상함수는 명령이 아니라 채점표다"** — 06번의 전제

### 02. 딥레이서 학습 구조 — "무엇을 건드리면 무엇이 바뀌나"

**목적**: 보상함수 말고도 손댈 수 있는 손잡이가 무엇인지, 각각이 어디에 영향을 주는지.

- 카메라 이미지 → 신경망 → 행동 선택. 입력이 **이미지 한 장**뿐이라는 사실이 주는 제약
- 학습 루프: 여러 에피소드 수집 → 신경망 갱신 → 반복 (PPO는 이름만, 원리는 비유로)
- **에피소드가 끝나는 조건** — 완주 / 코스아웃 / 최대 스텝
- **학습(training)과 평가(evaluation)의 차이** — 평가에는 무작위 탐험도 보상도 없다.
  *학습 중 성적이 좋아도 평가에서 다르게 나오는 이유*
- **액션 스페이스** — 이산 vs 연속, 속도/조향 범위를 어떻게 잡나, 최고속을 올렸을 때 실제로 생기는 일
- **하이퍼파라미터** 표: learning rate / batch size / entropy / discount factor / epochs / 에피소드 수
  → 각각 "올리면 / 내리면 어떻게 되나"를 한 줄씩
- 학습 시간과 수렴 — 언제까지 돌려야 하나 (08번으로 연결)
- `> [더 알고 싶다면]` 박스: 정책경사, PPO의 clip, 가치함수

### 05. 보상함수 파라미터 사전 — 참조용

**목적**: 읽는 문서가 아니라 **찾는 문서**.

- 전체 파라미터 표 (이름 / 타입 / 단위 / 범위 / 한 줄 설명)
  `all_wheels_on_track, x, y, heading, distance_from_center, track_width, track_length,
  is_left_of_center, is_offtrack, is_crashed, is_reversed, progress, speed, steering_angle,
  steps, closest_waypoints, waypoints, closest_objects, objects_*`
- 자주 쓰는 5개 심화: `distance_from_center`, `progress`, `steps`, `speed`, `closest_waypoints`
- **좌표와 각도** — `heading`의 기준(-180~180), waypoint 두 개로 진행 방향 구하기, `math.atan2`
- **함정 모음**
  - `track_width`는 **전체 폭**이다 → 중앙 기준으로 쓰려면 절반으로 나눠야 한다
  - `steps`는 15fps 기준 → `progress/steps`가 "효율" 지표가 되는 이유
  - `all_wheels_on_track`과 `is_offtrack`은 같은 말이 아니다
  - 물체 관련 파라미터(`objects_*`)는 이번 대회 트랙에서는 쓰지 않는다
- 출처: [AWS 공식 파라미터 문서](https://docs.aws.amazon.com/deepracer/latest/developerguide/deepracer-reward-function-input.html)

### 06. 보상함수 작성법과 예시 — 가장 중요한 문서

**목적**: 복붙에서 **의도를 가진 설계**로 넘어가게 한다.

- 보상함수의 뼈대 — `def reward_function(params) -> float`, 반환값의 의미
- **설계 원칙 5가지**
  1. 원하는 결과가 아니라 **원하는 행동**에 점수를 준다
  2. 스케일을 통제한다 (값이 폭주하면 학습이 망가진다)
  3. 급격한 절벽보다 **완만한 곡선** (07번이 이걸 눈으로 확인하는 문서)
  4. 조건을 늘릴수록 서로 상쇄된다 — 항목은 적게, 가중치는 명확하게
  5. 코스아웃은 이미 에피소드 종료로 처벌된다 — 이중 처벌 주의
- **예시 A. 중앙선 따라가기** — 가장 기본, 왜 이게 출발점인가
- **예시 B. 지그재그 억제** — 조향 페널티
- **예시 C. 속도 보상** — 직선에서만 주기 (코너에서 주면 코스아웃)
- **예시 D. 효율 보상** — `progress / steps`
- **예시 E. 주행선(racing line) 추종** — waypoint로 이상적 경로를 만들고 거기에 붙이기
- **예시 F. 이번 대회용 조합** — §3 규칙(3바퀴 전부 완주)을 반영해 **완주 안정성에 무게를 둔** 버전
- **안티패턴** — `return 0` 남발 / 음수 보상 / if 20개 / 완주에만 큰 보상(희소 보상)
- 각 예시마다 반드시: 코드 → **무엇을 노렸나 / 어떤 부작용이 생기나 / 언제 쓰나**
- 참고: [AWS 보상함수 예시](https://docs.aws.amazon.com/deepracer/latest/developerguide/deepracer-reward-function-examples.html)

### 07. 보상함수를 그래프로 검증하기

**목적**: 4시간짜리 학습을 돌리기 **전에** 5분 만에 함수가 이상한지 확인한다.

- 왜 그리나 — 코드를 읽어서는 "절벽"이 안 보인다. 그림엔 보인다
- **1단계: 파라미터 1개 vs 보상 곡선** — `distance_from_center`를 0부터 폭 절반까지 훑으며 그리기 (matplotlib 코드 그대로 제공)
- 좋은 곡선 / 나쁜 곡선 대조 그림 — 계단형, 불연속, 한쪽만 0, 스케일 폭주
- **2단계: 파라미터 2개 히트맵** — 속도 × 조향 같은 조합
- **3단계: 트랙 위에 그리기** — waypoint를 뿌려 트랙을 그리고 그 위에 보상을 색으로 얹기
- **4단계: 학습 로그로 검증** — `SIM_TRACE_LOG`를 읽어 실제 궤적·속도·보상을 트랙에 얹는다 (08번과 연결)
- 도구: 로컬 matplotlib / 주피터 / (수식만 볼 거면) Desmos
- 체크리스트: 연속인가 / 단조로운가 / 최댓값 위치가 의도대로인가 / 최솟값이 0 이상인가

### 08. 로그 읽고 모델 개선하기

**목적**: "학습은 돌아가는데 기록이 안 나온다"를 푸는 문서.

- `SIM_TRACE_LOG` 한 줄의 구조 (기존 `01-환경설정.md` §12를 흡수·확장)
- 볼 지표 3개: **완주율**, 에피소드당 보상 추이, 랩타임 추이
- **언제 멈추나** — 보상이 평평해지고 완주율이 더 안 오르면
- **증상 → 처방 표**

  | 증상 | 흔한 원인 | 해볼 것 |
  |---|---|---|
  | 같은 자리에서 항상 코스아웃 | 그 코너에서 속도 과함 | 최고속 낮추기 / 코너 속도 페널티 |
  | 완주는 하는데 느림 | 중앙선 보상만 있음 | 효율·속도 보상 추가 (예시 C·D) |
  | 지그재그 | 조향 페널티 없음 | 예시 B |
  | 보상은 오르는데 완주는 안 됨 | 보상이 완주와 무관 | 보상 재설계 |
  | 초반만 좋고 이후 나빠짐 | learning rate 과함 / 보상 폭주 | 07번으로 곡선 확인 |

- **이어학습(클론)** — 기존 모델에서 이어 학습, 트랙 바꿔 일반화
- 제출 전 자체 평가 — **본 대회와 같은 3바퀴 조건으로 미리 돌려본다**

## 6. 공통 형식 규칙

`docs/study/`의 [쉬움]/[전공] 2단 구성은 **그대로 쓰지 않는다.** 참가자 문서는 본문이
곧 [쉬움]이고, 깊은 내용은 접어 넣는다.

- 모든 코드 블록은 **복붙 가능한 완성형** (조각 금지)
- 문서 끝에 **"이 문서를 읽고 답할 수 있어야 하는 질문" 3~5개**
- 대회 규칙을 인용할 때는 §3 표의 값만 쓴다 (문서마다 다른 숫자가 돌아다니는 것을 막는다)
