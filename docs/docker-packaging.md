> **이 문서는 조사·판단 문서다. 구현 지시서가 아니다.**
> "내년 회장이 운영하기 쉽도록 도커 이미지를 만들자"는 아이디어가 실제로 얼마나 도움이 되는지,
> 어디까지 가능하고 어디부터는 불가능한지를 정리한다. 실제로 만들기로 정하면

## 0. 결론부터

| 질문 | 답 |
|---|---|
| 도커 이미지를 우리 서비스에 적용할 수 있나 | **웹 쪽은 이미 적용돼 있다.** `Dockerfile`과 `docker-compose.prod.yml`이 이미 그것이다 |
| 그럼 뭘 더 할 수 있나 | 이미지를 **레지스트리에 올려두는 것**(서버에서 빌드하지 않고 받아 쓰기). 실익이 가장 큰 한 가지다 |
| 평가 워커·DRFC도 이미지로 만들 수 있나 | **기술적으로는 가능하지만 권할 만하지 않다.** DRFC 자체가 이미 컨테이너를 띄우는 도구라 중첩이 된다. 이쪽은 도커 이미지가 아니라 **AMI**가 맞는 도구이고, 이미 그렇게 하고 있다 |
| 이미지를 만들면 인수인계가 쉬워지나 | **부분적으로만.** 다음 회장이 겪을 어려움의 대부분은 "설치"가 아니라 **"계정·비밀값·도메인·요금"**이고, 이건 이미지가 담을 수 없는 영역이다 (§5) |

**한 줄 요약**: 도커 이미지는 *"프로그램을 어떻게 설치하지?"* 를 없애준다.
*"이 서비스의 비밀번호가 뭐지? 도메인 결제는 누가 하지? AWS 계정은 누구 거지?"* 는 그대로 남는다.
그리고 우리 프로젝트에서 진짜 무서운 건 후자다.

## 1. 도커 이미지란 무엇인가

### 1.1 쉽게

컴퓨터에 프로그램을 설치해 본 적이 있다면, 이런 경험을 했을 것이다.

> "파이썬 3.12 깔고, pip로 라이브러리 12개 깔고, PostgreSQL 깔고, 설정 파일 고치고…
> 어? 내 노트북에선 되는데 왜 다른 컴퓨터에선 안 되지?"

**도커 이미지는 "이 프로그램이 돌아가는 데 필요한 것 전부를 통째로 찍은 사진"이다.**
운영체제 파일, 파이썬, 라이브러리, 우리 코드까지 전부 한 덩어리로 굳혀 놓은 것.

비유하자면 이렇다.

| 개념 | 비유 |
|---|---|
| **이미지(image)** | **밀키트**. 재료가 손질돼 한 봉지에 담겨 있다. 그 자체로는 아직 요리가 아니다 |
| **컨테이너(container)** | 밀키트를 **실제로 조리해 접시에 담은 것**. 하나의 밀키트로 여러 접시를 만들 수 있다 |
| **Dockerfile** | 밀키트를 만드는 **레시피**. "쌀 넣고, 야채 썰어 넣고…" |
| **레지스트리(registry)** | 밀키트를 사고파는 **마트**. Docker Hub, GitHub Container Registry(GHCR) 등 |
| **볼륨(volume)** | 밀키트에 들어 있지 **않은** 것 — 접시, 남은 음식. 즉 **데이터**. 밀키트를 새로 사도 어제 먹다 남긴 건 그대로 있어야 한다 |

마지막 줄이 핵심이다. **이미지에는 "프로그램"만 들어가고 "데이터"는 들어가지 않는다.**
우리 DB의 팀 목록도, 참가자가 올린 모델 파일도, 평가 영상도 이미지에는 없다.

### 1.2 조금 더 정확하게

- 이미지는 **읽기 전용 레이어의 스택**이다. `Dockerfile`의 명령 하나가 레이어 하나를 만든다.
  그래서 `requirements.txt`를 코드보다 먼저 `COPY`하면(우리 `Dockerfile`이 그렇게 하고 있다),
  코드만 고쳤을 때 라이브러리 설치 레이어를 캐시에서 재사용해 빌드가 빨라진다.
- 컨테이너는 그 스택 위에 **쓰기 가능한 얇은 레이어 하나**를 얹어 실행한 것이다.
  컨테이너를 지우면 그 레이어도 사라진다 — 그래서 남아야 할 것은 볼륨에 둔다.
- 이미지는 **태그**로 버전을 구분한다(`myapp:v1.3`, `myapp:latest`).
  태그를 붙여 레지스트리에 올려두면 **"어제 버전으로 되돌리기"가 명령 한 줄**이 된다.
- 이미지는 **CPU 아키텍처에 묶인다**(`amd64` / `arm64`). 노트북에서 만든 이미지가
  서버에서 안 돌 수 있다. 우리 서버(Lightsail·EC2)는 모두 `amd64`다.

## 2. 우리 서비스는 지금 어떤 상태인가

**이미 절반 이상 도커화되어 있다.** 새로 시작하는 게 아니다.

```
[클라우드 서버 — Lightsail]              [평가 서버 — EC2]
                                          
  ┌─ caddy    (컨테이너) ─┐                호스트에서 직접 실행:
  ├─ web      (컨테이너) ─┤ ← 도커화 완료    ├─ worker/run.py  (systemd)
  └─ db       (컨테이너) ─┘                └─ DRFC (bin/activate.sh)
                                               │
     docker-compose.prod.yml                   └→ Docker Swarm으로 컨테이너를 띄운다
                                                  ├─ robomaker  (시뮬레이션)
                                                  ├─ rl_coach   (평가 제어)
                                                  └─ minio      (모델 저장소)
```

| 구성요소 | 지금 | 이미지로 배포되고 있나 |
|---|---|---|
| `web` (FastAPI) | 컨테이너 | ✅ 컨테이너지만 ❌ **서버에서 직접 빌드**한다 (`build: .`) |
| `db` (PostgreSQL) | 컨테이너 | ✅ 공식 이미지 `postgres:16`을 받아 쓴다 |
| `caddy` | 컨테이너 | ✅ 공식 이미지 `caddy:2` |
| 평가 워커 (`worker/run.py`) | EC2 호스트에서 systemd | ❌ |
| DRFC | EC2 호스트 스크립트 | ❌ (단, DRFC가 **띄우는** 것들은 전부 컨테이너다) |

여기서 `web`의 `build: .`이 눈여겨볼 지점이다. 지금은 **서버에 소스코드를 내려받아 서버에서
빌드**한다. 이건 이미지의 장점을 절반만 쓰는 것이다 — §4.1에서 다시 다룬다.

## 3. 구성요소별로 — 어디까지 가능한가

### 3.1 `web` — 이미 됐고, 더 좋게 만들 여지가 있다 ✅

가능하다. 이미 되어 있다. 남은 개선은 **빌드된 이미지를 레지스트리에 올려두는 것**이다(§4.1).

### 3.2 `db` / `caddy` — 손댈 것 없다 ✅

공식 이미지를 쓰고 있다. 우리가 만들 이미지가 아니다.

### 3.3 평가 워커 (`worker/run.py`) — 가능하지만 권하지 않는다 ⚠️

**기술적으로는 가능하다.** 파이썬 프로그램이니 `Dockerfile`을 하나 더 쓰면 된다.
문제는 이 워커가 **하는 일**이다.

워커는 `dr-start-evaluation`을 호출하고, 그것이 **호스트의 Docker Swarm에 스택을 배포**한다
(`worker/run_evaluation.sh` — 스택 이름 `deepracer-eval-$DR_RUN_ID`).
즉 **워커는 도커를 조종하는 프로그램**이다. 이걸 컨테이너에 넣으면 "컨테이너 안에서 바깥 도커를
조종"해야 한다. 방법은 있다 — 호스트의 `/var/run/docker.sock`을 컨테이너에 마운트하는
**Docker-outside-of-Docker** 방식이다. 하지만 대가가 있다.

| 대가 | 내용 |
|---|---|
| 보안 | `docker.sock`을 마운트한 컨테이너는 **사실상 호스트 root 권한**을 갖는다. 격리의 의미가 거의 사라진다 |
| 경로 불일치 | 컨테이너 안의 `/app/storage`와 호스트의 `/home/ubuntu/...`가 다르다. DRFC에 넘기는 경로가 **호스트 기준**이어야 해서 경로 변환 버그가 나기 쉽다 |
| 디버깅 | 지금은 `journalctl -u ...`나 `/tmp/worker.log`로 끝난다. 컨테이너가 끼면 로그 계층이 하나 더 생긴다 |
| 실익 | 워커가 설치를 어려워한 적이 없다. `pip install -r requirements.txt`가 전부다. **어려운 건 DRFC 설치와 Tailscale 등록이지 워커가 아니다** |

**판단: 하지 않는다.** 얻는 것보다 잃는 것이 많다.

### 3.4 DRFC — 이미지로 만들 대상이 아니다 ❌

DRFC(deepracer-for-cloud)는 **그 자체가 컨테이너 오케스트레이션 도구**다.
`dr-start-evaluation`은 Docker Swarm에 robomaker·rl_coach·minio 컨테이너를 띄우는 셸 스크립트 묶음이다.

이걸 이미지로 감싸는 건 **"컨테이너를 띄우는 도구를 컨테이너에 넣는 것"** 이라 중첩이 된다.
게다가 DRFC의 설정은 `run.env`·`system.env` 같은 **서버마다 다른 파일**에 들어 있어
(평가 조건 `DR_EVAL_MAX_RESETS=15`, `DR_WORLD_NAME=Vegas_track` 등 —
[worker-server-setup.md](worker-server-setup.md) §7.3) 이미지에 굳혀 넣으면 오히려 바꾸기 어려워진다.

**대신 이 영역에는 이미 맞는 도구가 있다 — AMI다.**
[worker-server-setup.md](worker-server-setup.md) §8.5가 그것이다. AMI는 **EC2 인스턴스 전체를 통째로
찍은 이미지**라, DRFC·Tailscale·워커·설정 파일까지 전부 포함한다. 도커 이미지보다 훨씬 넓게 담는다.

> **정리**: 평가 서버 쪽 인수인계는 "도커 이미지를 만드는 문제"가 아니라
> **"AMI를 최신 상태로 유지하고, 그 AMI로 인스턴스를 띄우는 절차를 문서화하는 문제"** 다.
> 그리고 그건 이미 되어 있다.

## 4. 그래서 실제로 실익이 있는 것

우선순위 순으로.

### 4.1 [실익 큼] `web` 이미지를 GHCR에 올려서 배포하기

**지금**: 서버에서 `git pull` → `docker compose build` → `up -d`.
**바꾸면**: GitHub Actions가 이미지를 빌드해 GHCR에 올리고, 서버는 `docker compose pull` → `up -d`.

| 얻는 것 | 설명 |
|---|---|
| **롤백이 한 줄** | `image: ghcr.io/.../web:v1.3`으로 태그만 바꾸면 어제 버전으로 되돌아간다. 대회 중 배포가 잘못됐을 때 가장 값진 기능이다 |
| 서버 부담 감소 | Lightsail의 작은 인스턴스에서 pip 빌드를 하지 않는다. 배포 시간도 짧아진다 |
| "내 PC에선 되는데" 제거 | 검증한 이미지와 배포되는 이미지가 **바이트 단위로 동일**하다 |
| 인수인계 | 다음 회장이 서버에서 빌드 환경을 신경 쓸 일이 없다 |

| 치러야 하는 비용 | 설명 |
|---|---|
| GitHub Actions 워크플로 작성 | 처음 한 번 |
| 레지스트리 인증 | 서버에서 GHCR에 로그인해야 한다(공개 이미지로 두면 불필요) |
| **이미지 공개 여부 판단** | 공개로 두면 누구나 우리 앱 이미지를 받을 수 있다. 코드는 어차피 저장소에 있으니 큰 문제는 아니지만, **비밀값이 이미지에 들어가지 않는지 반드시 확인해야 한다**(§5) |

### 4.2 [실익 중간] 개발용 원클릭 실행 정리

다음 회장이 **로컬에서 서비스를 띄워 보는 것**은 `docker compose up`으로 이미 된다.
다만 `.env` 예시 파일(`.env.example`)과 시드 데이터 절차가 문서에 흩어져 있다.
이건 **도커 이미지 문제가 아니라 문서 문제**다.

### 4.3 [실익 작음] 워커 컨테이너화

§3.3 참고. 하지 않는다.

## 5. 이미지가 절대 해결해 주지 못하는 것

**여기가 이 문서에서 가장 중요한 부분이다.** 다음 회장이 막히는 지점은 대부분 여기다.

| 항목 | 왜 이미지에 못 넣나 | 어떻게 넘겨야 하나 |
|---|---|---|
| `SESSION_SECRET`, `POSTGRES_PASSWORD`, `WORKER_TOKEN`, `ADMIN_LOGIN_PATH` | **이미지에 넣으면 안 된다.** 이미지 레이어는 뜯어볼 수 있고, 한 번 들어간 값은 나중 레이어에서 지워도 남는다 | `.env`를 안전한 경로로 직접 전달 |
| **AWS 계정** (EC2·Lightsail 요금) | 계정 소유·결제 수단 문제 | 계정 이관 또는 신규 발급 절차를 문서화 |
| **도메인** (`doublejeong.com`) | 등록기관 계정과 결제에 묶여 있다 | 소유권 이전 또는 새 도메인 |
| **Tailscale 등록** | 기기마다 인증이 필요하고 키에 만료가 있다 | [worker-server-setup.md](worker-server-setup.md) §3 절차대로 재수행 |
| **DB 데이터** (팀·기록·영상) | 볼륨이지 이미지가 아니다 | 백업/복원 절차 ([operations.md](operations.md)) |
| **HTTPS 인증서** | Caddy가 도메인 소유를 증명해 발급받는다 | 도메인이 넘어가면 자동으로 재발급된다 |
| **DRFC 평가 조건** (`run.env`) | 서버마다 다르고 대회마다 바뀐다 | [worker-server-setup.md](worker-server-setup.md) §7.3 |
| **운영 판단** — 언제 EC2를 켜고 끄는가, 대기열이 막혔을 때 뭘 보는가 | 지식이지 파일이 아니다 | [handover.md](handover.md), [operational-error-handling.md](operational-error-handling.md) |

> **비유를 다시 쓰면**: 도커 이미지는 완벽한 밀키트다. 하지만 **부엌도, 전기요금 고지서도,
> "이 집 가스레인지는 왼쪽 화구가 안 켜진다"는 요령도** 밀키트에는 들어 있지 않다.
> 다음 회장이 물어볼 질문의 대부분은 밀키트가 아니라 부엌에 대한 것이다.

**따라서 인수인계 품질을 가장 크게 올리는 일은 도커 이미지를 만드는 게 아니라
`docs/handover.md`를 계속 손보는 것이다.** 도커 이미지는 그다음이다.

## 6. 만들기로 한다면 — 먼저 정해야 할 것

§4.1(웹 이미지를 레지스트리에 올리기)을 실제로 진행하기로 하면, 아래를 먼저 결정해야 한다.
**이 문서는 여기까지고, 결정되면 tasks.md에 별도 Phase로 넣는다.**

- [ ] **레지스트리**: GHCR(저장소가 GitHub에 있으니 자연스럽다) vs Docker Hub
- [ ] **이미지 공개 범위**: public(인증 불필요, 간단) vs private(서버에서 로그인 필요)
- [ ] **태그 규칙**: `latest`만 vs 커밋 SHA vs `v1.2.3` 수동 태그
      → 롤백이 목적이라면 **불변 태그(SHA 또는 버전)** 가 필요하다. `latest`만으로는 되돌릴 수 없다
- [ ] **빌드 트리거**: `main` 푸시마다 vs 태그를 붙였을 때만
- [ ] **`docker-compose.prod.yml` 처리**: `build: .`를 `image:`로 바꾸면 **서버에서 로컬 빌드를 못 하게 된다.**
      급할 때 서버에서 직접 고쳐 띄우던 방법이 막히므로, 그 상황의 대안을 정해둬야 한다
- [ ] **마이그레이션 타이밍**: 지금 `CMD`가 `alembic upgrade head && uvicorn ...`이다.
      이미지 배포로 바뀌어도 이 동작은 유지할지 (유지하는 쪽이 단순하다)
- [ ] **`.dockerignore` 추가**: 확인해 보니 **현재 저장소에 `.dockerignore`가 없다.**
      다행히 `Dockerfile`이 `COPY . .`가 아니라 `app`·`migrations`·`alembic.ini`만 골라 복사해서
      **`.env`가 이미지에 들어가지는 않는다.** 다만 빌드할 때마다 `storage/`(모델 파일 수백 MB)까지
      빌드 컨텍스트로 도커 데몬에 전송되므로 빌드가 느려진다. `.dockerignore`에
      `storage/`·`.env`·`.git`·`__pycache__`를 넣어두는 편이 좋다
- [ ] **대회 기간 중 배포 정책**: 자동 배포까지 갈지, 이미지만 올려두고 서버 반영은 수동으로 할지
      → 대회 중이라면 **수동을 권한다**. 자동 배포는 평가 대기열이 도는 중에 웹을 재시작시킬 수 있다
