## 🏎️ DeepRacer-for-Cloud 트러블슈팅 가이드

본 문서는 `deepracer-for-cloud`를 활용한 로컬 가상 환경 구축 중 발생할 수 있는 주요 에러와 최종 해결 방법을 정리한 가이드라인입니다.

### 1. AttributeError: module 'lib' has no attribute 'X509_V_FLAG_NOTIFY_POLICY'

#### 🚨 에러 상황

`aws configure --profile minio` 명령어 실행 시 시스템 Python 패키지 충돌로 인해 발생

#### 🔍 원인 분석

- 최근 `cryptography` 패키지가 업데이트되면서 `X509_V_FLAG_NOTIFY_POLICY` 플래그가 삭제됨.
- 반면 시스템에 설치된 구버전 `pyOpenSSL`이 이 플래그를 계속 참조하려다 에러 발생.
- `apt`로 설치한 AWS CLI v1은 시스템 Python 환경에 의존하기 때문에 이 패키지 충돌의 영향을 그대로 받음.

#### 💡 최종 해결 방법 (AWS CLI v2 새 설치 추천)

시스템 Python 환경과 완전히 독립되어 작동하는 AWS CLI v2를 설치하는 것이 가장 깔끔하고 근본적인 해결책입니다.

```bash
# 1. 기존 구버전 awscli 제거
sudo apt remove awscli -y
sudo apt autoremove -y

# 2. AWS CLI v2 다운로드 및 설치
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
sudo apt install unzip -y
unzip awscliv2.zip
sudo ./aws/install

# 3. 설치 확인 및 재시도
aws --version
aws configure --profile minio
```

### 2. Error response from daemon: This node is not a swarm manager.

#### 🚨 에러 상황

`source bin/activate.sh` 실행 시 도커 스웜(Docker Swarm) 관련 경고 문구와 함께 활성화 실패

#### 🔍 원인 분석

- `deepracer-for-cloud` 환경은 로컬 MinIO 서버와 학습 컨테이너들을 관리하기 위해 Docker Swarm 기능을 사용함.
- 도커가 초기 상태이거나 스웜 모드가 활성화되어 있지 않아 발생.

#### 💡 최종 해결 방법

현재 노드를 Docker Swarm의 매니저 노드로 초기화해 줍니다.

```bash
# Docker Swarm 모드 활성화
docker swarm init

# (참고) WSL2 등에서 IP 선택 에러 발생 시 아래 명령어 사용
docker swarm init --advertise-addr 127.0.0.1
```

### 3. bash: eval: line 14: syntax error near unexpected token `newline` (export DR_DOCKER_STYLE=&lt;DOCKER_STYLE&gt;)

#### 🚨 에러 상황

`source bin/activate.sh` 실행 시 특정 라인에서 구문 오류(`syntax error`) 발생

#### 🔍 원인 분석

- `system.env` 설정 파일 내에 기본 템플릿 값인 `DR_DOCKER_STYLE=<DOCKER_STYLE>`이 그대로 남아있음.
- 리눅스 셸(Bash)에서 괄호(`< >`)는 입출력 리다이렉션 기호로 해석되기 때문에 문법 에러가 발생함.
- 주의: `sudo ./bin/init.sh`를 실행하면 `system.env` 파일이 항상 초기 템플릿 상태로 덮어써지므로(리셋), 수정 순서가 중요함.

#### 💡 최종 해결 방법

명령어 실행 순서를 [init.sh 실행 ➡️ system.env 파일 수정 ➡️ activate.sh 실행]으로 진행해야 합니다.

```bash
# 1. 초기화 스크립트 먼저 실행 (파일이 리셋됨)
sudo ./bin/init.sh -a cpu -c local

# 2. 리셋된 system.env 파일 수정
nano system.env

# [수정 사항] 아래 라인을 찾아 괄호를 지우고 swarm으로 변경 후 저장 (Ctrl+O -> Enter -> Ctrl+X)
# 변경 전: DR_DOCKER_STYLE=<DOCKER_STYLE>
# 변경 후: DR_DOCKER_STYLE=swarm
```

### 4. network "sagemaker-local" is declared as external, but could not be found.

#### 🚨 에러 상황

`source bin/activate.sh` 실행 시 `sagemaker-local` 네트워크를 찾을 수 없다는 에러와 함께 스택 배포 실패

#### 🔍 원인 분석

- WSL2 환경의 권한 문제 등으로 인해 `init.sh` 스크립트 내부에서 오버레이(Overlay) 가상 네트워크 생성 및 노드 라벨링 설정 단계가 정상적으로 완료되지 못함.

#### 💡 최종 해결 방법

네트워크와 필수 설정을 터미널에서 수동으로 직접 강제 주입해 줍니다.

```bash
# 1. sagemaker-local 오버레이 네트워크 수동 생성
docker network create -d overlay --attachable sagemaker-local

# 2. 현재 도커 스웜 노드 ID를 가져와 필수 라벨링 추가 (컨테이너 배치용)
SWARM_NODE=$(docker node ls -q)
docker node update --label-add Sagemaker=true $SWARM_NODE
docker node update --label-add Robomaker=true $SWARM_NODE

# 3. 환경 활성화 재시도
source bin/activate.sh
```

### 5. expr: non-integer argument (run.env 필수 변수 누락)

#### 🚨 에러 상황

`dr-start-training` 실행 시 `expr: non-integer argument` 에러가 여러 줄 발생하며 학습이 시작되지 않거나, `Selected path ... exists` 메시지와 함께 강제 종료됨.

#### 🔍 원인 분석

- `sudo ./bin/init.sh` 초기화 스크립트를 실행하면 `system.env`뿐만 아니라 `run.env` 파일도 기본 템플릿 상태로 리셋(덮어쓰기)됨.
- 리셋된 `run.env` 내부에 학습 및 평가 시간을 결정하는 필수 변수(`DR_TRAIN_MINUTES`, `DR_EVAL_MINUTES`)가 누락되었거나 숫자가 아닌 `<MINUTES>` 같은 템플릿 문자로 채워져 있어, 내부 스크립트가 연산(`expr`)할 때 정수가 아니라는 문법 에러를 발생시킴.
- 또한, `DR_LOCAL_S3_MODEL_PREFIX` 경로 설정이 고정되어 있으면 모델 ID를 바꿔도 계속 같은 MinIO 폴더를 바라보게 되어 중복 에러(`Selected path exists`)가 발생함.

#### 💡 최종 해결 방법

`run.env` 파일을 열어 누락된 필수 시간 변수를 주입하고, 모델 저장 경로가 ID에 따라 동적으로 바뀌도록 수정합니다.

```bash
# 1. run.env 파일 편집
nano run.env

# [수정 사항 1] 중간에 있는 모델 경로 설정을 찾아 ID 변수($DR_RUN_ID) 기반으로 동적 변경
# 변경 전: DR_LOCAL_S3_MODEL_PREFIX=rl-deepracer-sagemaker
# 변경 후: DR_LOCAL_S3_MODEL_PREFIX=rl-deepracer-sagemaker-$DR_RUN_ID

# [수정 사항 2] 파일 최하단에 누락된 필수 시간 변수(정수형) 직접 추가
DR_TRAIN_MINUTES=60
DR_EVAL_MINUTES=15

# 2. 저장 후 학습 재시작 (ID가 겹치지 않는다면 정상 구동됨)
dr-start-training
```

> 💡 참고: 학습이 정상적으로 시동되면 터미널에 `Creating service deepracer...` 문구와 함께 대량의 환경 변수 JSON 로그가 출력되며, 마지막에 `Redis is starting oO0OoO0OoO0Oo` (벽돌 아스키 아트) 화면이 나타납니다. 이는 에러가 아니라 서버 인터페이스가 성공적으로 가동되었다는 신호입니다.

# 5부. 뭔가 꼬인 것 같을 때, 싹 다 밀어버리는 방법

> ⚠️ 이 절의 명령어들은 **되돌릴 수 없다.** `wsl --unregister`, `docker system prune -a --volumes`,
> `rm -rf ~/.aws` 는 실행 즉시 데이터가 영구 삭제된다. 아래 본문의 백업 안내를 반드시 먼저 읽는다.

## 5-1. Ubuntu 자체를 완전 초기화

Windows PowerShell에서 먼저 배포판 이름 확인:

```powershell
wsl -l -v
```

예를 들어:

```text
NAME            STATE     VERSION
Ubuntu-22.04    Running   2
```

이라면, 중요한 파일이 조금이라도 있으면 먼저 백업:

```powershell
wsl --export Ubuntu-22.04 D:\ubuntu-backup.tar
```

Microsoft 공식 문서에서도 `wsl --export`로 배포판 전체 snapshot을 만들 수 있다.

그다음:

```powershell
wsl --shutdown
```

그리고 핵폭탄 버튼:

```powershell
wsl --unregister Ubuntu-22.04
```

이 순간 그 Ubuntu 안에 있던 모든 파일, 프로그램, 설정이 영구 삭제된다.

즉,

```text
deepracer-for-cloud
Docker
Docker images
Docker containers
MinIO
MinIO 데이터
AWS CLI 설정
~/.aws
~/.profile 수정
Python 환경
apt로 설치한 패키지
DRFC system.env
DRFC run.env
각종 export 환경변수
```

까지 싹 사라진다. Microsoft도 `wsl --unregister`가 해당 배포판의 data, settings, software 전체를 영구 제거한다고 명시한다.

그 다음 다시:

```powershell
wsl --list --online
```

원하는 Ubuntu 확인하고:

```powershell
wsl --install -d Ubuntu-22.04
```

하면 완전히 새 Ubuntu에서 다시 시작할 수 있다.

## 5-2. Ubuntu는 남기고 DRFC 관련만 전부 지우고 싶다면

찌꺼기가 남을 가능성이 있어서 나는 위 방법을 선호하지만, 다른 프로젝트가 Ubuntu 안에 있다면 이걸 써야 한다.

Ubuntu에서 먼저 Docker 리소스를 전부 삭제한다.

```bash
docker ps -aq | xargs -r docker rm -f

docker system prune -a --volumes -f
```

`docker system prune -a --volumes`는 사용되지 않는 container, network, image, volume 등을 제거한다. 특히 `--volumes`를 넣어야 volume도 청소된다.

주의: 이 Docker 엔진을 다른 프로젝트도 사용하고 있으면 그 Docker 데이터도 같이 날아간다.

DRFC에서 Docker Swarm을 사용했으면:

```bash
docker swarm leave --force
```

DRFC 저장소 삭제:

```bash
cd ~
rm -rf ~/deepracer-for-cloud
```

다른 위치에 clone했다면:

```bash
find ~ -maxdepth 3 -type d -name "deepracer-for-cloud" 2>/dev/null
```

찾아서 삭제하면 된다.

DRFC local mode의 MinIO 데이터는 기본적으로 DRFC 저장소 안의 `docker/volumes`에 저장되므로 저장소를 날리면 이것도 같이 삭제된다.

AWS CLI profile도 확인:

```bash
aws configure list-profiles
```

예를 들어:

```text
default
minio
```

처럼 나올 수 있다.

AWS 설정 전체가 DRFC용이었다면:

```bash
rm -rf ~/.aws
```

하면 된다.

하지만 AWS를 다른 프로젝트에서도 쓴다면 `~/.aws` 전체 삭제하면 안 된다. DRFC 공식 문서상 MinIO credential 역시 `~/.aws/credentials`의 profile을 사용한다.

마지막으로 shell 설정에 DRFC가 박혀 있는지 확인:

```bash
grep -nEi 'deepracer|DR_|activate\.sh' \
    ~/.profile ~/.bashrc ~/.bash_profile 2>/dev/null
```

예를 들어 이런 게 남아 있으면:

```text
source ~/deepracer-for-cloud/bin/activate.sh
export DRFC_WSL_IP=...
export DR_LOCAL_S3_ENDPOINT_URL=...
```

직접 지워주면 된다.
