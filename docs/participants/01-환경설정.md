## 0. 전체 흐름

전체 과정은 아래 순서로 진행한다.

```text
WSL2 / Ubuntu 준비
→ Docker Desktop 준비 및 WSL 연결
→ DeepRacer for Cloud(DRfC) 설치
→ Docker Swarm / MinIO 초기화
→ DRfC 환경 활성화
→ 학습 파일 업로드
→ 학습 시작
→ 학습 상태 확인
→ 학습 종료
→ 저장된 모델 확인
→ 제출용 모델만 추출
→ .tar.gz로 압축
→ 제출 사이트 업로드
```

## 1. 권장 환경

이번 FATI 실습에서 실제로 사용한 환경은 다음과 같다.

```text
Windows 11
WSL2
Ubuntu 22.04
Docker Desktop
DeepRacer for Cloud
CPU 학습
```

Docker Desktop은 Intel/AMD Windows 노트북의 경우:

```text
Download for Windows - AMD64
```

버전을 설치한다.

> `AMD64`는 일반적인 Intel/AMD 64비트 Windows PC용이다.

## 2. WSL 배포판 확인

PowerShell에서:

```powershell
wsl -l -v
```

예시:

```text
NAME              STATE      VERSION
Ubuntu-18.04      Running    2
Ubuntu-20.04      Running    2
Ubuntu-22.04      Stopped    2
docker-desktop    Running    2
```

Ubuntu 22.04를 기본으로 사용하려면:

```powershell
wsl --set-default Ubuntu-22.04
```

Ubuntu 22.04를 직접 실행하려면:

```powershell
wsl -d Ubuntu-22.04
```

Ubuntu 안에서 버전 확인:

```bash
cat /etc/os-release
```

---

\* 주의: Ubuntu 20.04에서 [prepare.sh](http://prepare.sh) 실행 불가.
Ubuntu 22.04 WSL 환경으로 변경하여 진행

```powershell
wsl --set-default Ubuntu-22.04
wsl -d Ubuntu-22.04
```

## 3. Docker Desktop 설정

\* Docker를 사용한 적 있는 경우 [3-2. 해당 노트북에서 Docker를 이미 사용한 적 있는 경우](#3-2-해당-노트북에서-docker를-이미-사용한-적-있는-경우)로 넘어갑니다.

### 3-1. 해당 노트북에서 Docker를 사용한 적 없는 경우

Docker Desktop을 설치한다.

설치 시 다음 설정을 사용한다.

```text
Per-user installation
Use WSL 2 instead of Hyper-V
Allow Windows Containers → 체크하지 않음
```

설치 후 Docker Desktop 실행 후 다음을 들어간다.:

```text
Settings
→ Resources
→ WSL Integration
```

다음 설정을 켠다.

```text
Enable integration with my default WSL distro
Ubuntu-22.04 → ON
```

설정 후:

```text
Apply & Restart
```

PowerShell에서 WSL을 다시 시작한다.

```powershell
wsl --shutdown
wsl -d Ubuntu-22.04
```

Ubuntu에서 Docker 확인:

```bash
docker --version
```

테스트:

```bash
docker run --rm hello-world
```

다음 문구가 나오면 Docker 연결 성공이다.

```text
Hello from Docker!
```

> `docker: command not found`가 나오면
> → [02-에러해결.md 3-1](02-에러해결.md#3-1-docker-command-not-found)
>
> `Failed to start docker.service: Unit docker.service not found.`가 나오면
> → [02-에러해결.md 3-2](02-에러해결.md#3-2-dockerservice가-없다고-나오는-경우)

### 3-2. 해당 노트북에서 Docker를 이미 사용한 적 있는 경우

이미 Docker Desktop이 설치되어 있다면 새로 Docker Engine을 설치하지 않고 기존 Docker Desktop을 사용한다.

우선 Docker Desktop을 실행한다.

그 후:

```text
Settings
→ Resources
→ WSL Integration
```

에서 현재 사용하는:

```text
Ubuntu-22.04
```

가 ON인지 확인한다.

Ubuntu에서:

```bash
docker --version
docker info
```

가 정상적으로 실행되면 바로 DRfC 설치 단계로 넘어간다.

## 5. DeepRacer for Cloud 설치

```bash
cd ~
```

```bash
git clone https://github.com/aws-deepracer-community/deepracer-for-cloud.git
```

이동:

```bash
cd ~/deepracer-for-cloud
```

CPU + 로컬 MinIO 환경으로 초기화:


```bash
./bin/init.sh -a cpu -c local
```

## 8. DRfC 환경 활성화

DRfC 폴더에서:

```bash
source bin/activate.sh
```

환경 확인:

```bash
dr-summary
```

정상 예시:

```text
Docker style      swarm
Cloud / Bucket    local bucket
Workers           1
Race type         TIME_TRIAL
World / track     reinvent_base
```

새 터미널을 열었거나 WSL을 다시 시작했을 때 `dr-*` 명령이 동작하지 않으면 다시 실행한다.

```bash
cd ~/deepracer-for-cloud
source bin/activate.sh
```

이미 활성화되었는지 확인:

```bash
type dr-start-training
```

다음처럼 나오면 다시 `source`할 필요 없다.

```text
dr-start-training is a function
```

## 9. 학습용 파일 / 설정 업데이트 / 업로드

### 9-1. 학습용 파일

기본적으로 `custom_files` 안에 다음 파일들이 존재한다.

```text
custom_files/
├── reward_function.py
├── model_metadata.json
└── hyperparameters.json
```

이미 파일들이 있다면 새로 복사할 필요 없다.

확인:

```bash
ls custom_files
```

### 9-2. 학습 설정 업데이트

환경변수만 다시 반영하려면:

```bash
dr-update-env
```

다만 `dr-start-training` 함수 자체에서 먼저 `dr-update-env`를 호출하므로, 일반적으로 학습 직전에 별도로 실행하지 않아도 된다.

확인:

```bash
type dr-start-training
```

예시:

```bash
dr-start-training ()
{
    dr-update-env;
    $DR_DIR/scripts/training/start.sh "$@"
}
```

### 9-3. 학습 파일 업로드

```bash
dr-upload-custom-files
```

업로드 대상:

```text
reward_function.py
model_metadata.json
hyperparameters.json
```

이 파일들이 로컬 MinIO의:

```text
s3://bucket/custom_files/
```

에 저장된다.

## 12. 학습 로그 읽는 법

예시:

```text
Training> Name=main_level/agent, Worker=0, Episode=1,
Total reward=14.77, Steps=77, Training iteration=0
```

의미:

```text
Episode=1
→ 첫 번째 에피소드

Total reward=14.77
→ 해당 에피소드에서 받은 누적 보상

Steps=77
→ 해당 에피소드에서 수행한 step 수

Training iteration=0
→ 아직 첫 번째 학습 iteration

Worker=0
→ 첫 번째 시뮬레이션 worker
```

초기에는 낮은 reward와 짧은 step이 나와도 정상이다.

여러 episode를 학습하며 다음을 본다.

```text
Total reward 증가 여부
Steps 증가 여부
Training iteration 증가 여부
트랙 progress 증가 여부
완주 발생 여부
```

### RoboMaker `SIM_TRACE_LOG` 읽기

예:

```text
SIM_TRACE_LOG:39,110,...,17.71,...,in_progress,...
```

주요 의미:

```text
39
→ Episode 번호

110
→ Step 번호

17.71
→ 트랙 진행률 약 17.71%

in_progress
→ 아직 에피소드 진행 중
```

따라서:

```text
Episode 39
Step 110
Progress 17.71%
```

정도로 해석할 수 있다.

### 완주 여부 확인

단순히 로그에:

```text
,100,
```

이 있는지 검색하면 안 된다.
`Step=100`도 검색되기 때문이다.

진행률이 100%에 가까운 로그를 찾으려면:

```bash
dr-logs-robomaker | grep --line-buffered "SIM_TRACE_LOG" | \
awk -F',' '$15 >= 99.9 {print}'
```

또는:

```bash
dr-logs-robomaker | grep --line-buffered -Ei \
"lap_complete|episode_complete|finished"
```

등으로 확인한다.

## 13. 학습 종료 시점과 종료

학습 시간이 오래됐다고 무조건 종료하지 않는다.

다음과 같은 지표를 본다.

```text
Total reward가 지속적으로 개선되는가
Steps가 늘어나는가
progress가 높아지는가
완주 episode가 발생하는가
여러 iteration 동안 성능이 정체되는가
```

완주가 반복적으로 발생하거나 성능 향상이 정체되면 종료를 고려한다.

### 학습 종료

```bash
dr-stop-training
```

정상적인 종료 과정에서는:

```text
Stopping service ...
Removing service deepracer-0_rl_coach
Removing service deepracer-0_robomaker
```

등이 출력된다.

확인:

```bash
docker service ls
```

정상적으로 종료되었다면 보통:

```text
s3_minio   1/1
```

만 남는다.

## 14. 노트북 종료 / 절전 관련

학습은 로컬 Docker + WSL에서 실행된다.

따라서 노트북이:

```text
절전
최대 절전
종료
재부팅
```

상태가 되면 학습은 계속 진행되지 않는다.

화면만 꺼지는 것은 상관없지만 시스템 자체가 깨어 있어야 한다.

학습 중에는 가능하면:

```text
전원 연결
절전 사용 안 함
Docker Desktop 실행 유지
```

상태로 두는 것이 좋다.

인터넷은 Docker 이미지 다운로드 등이 완료된 뒤의 로컬 학습 자체에는 항상 필요한 것은 아니다.

## 15. 껐다 켠 뒤 다시 학습하기

노트북을 완전히 종료했다가 다시 켠 경우 기존 학습 프로세스는 살아 있지 않다고 보는 것이 안전하다.
하지만 학습 중 저장된 모델과 체크포인트는 MinIO에 남아 있을 수 있다.

다음 순서대로 확인한다.

```text
Docker Desktop
```

```text

```

상태인지 확인한다.

```text
Settings
→ Resources
→ WSL Integration
```

```text
Enable integration with my default WSL distro → ON
Ubuntu-22.04 → ON
```

필요하면:

```text
Apply & Restart
```

### 15-3. Ubuntu 22.04 실행

```powershell
wsl -d Ubuntu-22.04
```

### 15-4. DRfC 폴더로 이동

```bash
cd ~/deepracer-for-cloud
```

### 15-7. 현재 Docker Swarm 상태 확인

## 20. 대원칙

### 20-1. `dr-*` 명령어가 안 먹으면 먼저 환경 활성화

DeepRacer for Cloud의 `dr-summary`, `dr-start-training`, `dr-stop-training` 같은 명령어가 인식되지 않으면 가장 먼저 아래 명령을 실행한다.

```bash
cd ~/deepracer-for-cloud
source bin/activate.sh
```

그 후 다시 확인:

```bash
type dr-start-training
```

정상이라면:

```text
dr-start-training is a function
```

처럼 나온다.

이 상태에서는 다음 명령들이 정상적으로 동작한다.

```bash
dr-summary
dr-update-env
dr-upload-custom-files
dr-start-training
dr-stop-training
dr-logs-sagemaker
dr-logs-robomaker
```

즉, 앞으로의 대원칙은 다음과 같다.

```text
dr-* 명령어가 안 먹음
→ deepracer-for-cloud 폴더로 이동
→ source bin/activate.sh
→ 다시 실행
```

새 Ubuntu 터미널을 열었거나 WSL을 종료했다가 다시 실행한 경우에는 다시 활성화해야 할 수 있다.

### 20-2. 최종 대원칙

DeepRacer for Cloud 작업 중 문제가 생기면 우선 아래 순서로 확인한다.

```text
① Docker Desktop이 켜져 있는가?

② Ubuntu-22.04 WSL Integration이 켜져 있는가?

③ docker info가 정상적으로 실행되는가?

④ docker node ls가 Ready / Active / Leader인가?

⑤ dr-* 명령어가 안 먹으면 source bin/activate.sh 했는가?

⑥ docker service ls에서 이상한 0/1 서비스가 남아 있지 않은가?

⑦ MinIO에 기존 모델이 남아 있는가?

⑧ dr-summary의 트랙과 모델 prefix가 내가 원하는 설정인가?

⑨ 그 후 학습을 시작한다.
```

## 부록 C. 환경설정 도전 3 — GPU 사용하는 경우

> 이 부록은 노션에 첨부돼 있던 `DRfC_WSL2_GPU_Setup_Guide.md` 파일의 내용 전문이다.

### DRfC WSL2 GPU 로컬 설치 가이드

이 문서는 Windows 11 + WSL2 Ubuntu + NVIDIA GeForce RTX 4060 Laptop GPU 환경에서 DeepRacer-for-Cloud(DRfC)를 GPU 및 Local MinIO 모드로 설치하고, 기본 학습을 시작하기까지의 절차를 정리한 체크리스트다.

#### 전체 설치 흐름

1. 사전 환경 확인
2. 기본 패키지 설치
3. Docker Engine 설치
4. NVIDIA Container Toolkit 설치
5. Docker NVIDIA runtime 구성
6. Docker 권한 설정
7. CUDA 컨테이너 GPU 검증
8. Docker Swarm 사전 확인
9. DRfC 다운로드
10. DRfC GPU·Local 초기화
11. MinIO 프로필 확인
12. DRfC 환경 활성화
13. DRfC 인프라 확인
14. Custom files 검증
15. MinIO 업로드 및 첫 학습

> 중요: WSL Ubuntu 안에 `nvidia-driver-*`, `cuda-drivers`를 설치하지 않는다. NVIDIA driver는 Windows에만 설치하고, WSL에는 NVIDIA Container Toolkit만 설치한다.

---

#### C-0. 사전 환경 확인

WSL Ubuntu에서 다음을 실행한다.

```bash
cat /etc/os-release
uname -m
nvidia-smi
df -h /
free -h
```

확인 기준:

- 아키텍처가 `x86_64`인지 확인한다.
- `nvidia-smi`에 `NVIDIA GeForce RTX 4060 Laptop GPU`가 표시되는지 확인한다.
- 디스크 여유 공간은 최소 40GB, 가능하면 60GB 이상을 권장한다.
- 시스템 RAM과 GPU VRAM 합계는 가능하면 32GB 이상을 권장한다.

WSL에서 실행되는 `nvidia-smi`의 좌측 `NVIDIA-SMI` 버전은 Windows와 다를 수 있다. 실제 driver 판단에는 중앙의 `Driver Version`을 사용한다.

```bash
nvidia-smi \
  --query-gpu=driver_version \
  --format=csv,noheader
```

WSL용 실행 파일 경로도 확인한다.

```bash
command -v nvidia-smi
```

일반적인 정상 경로:

```text
/usr/lib/wsl/lib/nvidia-smi
```

---

#### C-1. 기본 패키지 설치

```bash
sudo apt-get update
```

#### C-3. NVIDIA Container Toolkit 설치

NVIDIA 저장소 검증키를 등록한다.

```bash
curl -fsSL \
  https://nvidia.github.io/libnvidia-container/gpgkey |
sudo gpg --dearmor --yes \
  -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
```

NVIDIA Container Toolkit 저장소를 등록한다.

```bash
curl -s -L \
  https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list |
sed \
  's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' |
sudo tee \
  /etc/apt/sources.list.d/nvidia-container-toolkit.list
```

패키지 목록을 갱신하고 Toolkit을 설치한다.

```bash
sudo apt-get update
sudo apt-get install -y nvidia-container-toolkit
```

구형 가이드의 `nvidia-docker2` 대신 현재는 `nvidia-container-toolkit`을 사용한다.

#### C-9. DRfC GPU·Local 모드 초기화

WSL에서는 `bin/prepare.sh`를 실행하지 않고 다음 초기화 명령을 사용한다.

```bash

  -a gpu \
  -c local
```

옵션 의미:

- `-a gpu`: GPU 학습 이미지 사용
- `-c local`: AWS S3 대신 로컬 MinIO 사용

초기화는 Docker 이미지 다운로드 때문에 오래 걸릴 수 있다. 다음 오류가 없어야 한다.

```text
Permission denied
Cannot connect to the Docker daemon
NVIDIA runtime not found
no space left on device
```

초기화 완료 후 생성 파일을 확인한다.

```bash
ls -l \
  system.env \
  run.env

ls -l custom_files
```

#### C-10. MinIO 프로필 확인

현재 DRfC의 `bin/init.sh -c local`은 AWS CLI의 `minio` 프로필을 먼저 확인한다.

- 이미 `minio` 프로필이 있으면 그대로 사용한다.
- 프로필이 없으면 임의 Access Key와 Secret Key를 생성한다.
- Region은 `us-east-1`로 설정한다.

따라서 사용자가 직접 `aws configure --profile minio`를 실행하지 않았더라도 다음 메시지와 함께 자동 생성될 수 있다.

```text
Creating default minio credentials in AWS profile 'minio'
```

프로필 목록을 확인한다.

```bash
aws configure list-profiles
```

`minio` 프로필 설정 상태를 확인한다.

```bash
aws configure list \
  --profile minio
```

Access Key와 Secret Key 원문을 터미널이나 로그에 출력하거나 공유하지 않는다.

##### `wsl --unregister` 이후에도 예전 프로필이 남을 수 있는가?

일반적인 경우에는 남지 않는다. `wsl --unregister <배포판명>`은 해당 배포판의 가상 디스크와 Linux 홈 디렉터리를 삭제하므로 `/home/<사용자>/.aws/credentials`도 함께 삭제된다.

이번 설치에서 `minio` 프로필이 존재하는 가장 유력한 이유는 현재 버전의 DRfC `init.sh`가 새 자격 증명을 자동 생성했기 때문이다.

예전 설정이 실제로 살아남을 수 있는 예외는 다음과 같다.

- 다른 이름의 WSL 배포판을 unregister하고 기존 배포판은 그대로 둔 경우
- `~/.aws`를 Windows 경로에 심볼릭 링크한 경우
- `AWS_SHARED_CREDENTIALS_FILE` 또는 `AWS_CONFIG_FILE`이 외부 경로를 가리키는 경우
- export/import 또는 백업 복원으로 배포판을 되살린 경우
- Windows의 `.aws` 폴더를 WSL 홈으로 복사한 경우

실제 저장 위치는 다음으로 확인할 수 있다.

```bash
printf 'HOME=%s\n' "$HOME"
printf 'AWS_SHARED_CREDENTIALS_FILE=%s\n' \
  "${AWS_SHARED_CREDENTIALS_FILE:-<unset>}"
printf 'AWS_CONFIG_FILE=%s\n' \
  "${AWS_CONFIG_FILE:-<unset>}"

ls -ld "$HOME/.aws"
readlink -f "$HOME/.aws"
```

일반적인 로컬 저장 위치는 다음과 같다.

```text
/home/<사용자>/.aws/credentials
/home/<사용자>/.aws/config
```

설정 파일의 값은 출력하지 않고 파일 생성 시간과 수정 시간만 확인할 수 있다.

```bash
stat \
  "$HOME/.aws/credentials" \
  "$HOME/.aws/config"
```

이 시간이 이번 `init.sh` 실행 시각과 비슷하면 새로 자동 생성된 것이다.
