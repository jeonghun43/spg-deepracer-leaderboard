# STEP 2 — 기술 계획: 오프라인 대회용 리더보드 & 비전 타이머

> 이 문서는 [spec.md](spec.md)(STEP1)의 요구사항을 만족시키기 위한 아키텍처·데이터 모델·기술 스택을 정한다. [001의 plan.md](../001-online-virtual-evaluation/plan.md)에서 정한 공용 플랫폼(웹 앱, DB, 계정 체계)을 그대로 재사용하는 것을 전제로 한다.

## 1. 확정된 전제 / 001과의 관계

- 001에서 이미 팀·시즌·계정·리더보드 웹 UI의 기반을 만들었으므로, 002는 **같은 웹 애플리케이션·DB에 "오프라인 모드"를 추가**하는 형태로 설계한다. 별도 사이트를 새로 만들지 않는다.
- 카메라·컴퓨팅 장비는 **아직 없음 → 신규 구축**이 전제다. 따라서 이 계획은 특정 제품 사양에 종속되지 않는 범용 아키텍처로 설계하고, 실제 장비가 정해지면 캘리브레이션 파라미터만 조정하면 되도록 한다.
- 참고 프로젝트([nalbam/deepracer-board](https://github.com/nalbam/deepracer-board), [ai-castle/deepracer-vision-timer](https://github.com/ai-castle/deepracer-vision-timer))는 UI/개념 참고용으로 삼되, 하드웨어를 그대로 이식하지는 않는다.

## 2. 전체 아키텍처

```
[새의 눈 시점 카메라] ── USB/IP
          │
          ▼
   [비전 계측 서비스] (Python + OpenCV)
     - 트랙/출발선 캘리브레이션
     - 출발선 통과 감지 → 타이머 시작/정지
     - 랩 카운트 (2바퀴)
     - 트랙 이탈 감지(자동) + 스태프 수동 보정
          │  주행 결과 이벤트 전송 (로컬 네트워크, HTTP API)
          ▼
   [웹 애플리케이션] (001과 동일 서버/코드베이스)
     - 스태프 콘솔: "지금 주행 중인 팀" 수동 선택, 연습/실제 모드 전환, 수동 기록 입력
     - 오프라인 리더보드: 실제주행 최고기록만 표시
          │
          ▼
   PostgreSQL (001과 공유) + 로컬 디스크 (경주 영상)
```

- **비전 계측 서비스**는 001의 웹 앱과 물리적으로 같은 서버에 둘 수도, 대회 현장에 별도로 두는 노트북/미니PC에 둘 수도 있다. 장비가 아직 없으므로 이 계획은 두 경우 모두 지원하도록 "비전 계측 서비스 → 웹 앱"을 **네트워크로 분리된 HTTP API 호출**로 설계한다. 실제 대회에서 같은 기기라면 로컬 호출이 되고, 분리된 기기라면 같은 로컬 네트워크(Wi-Fi/유선)로 통신하면 된다.
- **스태프 콘솔**은 001 관리자 페이지와 같은 인증 체계를 쓰는 별도 화면(현장 진행용 UI)이다.

## 3. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 비전 처리 | **Python + OpenCV** | 001과 언어 통일, 참고 프로젝트들도 유사한 스택 사용. 출발선 영역(ROI) 통과 감지 정도는 OpenCV만으로 충분 |
| 계측-웹 통신 | **HTTP API (내부망)** | 비전 서비스와 웹 앱의 물리적 배치가 아직 불확실하므로, 프로세스 경계를 명확히 분리해두면 나중에 같은 기기/다른 기기 어느 쪽이 되어도 코드 변경이 최소화됨 |
| 스태프 콘솔 UI | 001과 동일한 서버 렌더링(Jinja2) 화면에 페이지 추가 | 별도 프레임워크 도입 불필요 |
| 영상 저장 | 로컬 디스크, 001과 동일한 디렉터리 관례 확장 (`storage/videos/offline/{season}/{team}/`) | 확정된 전제(로컬 저장) 재사용 |

## 4. 데이터 모델 (001 확장)

| 엔티티 | 주요 속성 | 비고 |
|---|---|---|
| **OfflineEvent (본선 대회)** | id, season_id, 대회 일자, 상태 | 하나의 시즌에 온라인 예선 + 오프라인 본선이 함께 연결됨 |
| **Car (차량)** | id, 차량 식별 번호 (총 10대 고정 마스터 데이터) | |
| **CarAssignment (차량 배정)** | offline_event_id, team_id, car_id, 배정 방식(전담/공유), 추첨 순번 | 추첨 결과 기록 |
| **RaceRun (주행 기록)** | id, offline_event_id, team_id, car_id, 모드(연습/실제), 시작 시각, 종료 시각, 랩타임, 이탈 페널티 합계(초), 결과 소스(비전 자동/스태프 수동 입력), 영상 경로 | 연습 모드는 리더보드 집계에서 제외 |
| **TeamOfflineBestRecord (파생)** | team_id, offline_event_id, 최고기록을 낸 race_run_id | "실제" 모드 기록 중 최고값만 반영 |

관계: `Season 1—1 OfflineEvent`(대회당 1회 가정), `OfflineEvent 1—N CarAssignment`, `Team 1—N RaceRun`.

## 5. 핵심 흐름

### 5.1 대회 전 준비
1. 관리자가 001에서 확정된 본선 진출팀 명단을 불러온다.
2. 참가 규모에 따라 전담/공유 경계(N)를 정하고, 차량 배정과 연습·실제주행 순서를 **추첨** 기능(또는 수동 추첨 후 결과 입력)으로 확정해 `CarAssignment`에 저장한다.
3. 현장에서 카메라를 설치하고, 비전 계측 서비스에서 트랙 경계·출발선 위치를 화면상에서 지정(캘리브레이션)한다.

### 5.2 경주 진행
1. 스태프 콘솔에서 **지금 주행할 팀**과 **모드(연습/실제)** 를 수동으로 선택한다.
2. **연습주행**: 비전 서비스가 시간을 측정하더라도 `RaceRun.모드=연습`으로 저장되어 리더보드 집계에서 제외된다.
3. **실제주행**: 팀에게 배정된 10분 타이머가 시작된다(웹 앱이 관리). 그 안에서 차량이 출발선을 통과할 때마다 비전 서비스가 랩 계측을 시작/기록하고, 2바퀴째 통과 시 해당 시도의 기록을 확정한다. 10분 안에 여러 번 시도할 수 있으며, 매 시도 결과가 `RaceRun`으로 쌓이고 그중 최고기록만 `TeamOfflineBestRecord`로 반영된다.
4. 트랙 이탈은 비전 서비스가 트랙 경계 폴리곤 이탈을 자동 감지해 5초 페널티를 해당 시도 기록에 자동 가산하는 것을 1차 목표로 하되, 오탐 가능성을 고려해 스태프가 콘솔에서 페널티를 취소/추가로 수동 보정할 수 있게 한다.
5. 비전 인식이 실패(카메라 가림, 인식 오류 등)하면 스태프가 콘솔에서 랩타임을 **직접 입력**해 `RaceRun`을 생성한다 (결과 소스 = 수동).
6. 실제주행 결과가 저장될 때마다 오프라인 리더보드가 즉시 갱신된다.

### 5.3 리더보드
- 정렬 기준은 001과 동일하게 **실제주행 최고 랩타임(페널티 반영) 오름차순**.
- 각 팀의 최고기록에 연결된 영상을 리더보드에서 재생할 수 있다 (001과 동일 공개 정책).

## 6. 리스크·기술적 난이도

- **트랙 이탈 자동 감지**는 출발선 통과 감지보다 기술적으로 난이도가 높다 (차량 전체가 트랙 밖으로 나갔는지 판정하는 기준, 부분 이탈 처리 등). 초기 버전에서는 **자동 감지 + 스태프 수동 보정**을 함께 제공해 리스크를 낮추고, 실전 데이터를 쌓은 뒤 자동 감지 정확도를 개선하는 단계적 접근을 제안한다.
- **카메라·조명 환경**: 실내/실외, 조명 변화에 따라 인식 정확도가 달라질 수 있다. 장비 조달 후 실제 트랙 환경에서 캘리브레이션 테스트가 필요하다.
- **비전 서비스와 웹 앱의 물리적 배치**가 미정이므로, 네트워크 단절 시 계측 결과가 유실되지 않도록 비전 서비스 쪽에서도 결과를 임시 저장(재전송 가능하게) 하는 설계가 필요하다.

## 7. 열린 질문 (STEP3 전 확인 필요)

- [ ] 카메라 사양(해상도, 프레임레이트, 화각)과 설치 위치(트랙 크기 대비 높이)는 장비 조달 후 확정.
- [ ] 트랙 이탈 자동 감지의 판정 기준(차량 전체 이탈 vs 일부 바퀴 이탈 등)을 대회 규정으로 명문화할 필요.
- [ ] 비전 계측 서비스와 웹 앱을 같은 기기에 둘지, 분리할지 (현장 네트워크 환경에 따라 결정).
- [ ] 공유 차량팀의 10분 실제주행 시간에 차량 교대 시간이 포함되는지 (spec.md 열린 질문과 연동 — 포함된다면 비전 서비스가 "교대 중"을 별도로 구분해야 하는지).
