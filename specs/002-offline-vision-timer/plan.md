# STEP 2 — 기술 계획: 오프라인 대회용 리더보드 & 비전 타이머

> 이 문서는 [spec.md](spec.md)(STEP1)의 요구사항을 만족시키기 위한 아키텍처·데이터 모델·기술 스택을 정한다. [001의 plan.md](../001-online-virtual-evaluation/plan.md)에서 정한 공용 플랫폼(웹 앱, DB, 계정 체계)을 그대로 재사용하는 것을 전제로 한다.

## 1. 확정된 전제 / 001과의 관계

- 001에서 이미 팀·시즌·계정·리더보드 웹 UI의 기반을 만들었으므로, 002는 **같은 웹 애플리케이션·DB에 "오프라인 모드"를 추가**하는 형태로 설계한다. 별도 사이트를 새로 만들지 않는다.
- 참고 프로젝트([nalbam/deepracer-board](https://github.com/nalbam/deepracer-board), [ai-castle/deepracer-vision-timer](https://github.com/ai-castle/deepracer-vision-timer))는 UI/개념 참고용으로 삼되, 하드웨어를 그대로 이식하지는 않는다.

### 1.1 촬영 장비 결정 — 공기계 스마트폰 2대

전용 카메라를 구매하지 않고 **보유 중인 공기계 스마트폰 2대**를 쓴다.

**왜 폰인가.**
- 추가 비용이 0원이다. 검토했던 대안은 저가 UVC 웹캠(2~4만원), Raspberry Pi 5 + Camera Module 3 Wide(약 22~25만원), 글로벌 셔터 USB 모듈(4~9만원)이었다.
- **무선이라 거치 위치가 자유롭다.** USB 웹캠은 USB 2.0 패시브 케이블 한계(5m)가 높은 곳 설치의 실질적 걸림돌이 된다.
- **로컬 녹화가 공짜로 따라온다.** 이것이 리플레이 영상 요구사항([spec.md](spec.md) §6)과 "네트워크 단절 시 계측 결과 유실" 리스크(§6 아래)를 동시에 해결한다.
- 초광각 렌즈(수평 약 100~105°)를 쓸 수 있어 전체 트랙 카메라의 필요 설치 높이가 크게 낮아진다.

**검토 후 배제한 것: Tapo류 IP캠/CCTV.** 가격(3~5만원)과 PoE 설치 편의는 가장 좋지만 계측에 쓸 수 없다. fps가 15~20으로 낮고 VBR로 흔들려 프레임 기반 시간 계산조차 신뢰할 수 없고, H.264 인코딩 + RTSP 버퍼링 지연이 불규칙하다. 게다가 펌웨어 업데이트로 RTSP가 막힌 사례가 제조사 커뮤니티에 보고돼 있어 대회 당일 리스크가 크다. 감시용으로 최적화된 장비라 목적이 다르다.

### 1.2 거치 조건과 그 결과

**천장·트러스 설치가 불가능하다** (삼각대·스탠드 거치만 가능). 이 제약이 카메라 2대 분리 구성의 직접적인 원인이다.

| | 계측 카메라 (폰 A) | 전체 카메라 (폰 B) |
|---|---|---|
| 위치 | 출발선 옆 2~3m, 높이 1.5m↑ | 트랙 코너, 최대한 높게 (2~3m) |
| 겨누는 방향 | **주행 방향과 직교** | 트랙 전체가 대각선으로 담기게 |
| 렌즈 | 기본 렌즈 | **초광각** |
| fps | 30~60 (높을수록 좋음) | 10이면 충분 |

**왜 직교로 겨누는가.** 차가 화면을 가로질러 지나가면 프레임당 이동량이 커서 통과 시점이 선명하게 잡힌다. 차량이 카메라를 향해 다가오는 각도(주행 방향과 평행)는 프레임당 위치 변화가 작아 통과 판정이 흐려진다 — 최악의 배치다.

**왜 높이에 집착하는가.** 전체 카메라의 바닥 판정 해상도는 **카메라 높이에 선형으로 비례**한다. 8×5m 트랙, 초광각 1080p, 높이 2m 조건에서 계산하면 카메라 가까운 쪽은 3mm/픽셀인데 먼 쪽 코너는 **4.2cm/픽셀**이다. 이탈 판정에 ±5cm가 필요하다면 먼 쪽 오차 예산이 1픽셀뿐이라는 뜻이고, 탐지 노이즈 1픽셀이 곧 오판이 된다. 높이를 3m로 올리면 2.8cm/픽셀로 개선된다. **이것이 이탈 횟수를 자동 집계로 확정하지 않고 임원진 조정을 정상 절차로 두는 근거다.**

## 2. 전체 아키텍처

```
[폰 A — 출발선 전용]              [폰 B — 트랙 전체]
  30~60fps, 기본 렌즈              10fps, 초광각, 로컬 녹화
        │                                  │
        └──────── 로컬 네트워크 ────────────┘
                       │
                       ▼
        [비전 계측 서비스] (현장 노트북, Python + OpenCV)
          ├─ 게이트 파이프라인 (폰 A)
          │    - 출발선 양 끝점 캘리브레이션
          │    - 접지점 기준 통과 판정 + 서브프레임 보간
          │    - 랩 상태머신 → 1바퀴/2바퀴/총 기록
          └─ 전체 트랙 파이프라인 (폰 B)
               - 트랙 경계 밴드 캘리브레이션
               - 차량 추적, 체크포인트 통과 확인
               - 이탈 횟수 자동 집계 (제안값)
                       │  HTTP API + 재전송 큐
                       ▼
        [웹 애플리케이션] (001과 동일 서버/코드베이스)
          - 스태프 콘솔: 주행 팀 선택, 연습/실제 전환,
                        이탈 횟수 조정, 수동 기록 입력
          - 오프라인 리더보드: 실제주행 최고기록만 표시
                       │
                       ▼
        PostgreSQL (001과 공유) + 로컬 디스크 (경주 영상)
```

- **두 파이프라인은 프로세스를 분리한다.** 전체 트랙 탐지가 무거워 프레임을 떨어뜨려도 게이트 파이프라인의 fps에 영향을 주지 않아야 한다. 한 프로세스에 합치면 그 프레임 드랍이 그대로 랩타임 오차가 된다.
- **비전 계측 서비스**는 현장 노트북에서 돌리고, 웹 앱과는 **HTTP API로 통신**한다. 웹 앱은 클라우드(Lightsail)에 있으므로 이 경계는 실제로 네트워크를 건넌다. 따라서 전송 실패 시 결과를 잃지 않도록 **로컬 재전송 큐**가 필수다(§6 참조).
- **스태프 콘솔**은 001 관리자 페이지와 같은 인증 체계를 쓰는 별도 화면(현장 진행용 UI)이다.

## 3. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 비전 처리 | **Python + OpenCV** | 001과 언어 통일, 참고 프로젝트들도 유사한 스택 사용. 출발선 영역(ROI) 통과 감지 정도는 OpenCV만으로 충분 |
| 폰 → 노트북 스트림 | **Android + IP Webcam류 앱 (MJPEG/RTSP)**, 가능하면 **USB 테더링** | `cv2.VideoCapture(url)`로 바로 읽힌다. USB 테더링이 Wi-Fi보다 지터가 작고 충전이 동시에 되므로 우선한다. 현장 Wi-Fi는 관중 단말로 붐빈다 |
| 차량 탐지 | **트랙 마스크 + 배경 차분(MOG2) + 차량 상단 고대비 색 마커(HSV)** | 카메라가 고정이라 배경 차분이 잘 듣고, 색 마커로 확정하면 사람·그림자 오탐이 걸러진다. **학습 데이터가 필요 없어 대회 당일 현장 세팅이 가능**한 것이 결정적이다. [spec.md](spec.md) §6의 "동시 주행 없음"(트랙에 한 대만) 전제가 이 단순한 방식을 성립시킨다 |
| 차량 탐지 (2차) | YOLO11n 커스텀 학습 | 훨씬 견고하지만 라벨링 수백 장이 필요하다. 1차 방식으로 실전 데이터를 쌓은 뒤 넘어간다. COCO의 `car` 클래스는 1/18 스케일 DeepRacer에 잘 맞지 않아 사전학습 그대로는 못 쓴다 |
| 계측-웹 통신 | **HTTP API + 로컬 재전송 큐** | 웹 앱이 클라우드에 있어 이 경계는 실제로 네트워크를 건넌다. 큐 없이는 현장 회선이 끊기는 순간 기록이 사라진다 |
| 스태프 콘솔 UI | 001과 동일한 서버 렌더링(Jinja2) 화면에 페이지 추가 | 별도 프레임워크 도입 불필요 |
| 영상 저장 | 폰 B 로컬 녹화 → 세션 후 회수, 001과 동일한 디렉터리 관례 확장 (`storage/videos/offline/{season}/{team}/`) | 스트림을 노트북에서 다시 인코딩하지 않아도 되고, 네트워크와 무관하게 원본이 남는다 |

## 3.5 계측 정확도 설계

랩타임 정확도를 좌우하는 것은 카메라 성능이 아니라 **시간을 어떻게 계산하는가**다. 세 가지가 핵심이다.

**① 시각은 프레임 인덱스로 계산한다 — 도착 시각(wall clock)을 쓰지 않는다.**
랩타임은 `통과 시각 2 − 통과 시각 1`, 즉 차이값이다. 그래서 카메라~노트북 전송 지연이 얼마든 **일정하다면 상쇄된다.** 문제는 일정하지 않다는 것이다. MJPEG/RTSP 스트림은 버퍼링과 프레임 드랍이 흔해서(15fps가 6fps로 떨어지거나 수 초 지연이 쌓인 사례가 다수 보고돼 있다), **프레임을 받은 시각으로 타임스탬프를 찍으면 그 지터가 그대로 오차가 된다.** 따라서 `랩타임 = (통과 프레임 인덱스 차) ÷ fps`로 계산하고, 드랍을 감지하면 해당 시도를 무효 처리하거나 경고한다.

**② 판정 기준점은 차량의 접지점이다 — 차체 중심이 아니다.**
차 높이가 약 15cm인데, 낮은 각도에서 보면 그 높이만큼 바닥 위치가 어긋나 보인다(시차). 카메라 높이 1.2m·거리 3m 조건에서 계산하면 **약 25cm 오차 → 3m/s에서 83ms**로, 프레임 간격 오차(30fps에서 33ms)보다 크다. 바운딩 박스의 **아래쪽 변**(타이어 접지면)을 기준으로 쓰면 접지점이 바닥 평면 위에 있으므로 이 시차가 거의 사라진다. 구현상 한 줄 차이인데 정확도 차이가 크다.

**③ 게이트는 출발선의 실제 투영 선분이다 — 화면의 수직선이 아니다.**
바닥의 직선은 어떤 각도에서 촬영해도 이미지에서 직선으로 투영된다. 따라서 화면에서 **출발선 양 끝점 2개를 찍어** 그 선분을 게이트로 삼고, 접지점이 선분의 어느 쪽에 있는지(부호 판정)로 통과를 판정한다. 이러면 카메라 각도·원근 왜곡과 무관하게 기하학적으로 정확하고, 차량이 트랙 폭 어디로 통과해도 동일하게 맞는다. 참고 프로젝트가 요구하는 입력값도 같은 "출발선 양 끝점 좌표"다.

**결과 정확도.** 위 세 가지에 **서브프레임 보간**(통과 직전·직후 두 프레임의 접지점 위치로 선을 넘은 시각을 선형 보간)을 더하면 30fps에서도 실효 오차 **±10ms 수준**이다. 사람의 수동 계측(±200~300ms)보다 20배 이상 정확하다.

## 4. 데이터 모델 (001 확장)

| 엔티티 | 주요 속성 | 비고 |
|---|---|---|
| **OfflineEvent (본선 대회)** | id, season_id, 대회 일자, 상태 | 하나의 시즌에 온라인 예선 + 오프라인 본선이 함께 연결됨 |
| **Car (차량)** | id, 차량 식별 번호 (총 10대 고정 마스터 데이터) | |
| **CarAssignment (차량 배정)** | offline_event_id, team_id, car_id, 배정 방식(전담/공유), 추첨 순번 | 추첨 결과 기록 |
| **RaceRun (주행 기록)** | id, offline_event_id, team_id, car_id, 모드(연습/실제), 시작 시각, 종료 시각, `lap1_ms`, `lap2_ms`, `total_ms`, `offtrack_count_auto`, `offtrack_count_final`, `final_ms`, 결과 소스(비전 자동/스태프 수동 입력), 영상 경로 | 연습 모드는 리더보드 집계에서 제외 |
| **TeamOfflineBestRecord (파생)** | team_id, offline_event_id, 최고기록을 낸 race_run_id | "실제" 모드 기록 중 최고값만 반영 |

관계: `Season 1—1 OfflineEvent`(대회당 1회 가정), `OfflineEvent 1—N CarAssignment`, `Team 1—N RaceRun`.

**이탈 횟수를 두 컬럼으로 나눈 이유.** `offtrack_count_auto`(비전 자동 집계)와 `offtrack_count_final`(임원진 확정)을 따로 저장한다. 하나로 덮어쓰면 임원진이 조정한 순간 자동 집계값이 사라져서 **나중에 이의가 제기됐을 때 근거를 제시할 수 없고, 자동 감지 정확도를 개선할 데이터도 남지 않는다.** 순위 계산에는 `final`만 쓴다.

**랩타임을 정수 밀리초로 저장한다.** 부동소수점은 합산·비교에서 미세한 오차가 생겨 동순위 판정이 흔들릴 수 있다.

**최종 기록 계산**: `final_ms = total_ms + (offtrack_count_final × 5000)`. 파생값이지만 컬럼으로 저장한다 — 리더보드 정렬이 이 값 기준이므로 인덱스를 걸어야 하고, 페널티 규정이 나중에 바뀌어도 과거 대회 기록이 소급 변경되지 않아야 한다.

## 5. 핵심 흐름

### 5.1 대회 전 준비
1. 관리자가 001에서 확정된 본선 진출팀 명단을 불러온다.
2. 참가 규모에 따라 전담/공유 경계(N)를 정하고, 차량 배정과 연습·실제주행 순서를 **추첨** 기능(또는 수동 추첨 후 결과 입력)으로 확정해 `CarAssignment`에 저장한다.
3. 현장에서 폰 2대를 거치하고 각각 캘리브레이션한다.
   - 폰 A: 화면에서 **출발선 양 끝점 2개**를 클릭한다. 바닥의 출발선에 고대비 테이프를 붙여두면 클릭 지점이 명확해진다.
   - 폰 B: 트랙 경계를 **밴드(안쪽선·바깥선)로** 지정하고, 트랙 반대편에 **체크포인트 영역** 1~2개를 지정한다.
   - 두 폰 모두 **노출·초점·화이트밸런스를 수동 고정**한다. 주행 중 자동 노출이 흔들리면 배경 차분이 무너진다. 실내 조명에서는 안티플리커(50/60Hz)도 설정한다.
4. **거치 밀림 감지 장치를 세팅한다.** 게이트 좌표는 픽셀 기준이라 삼각대가 발에 차여 조금만 움직여도 판정선이 트랙 밖으로 어긋난다. 그런데 **화면은 정상으로 보여서 알아채기 어렵고, 그 사이 기록 전체가 오염된다.** 대응: 트랙 바닥에 고정 마커 2~3개를 붙여 항상 프레임에 보이게 하고, 시스템이 매 세션 시작 시 마커 위치 변화를 검사해 어긋났으면 **경고를 띄우고 계측을 막는다.** 삼각대 다리 위치도 바닥에 테이프로 마킹해 원복을 쉽게 한다.

### 5.2 경주 진행
1. 스태프 콘솔에서 **지금 주행할 팀**과 **모드(연습/실제)** 를 수동으로 선택한다.
2. **연습주행**: 비전 서비스가 시간을 측정하더라도 `RaceRun.모드=연습`으로 저장되어 리더보드 집계에서 제외된다.
3. **실제주행**: 팀에게 배정된 10분 타이머가 시작된다(웹 앱이 관리). 그 안에서 아래 랩 상태머신이 시도 단위로 돌아가고, 매 시도 결과가 `RaceRun`으로 쌓이며 그중 최고기록만 `TeamOfflineBestRecord`로 반영된다.
4. 비전 인식이 실패(카메라 가림, 인식 오류 등)하면 스태프가 콘솔에서 랩타임을 **직접 입력**해 `RaceRun`을 생성한다 (결과 소스 = 수동).
5. 실제주행 결과가 저장될 때마다 오프라인 리더보드가 즉시 갱신된다.

### 5.2.1 랩 상태머신 (폰 A)

```
IDLE
 └─(게이트 통과: 정방향)──▶ LAP1_RUNNING   시작 프레임 기록
                              │
       ┌──────────────────────┘
       │ (게이트 통과: 정방향 + 체크포인트 통과 완료 + 최소 랩타임 경과)
       ▼
    LAP2_RUNNING              lap1_ms 확정
       │
       │ (동일 조건)
       ▼
    FINISHED                  lap2_ms 확정, total_ms 확정 → 자동 저장
```

이탈이 발생하면 어느 상태에서든 `OFFTRACK_HOLD`로 진입하고, 차량이 트랙으로 복귀하면 원래 상태로 돌아온다. **이 구간의 추적 결과는 랩 판정에 반영하지 않는다** — 스태프가 차량을 집어 트랙에 올려놓는 동안 사람의 손·팔이 차량으로 오인되기 때문이다.

### 5.2.2 오감지 방지 장치 4개

전부 실제로 터지는 케이스다. 이것 없이 만들면 대회 당일 기록이 오염된다.

| 장치 | 막는 것 | 방법 |
|---|---|---|
| **통과 방향 판정** | 스태프가 차량을 손으로 들어 출발선 뒤로 옮길 때 랩이 올라가는 것 | 접지점의 게이트 부호가 정방향으로 바뀔 때만 유효 처리 |
| **체크포인트 필수 통과** | 출발선 근처에서 스핀하며 선을 다시 넘어 한 바퀴로 오인되는 것 | 트랙 반대편 체크포인트 영역을 지난 뒤의 게이트 통과만 랩으로 인정 (폰 B가 판정) |
| **최소 랩타임 디바운스** | 차량이 선 위에 걸쳐 멈춰 통과 판정이 떨리며 랩이 폭증하는 것 | 유효 통과 사이 최소 간격(예: 3초) 하한 |
| **이탈 판정 히스테리시스** | 경계선에 걸친 상태에서 in/out이 프레임마다 바뀌며 이탈 횟수가 수십 번으로 뛰는 것 | 경계를 **밴드**로 두고 바깥선을 넘으면 "이탈 시작", 안쪽선으로 복귀해야 "이탈 종료" → 1회 집계. 추가로 N프레임 연속 조건 |

### 5.2.3 이탈 횟수 처리 (폰 B)

1. 비전 서비스가 위 히스테리시스 규칙으로 이탈 횟수를 세어 `offtrack_count_auto`에 기록한다.
2. 스태프 콘솔이 이 값을 **제안값으로 표시**하고, 임원진이 조정해 `offtrack_count_final`을 확정한다. 자동값은 지우지 않고 남긴다.
3. `final_ms = total_ms + (offtrack_count_final × 5000)`으로 최종 기록이 계산되고 리더보드에 반영된다.

**자동 확정이 아니라 임원진 확정으로 둔 이유**는 §1.2에서 계산한 대로 카메라에서 먼 쪽 코너의 판정 해상도가 1픽셀 수준까지 떨어지기 때문이다. 자동값을 그대로 순위에 반영하면 참가팀 이의를 감당할 수 없다.

> **미확정**: 이탈의 판정 기준(바퀴 하나 vs 접지 중심)은 대회 규정 결정 사항으로 아직 확정되지 않았다. [spec.md](spec.md) §10 참조. 구현 시에는 판정 기준을 **설정값으로 빼두어** 규정이 정해지면 코드 수정 없이 바꿀 수 있게 한다.

### 5.3 리더보드
- 정렬 기준은 001과 동일하게 **실제주행 `final_ms`(이탈 페널티 반영) 오름차순**.
- 각 팀 행에 총 기록과 함께 **1바퀴·2바퀴 구간기록, 이탈 횟수**를 보여준다. 페널티가 어디서 왔는지 보이지 않으면 참가팀이 순위를 납득하기 어렵다.
- 각 팀의 최고기록에 연결된 영상을 리더보드에서 재생할 수 있다 (001과 동일 공개 정책).

## 6. 리스크·기술적 난이도

난이도 순으로, 높은 것부터:

- **트랙 이탈 자동 감지 (가장 높음).** §1.2의 계산대로 천장 설치가 불가능해 먼 쪽 코너의 판정 해상도가 1픽셀 수준까지 떨어진다. **자동 집계 + 임원진 확정**을 정상 절차로 두어 이 리스크를 흡수하고, `offtrack_count_auto`와 `final`을 함께 저장해 실전 데이터를 쌓은 뒤 정확도를 개선한다. 높이를 1m 더 확보하는 것이 어떤 알고리즘 튜닝보다 효과가 크다.
- **거치대 밀림 (조용히 터지는 리스크).** 삼각대가 밀려도 화면은 정상으로 보여서 알아채기 어렵고, 그 사이 기록이 전부 오염된다. §5.1의 바닥 마커 기반 자동 검사가 유일한 실용적 대응이다. **이건 v1에 반드시 들어가야 한다.**
- **가림(occlusion).** 낮은 측면 시야는 카메라와 출발선 사이에 사람 다리·스태프·대기 참가자가 들어오면 그대로 막힌다. 천장 시야에는 없는, 이 구성 고유의 문제다. 대응은 소프트웨어가 아니라 현장 운영이다 — 사람이 서는 쪽 **반대편**에 거치하고 시선 경로를 콘·라인테이프로 막는다.
- **작은 객체 탐지.** 초광각 1080p 기준으로 먼 쪽 코너의 차량이 약 30픽셀까지 작아진다. 폰 B는 1080p보다 4K로 촬영해 여유를 두는 것을 검토한다.
- **폰 발열·프레임 드랍.** 장시간 스트리밍 + 충전을 동시에 하면 스로틀링으로 fps가 떨어진다. 케이스를 벗기고 화면 밝기를 최소로 하며, 세션 사이에 식힌다. 오래 방치된 공기계는 **배터리 팽창** 여부를 먼저 확인한다 — 종일 충전 상태로 두는 것은 위험하다.
- **폰 방해 요소.** 알림·전화·화면 꺼짐으로 스트림이 끊긴다. SIM을 빼고 화면 항상 켜짐으로 설정한다.
- **조명 환경.** 실내 형광등·LED 아래에서 셔터를 고정하면 플리커 밴딩이 생긴다. 안티플리커(50/60Hz) 설정이 필요하다.
- **네트워크 단절.** 웹 앱이 클라우드에 있으므로 현장 회선이 끊기면 계측 결과가 유실될 수 있다. 비전 서비스 쪽 **로컬 재전송 큐**로 대응하고, 폰 B의 로컬 녹화가 최후의 백업이 된다.

## 7. 열린 질문 (STEP3 전 확인 필요)

- [ ] **트랙 실측 크기(긴 변 × 짧은 변)와 확보 가능한 거치 높이.** 이 두 값이 있어야 폰 B의 필요 화각과 거치 위치를 확정할 수 있다. 계산식: `필요 높이 = (긴 변 ÷ 2) ÷ tan(수평화각 ÷ 2)` — 정면 상단 기준이며, 코너에서 대각선으로 겨누면 더 낮은 높이로도 커버된다.
- [ ] **보유 공기계의 OS(안드로이드/아이폰)와 모델.** 안드로이드면 IP Webcam류로 노출 고정·해상도·fps 제어까지 되어 실시간 스트림이 쉽다. 아이폰은 Windows 쪽 연결 옵션이 제한적이라 **"로컬 녹화 후 처리"** 방식이 사실상 유일한 안정 경로이며, 그 경우 §3.5의 프레임 인덱스 계산이 오히려 더 정확해진다(고정 fps, 드랍 없음).
- [ ] **트랙 이탈 판정 기준의 규정 명문화** — [spec.md](spec.md) §10과 연동. 확정 전까지는 설정값으로 분리해 구현한다.
- [ ] 비전 계측 서비스를 돌릴 현장 노트북 사양 (배경 차분 방식은 CPU로 충분하나, YOLO로 넘어갈 때 GPU 필요 여부 판단).
- [ ] 공유 차량팀의 10분 실제주행 시간에 차량 교대 시간이 포함되는지 (spec.md 열린 질문과 연동 — 포함된다면 비전 서비스가 "교대 중"을 별도로 구분해야 하는지).
