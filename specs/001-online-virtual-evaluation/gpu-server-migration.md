# GPU 서버 이전 절차

> ## ⚠️ 이 문서는 대체되었다 (2026-08-01)
>
> **실제 이전은 GPU 서버가 아니라 CPU 인스턴스(AWS EC2 m7i.xlarge 스팟)로 이뤄졌다.**
> 실행 절차는 **[worker-server-setup.md](../../docs/worker-server-setup.md)** 를 본다.
>
> 이 문서의 전제("GPU 서버로 옮기면 평가가 빨라진다")는 검토 결과 성립하지 않았다.
> 평가는 학습과 달리 Gazebo 물리 연산·컨테이너 기동이 대부분이고 GPU가 관여하는 부분은
> 카메라 렌더링뿐이다. DRFC도 이미 CPU 전용 이미지(`DR_SIMAPP_VERSION=6.0.4-cpu`)로 돌고 있었다.
> GPU 인스턴스는 값이 2배인데 그만큼 빨라진다는 근거가 없어 CPU 인스턴스를 선택했고,
> 실측 결과 노트북 약 14분 → EC2 약 8분으로 충분히 줄었다.
>
> 아래 내용은 **당시의 검토 기록**으로 남긴다. 체크리스트 중 GPU 드라이버·NVIDIA Container
> Toolkit 항목은 현재 구성에 해당하지 않는다.

> 현재(2026-07) 개발/운영 환경: **Windows 노트북(GPU 없음) + WSL2 Ubuntu** 안에서 DRFC의 `dr-start-evaluation`을 실행하는 방식. 나중에 GPU가 있는 별도 컴퓨터로 옮기고 싶을 때를 대비한 절차 문서.

## 결론: 가능하다

이관이 가능한 이유는 이 프로젝트를 애초에 그렇게 설계했기 때문이다.

- DRFC 자체가 Docker Compose 기반이라 "어떤 하드웨어에서 도는가"와 무관하게 동일한 명령(`dr-start-evaluation`)으로 동작한다. WSL2 Ubuntu든 네이티브 Linux든 Docker가 돌아가는 환경이면 실행된다.
- 우리 애플리케이션(웹/워커/DB)도 [plan.md](plan.md)에서 Docker Compose + 로컬 디스크 저장 + PostgreSQL로 설계했기 때문에, "설정 파일 + 데이터(DB, storage 디렉터리)"만 옮기면 코드 변경 없이 새 서버에서 그대로 재기동할 수 있다.
- DRFC 관련 환경변수(`DR_LOCAL_S3_*` 등)는 우리 앱이 별도로 관리하지 않고 **DRFC 자체의 `run.env`/`system.env`를 그대로 사용**하도록 결정했으므로(plan.md §1), 새 서버에도 DRFC를 표준 방식대로 새로 설치하기만 하면 이 부분은 자동으로 맞춰진다.

즉, "우리 서비스 코드"는 그대로 두고 "실행 위치"만 바꾸는 인프라 이관 작업이다.

## 이전 절차

### 1. 신규 서버 준비
- [ ] GPU 드라이버 설치 (NVIDIA 드라이버)
- [ ] Docker, Docker Compose 설치
- [ ] NVIDIA Container Toolkit 설치 (컨테이너에서 GPU를 쓰려면 필수)
- [ ] 가능하면 **네이티브 Linux**를 권장한다. WSL2에서도 GPU 패스스루가 되긴 하지만(WSL2 CUDA 지원), 추가 설정이 필요하고 네이티브보다 손이 더 간다 — 어차피 서버를 옮기는 김이라면 처음부터 네이티브 Linux로 두는 편이 이후 운영이 단순하다.

### 2. DRFC를 새 서버에 새로 설치
- [ ] DRFC 리포지토리를 새 서버에 클론
- [ ] `run.env` / `system.env`를 GPU를 사용하도록 설정 (기존 노트북 환경의 CPU 전용 설정과 달라지는 부분을 DRFC 공식 문서에서 확인)
- [ ] `dr-start-evaluation`을 단독으로 한 번 실행해, 새 서버에서 정상 동작하는지부터 검증한다 (우리 서비스 연결 전에 DRFC 자체가 되는지 먼저 확인)

### 3. 우리 애플리케이션 이관
- [ ] 코드: git 리포지토리를 새 서버에 클론 (코드 변경 없음)
- [ ] DB 이관: 기존 서버에서 `pg_dump`로 백업 → 새 서버로 전송 → `pg_restore`로 복원
- [ ] 파일 이관: `storage/models/`, `storage/videos/` 디렉터리를 통째로 복사 (rsync, 외장 디스크 등— 용량에 따라 방식 선택)
- [ ] `docker-compose.yml` 및 우리 앱 자체 설정(DATABASE_URL, 세션 시크릿 등)을 새 서버 환경에 맞게 설정

### 4. 서비스 기동 및 검증
- [ ] `docker-compose up`으로 웹/워커/DB 기동
- [ ] tasks.md의 **Phase 8 검증 항목**(T043~T047 상당)을 새 서버에서 다시 실행해 정상 동작 확인
- [ ] 실제 참가자 트래픽을 새 서버로 돌리기 전, 소규모로 제출 1~2건을 직접 넣어보고 결과가 정상적으로 나오는지 확인

### 5. 평가 소요 시간 재측정
- [ ] GPU 서버에서 `dr-start-evaluation` 평가 1건당 소요 시간을 실측한다
- [ ] plan.md §1의 "평가 1건당 약 10분" 수치를 새 값으로 갱신
- [ ] 참가자에게 보여주는 "예상 대기 시간" 계산 로직(tasks.md T026 상당)에도 새 수치를 반영

### 6. 전환 및 정리
- [ ] 실제 서비스 트래픽을 새 서버로 전환 (도메인/링크가 있다면 그쪽을 새 서버로 연결)
- [ ] 기존 노트북 서버는 이관이 안정적으로 확인될 때까지 **바로 폐기하지 말고 며칠간 그대로 유지** — 문제가 생기면 되돌릴 수 있는 롤백 경로로 남겨둔다
- [ ] 안정성이 확인되면 기존 노트북은 원래 용도로 반납/재사용

## 주의할 점

- DB와 storage 디렉터리는 **반드시 함께** 이관해야 한다. 둘 중 하나만 옮기면 리더보드에 표시되는 팀·기록과 실제 영상 파일이 어긋난다.
- 이관 도중(백업 시점 이후) 기존 서버에서 새로 들어온 제출이 있다면 누락되므로, 실제 전환 시점에는 잠깐 제출을 막아두고(공지 후) 마지막 스냅샷을 뜬 뒤 전환하는 것을 권장한다.
- GPU 서버에서는 평가 속도가 빨라지므로, 대기열이 밀리는 상황 자체가 줄어들 가능성이 높다 — 다만 실측 전까지는 가정하지 말고 반드시 재측정 후 안내 문구를 갱신할 것.
