# STEP 2 — 기술 계획: 가상 트랙 기반 자동 평가 플랫폼

> 이 문서는 [spec.md](spec.md)(STEP1)의 요구사항을 만족시키기 위한 아키텍처·데이터 모델·기술 스택을 정한다. 세부 작업 분해는 STEP3(tasks.md), 실제 코드는 STEP4에서 다룬다.

## 1. 확정된 전제

- 백엔드 언어는 **Python**으로 확정 (DRFC, 평가 파이프라인, 향후 002의 비전 처리까지 모두 Python 생태계로 통일).
- 서버는 정식 사양이 아직 없어, 우선 **GPU 없는 Windows 노트북 + WSL2 Ubuntu** 환경에서 DRFC `dr-start-evaluation`을 실행하는 방식으로 개발·운영한다 (실제 동작 확인됨). 실측 결과 **평가 1건당 약 10분**이 걸린다 — 이 수치를 대기열 설계와 참가자 안내 문구의 기준값으로 삼는다. 추후 GPU 서버로 이전하는 절차는 [gpu-server-migration.md](gpu-server-migration.md)에 별도로 정리한다.
- 평가 영상·모델 파일은 **로컬 서버 디스크**에 그대로 저장한다. 외부 스토리지 연동은 하지 않는다.
- 예상 규모: 시즌당 약 **10팀**, 팀당 하루 제출 수는 **3~5회** 수준으로 예상 (하루 한도 5회와 거의 맞물림). 최악의 경우(10팀 × 5회 = 하루 50건)에도 평가 1건당 10분이면 총 약 500분(8시간 20분)으로, 순차 처리로도 하루 안에 소화 가능한 규모다 — 별도의 대규모 큐 인프라 없이 DB 테이블 기반 큐로 충분하다는 판단의 근거.

## 2. 전체 아키텍처

```
[참가자/관리자/관전자 브라우저] (LAN 안이든 밖이든 무관)
          │  HTTPS
          ▼
   [Cloudflare Tunnel (cloudflared)]  ── 공유기 포트포워딩/고정 공인 IP 불필요
          │  HTTP (로컬 구간)
          ▼
   [웹 애플리케이션] ── PostgreSQL (팀·시즌·제출·기록 메타데이터)
          │                     
          │ 제출 등록          
          ▼
   [평가 대기열 (DB 테이블 기반)]
          │
          ▼
   [평가 워커 프로세스] ── dr-start-evaluation(DRFC, Docker) 실행
          │
          ▼
   [로컬 디스크] ── 모델 파일 원본 / 평가 결과 영상 / 로그
```

- **웹 애플리케이션**: 참가자 제출 페이지, 공개 리더보드, 관리자 페이지를 모두 제공하는 단일 서비스.
- **평가 대기열**: 별도 메시지 브로커(Redis/RabbitMQ 등) 없이 **DB 테이블을 큐로 사용**한다. 어차피 평가는 서버 한 대에서 순차 실행되는 것을 전제하므로(동시에 여러 dr-start-evaluation을 돌리는 것은 리소스상 무리), 큐 인프라를 추가하는 것보다 "대기중 → 실행중 → 완료/실패" 상태를 가진 테이블 + 워커의 폴링 방식이 훨씬 단순하고 운영 부담이 적다.
- **평가 워커**: 큐에서 다음 제출 건을 꺼내 DRFC 평가를 실행하고, 끝나면 결과를 파싱해 DB에 반영하는 별도 프로세스(웹 서버와 분리). 웹 요청 처리와 무거운 평가 작업을 분리해 웹 페이지 응답성을 지킨다.

## 3. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 백엔드 프레임워크 | **FastAPI** | Python 기반 확정, 비동기 처리·자동 API 문서화 지원, 가볍고 배우기 쉬움 |
| 프론트엔드 | **서버 렌더링(Jinja2) + 필요 시 HTMX** | 참가자 제출/리더보드/관리자 화면 모두 상대적으로 단순한 CRUD·조회 위주라 별도 SPA 프레임워크(React 등) 없이도 충분. 개발·운영 복잡도를 최소화 |
| 데이터베이스 | **PostgreSQL** | 팀·시즌·제출·기록이 관계형 데이터이고, 동시 제출·정렬(리더보드)·트랜잭션 처리에 안정적. SQLite보다 향후 시즌 누적 데이터가 많아져도 안정적으로 대응 |
| 평가 실행 | **DRFC (`dr-start-evaluation`)** | 이미 로컬 평가가 검증된 도구이므로 그대로 재사용. 웹 앱은 이를 subprocess/Docker로 호출하는 오케스트레이션만 담당 |
| 인증 | **세션 기반 로그인 + 비밀번호 해시(bcrypt)** | 관리자가 팀 계정을 사전 발급하는 구조이므로 OAuth 등 외부 인증 불필요. 단순 아이디/비밀번호로 충분 |
| 파일 저장 | **로컬 디스크 (구조화된 디렉터리)** | 확정된 전제. `storage/models/{season}/{team}/`, `storage/videos/{season}/{team}/` 형태로 정리 |

## 4. 데이터 모델 (핵심 엔티티)

| 엔티티 | 주요 속성 | 비고 |
|---|---|---|
| **Season (시즌/대회)** | id, 이름, 시작일, 마감일(예선 마감), 트랙 식별자, 상태(준비중/진행중/마감/아카이브됨) | 대회당 트랙 1개 고정 |
| **Team (팀)** | id, season_id, 팀명, 생성 시각, 실격 여부(플래그) | **매 시즌 완전히 새로 등록**한다 (지난 시즌 팀을 이어받지 않음). 팀명이 같아도 시즌마다 별개의 레코드 |
| **Account (계정)** | id, team_id, 로그인 아이디, 비밀번호 해시 | 관리자가 팀 등록 시 함께 발급. **시즌 아카이브 시 삭제 대상** (§5.4) |
| **Submission (제출)** | id, team_id, 제출 시각, 모델 파일 경로, 상태(대기/평가중/완료/오류), 하루 제출 카운트에 포함 여부(bool) | 하루 5회 한도는 **"완료" 상태가 된 제출만** 카운트한다 — 완주했든 시간 초과로 미완주했든 **평가 자체가 끝까지 실행되었으면 "완료"** 다. 모델 업로드 자체가 잘못됐거나 DRFC 실행이 시작/완주되지 못한 인프라적 문제(오류)만 카운트에서 제외된다 (§5.3). **한 팀은 "대기" 또는 "평가중" 상태의 제출을 동시에 1건만 가질 수 있다** — 새 모델은 이전 제출이 "완료" 또는 "오류"로 끝나 서버에 자기 모델이 올라가 있지 않은 상태일 때만 업로드할 수 있다 (§5.1) |
| **EvaluationResult (평가 결과)** | id, submission_id, 완주 여부(완주 / 미완주-타임아웃), 랩타임(미완주 시 null), 트랙 이탈 이벤트 수, 영상 경로, 원본 metrics json 저장 경로, 평가 완료 시각 | 제출 1건당 1개. "완료" 상태의 Submission에는 반드시 이 레코드가 있다(완주 실패도 유효한 결과). DRFC가 만드는 원본 metrics json도 그대로 보관해두면 추후 재파싱이 필요할 때 유용 |

리더보드의 "팀 최고기록"은 별도 테이블 없이 `EvaluationResult`를 팀별로 조회해 즉시 계산한다. 예상 규모(시즌당 10팀, 하루 제출 수 개)에서는 쿼리 성능이 문제되지 않으므로, 캐시 테이블을 두는 복잡도를 감수할 이유가 없다.

관계: `Season 1—N Team`, `Team 1—N Submission`, `Submission 1—1 EvaluationResult`.

## 5. 핵심 흐름

### 5.1 제출 → 평가 → 리더보드 반영
1. 참가자가 모델 파일을 업로드하면, 서버는 먼저 **이 팀이 현재 "대기" 또는 "평가중" 상태인 제출을 갖고 있는지** 확인한다. 있다면 업로드 자체를 막는다 — 참가자가 새 모델을 올릴 수 있는 유일한 상황은 자신의 이전 제출이 "완료"(기록 확정)되었거나 "오류"(업로드 실패 등)로 끝나, 현재 서버에 올라가 있는 자기 모델이 없는 상태뿐이다.
2. 다음으로 **오늘 "완료" 상태가 된 제출 횟수**가 5회 미만인지 검사한다. 초과 시 업로드를 막고 사유를 안내한다. ("완료"의 정확한 기준은 아래 5·6·8번 참고 — 업로드/실행 오류만 예외이고, 모델이 못 달려서 시간 초과가 나도 "완료"로 카운트된다.)
3. 두 조건을 통과하면 업로드된 파일이 DRFC가 기대하는 형식(확장자·용량)인지 검증한다. 이 단계에서 걸러지면(파일이 손상됐거나 형식이 틀림) 큐에 등록하지 않고 즉시 오류를 안내하며, **카운트하지 않는다**. (이 경우 "대기/평가중" 제출이 생기지 않으므로 참가자는 바로 재시도할 수 있다.)
4. 형식 검증을 통과하면 파일을 `storage/models/`에 저장하고 `Submission` 레코드를 "대기" 상태로 생성한다 (큐에 등록).
5. 평가 워커가 유휴 상태가 되면 큐에서 가장 오래된 "대기" 건을 꺼내 "평가중"으로 바꾸고 평가를 실행한다 (평균 약 10분 소요, §1 참고). 실행 절차는 §5.1a에서 상세히 다룬다.
6. 평가가 끝까지 실행되면(모델이 3바퀴를 완주했든, 시간 초과로 중단됐든 상관없이) 결과를 조회해 파싱한다 (§5.1a).
7. 파싱한 결과로 `EvaluationResult`를 생성한다 — 완주했으면 랩타임이 채워지고, 시간 초과로 미완주했으면 "미완주-타임아웃"으로 기록된다(랩타임 없음). 어느 쪽이든 `Submission` 상태를 "완료"로 바꾸고, **이 시점에 하루 제출 횟수(5회)에 카운트**되며, 동시에 이 팀은 다시 새 모델을 업로드할 수 있게 된다.
8. 이번 기록이 해당 팀의 기존 최고기록보다 좋으면(완주 기록만 순위에 반영되므로, 미완주 결과는 최고기록 갱신에 영향을 주지 않음) 리더보드 조회 결과가 자동으로 갱신된다. 참가자는 별도 알림 없이 페이지 새로고침으로 이를 확인한다.
9. DRFC 실행 자체가 비정상 종료되어(컨테이너 크래시 등) 평가가 끝까지 실행되지 못하면 `Submission` 상태를 "오류"로 바꾸고 사유를 기록한다. **오류 건만 하루 제출 한도에서 제외된다** — "모델이 못 달렸다"는 결과와 "시스템이 평가를 못 끝냈다"는 오류를 명확히 구분한다. 이 경우도 팀은 다시 업로드할 수 있게 된다.

### 5.1a DRFC 연동 세부사항 (STEP4에서 실제 WSL2 DRFC 환경을 조사해 확정, 2026-07-24)

STEP2 작성 시점에는 "dr-start-evaluation을 호출한다" 정도로만 적었으나, 실제 DRFC(`~/deepracer-for-cloud`) 소스와 로컬 MinIO 버킷을 직접 조사해 아래와 같이 구체화했다.

- **제출 형식 계약**: 참가자는 자신의 DRFC `model/` 폴더 내용(`.coach_checkpoint`, `deepracer_checkpoints.json`, `model_metadata.json`, 체크포인트 파일들)을 압축(zip 또는 tar.gz)해서 제출해야 한다. AWS SageMaker 콘솔이 만드는 단순 내보내기 형식(`model_metadata.json` + `agent/model.pb`만 있는 tar.gz)은 DRFC 로컬 학습이 만드는 체크포인트 형식과 달라 호환이 검증되지 않았으므로 **이번 범위에서는 지원하지 않는다**.
  - **중요(실제 테스트에서 확인된 함정)**: MinIO는 오브젝트를 디스크에 "폴더 + `xl.meta`(+ `part.N`)" 형태로 저장한다. 참가자가 `aws s3 sync`로 내보내지 않고 **MinIO 데이터 폴더를 그대로 압축하면** 파일 이름은 그럴듯해 보이지만 실제 모델 데이터가 들어가지 않는다. 워커는 아카이브에 `xl.meta`가 있으면 이 경우로 판별해 올바른 내보내기 명령(`aws s3 sync ... && tar -czf ...`)을 오류 메시지로 안내한다. 참가자 공지문에도 이 내용을 반드시 넣어야 한다 (docs/operations.md 참고).
  - 아카이브 안에서 `model_metadata.json`은 최상위가 아니어도 되며(상위 폴더로 감싸 압축한 경우가 흔함), 워커가 재귀적으로 찾아 가장 얕은 위치를 모델 루트로 삼는다.
- **모델 주입**: `dr-start-evaluation`은 별도 모델 경로 인자를 받지 않고 **항상 `s3://{DR_LOCAL_S3_BUCKET}/{DR_LOCAL_S3_MODEL_PREFIX}/model/`을 평가한다** (`scripts/evaluation/start.sh` 확인). 따라서 워커는 평가 실행 전에 참가자 아카이브를 풀어 이 경로에 boto3로 직접 업로드(기존 내용은 삭제 후)해야 한다.
  - **검토했으나 기각한 대안(2026-07-25)**: "참가자 모델을 `~/deepracer-for-cloud/data/minio/bucket/rl-deepracer-sagemaker/`에 폴더째 풀어놓고 평가를 돌리면 되지 않나"는 아이디어를 실제 환경을 조사해 검증한 결과 **불가능**하다. 근거 세 가지:
    1. **robomaker는 그 폴더를 읽지 않는다.** `docker/docker-compose-eval.yml`의 robomaker 서비스에 MinIO 데이터 디렉터리 볼륨 마운트가 없고, `docker-compose-endpoint.yml`이 `S3_ENDPOINT_URL=${DR_MINIO_URL}`(=`http://minio:9000`)만 주입한다. 즉 모델은 **S3 API로** 가져간다. `data/minio/`는 MinIO 서버의 내부 저장소일 뿐 DRFC의 인터페이스가 아니다.
    2. **그 폴더 안은 평범한 파일이 아니다.** 실제로 열어보면 `model/model_metadata.json/xl.meta`처럼 **객체 이름이 디렉터리이고 그 안에 msgpack 바이너리 `xl.meta`가 들어있는** 구조다(128KiB 초과 데이터는 별도 UUID 파일로 분리). 정상 내보내기한 진짜 모델 파일을 여기에 풀면 MinIO가 객체로 인식하지 못한다.
    3. 수동 테스트에서 이 방식이 동작했던 것은 **복사해 온 폴더가 이미 MinIO 내부 포맷이었기 때문**이며(포맷이 우연히 일치), 폴더 이름을 맞춰서가 아니다. 이 포맷은 MinIO 버전·erasure 설정에 따라 달라져 다른 참가자 환경에서 온 것은 깨질 수 있다.

    참고로 참가자 폴더 이름은 애초에 결과에 영향을 주지 않는다 — 워커가 `get_model_prefix()`로 항상 같은 S3 경로에 올리기 때문이다. 문제는 이름이 아니라 **내용물의 포맷**이다.
- **비차단 실행**: `dr-start-evaluation -q`는 Docker Swarm 스택(`deepracer-eval-$DR_RUN_ID`)을 배포만 하고 즉시 반환한다(블로킹하지 않음). 워커는 `docker stack ps`를 폴링해 완료를 감지한다. 이 폴링 로직은 셸 래퍼(`worker/run_evaluation.sh`)로 구현하고, Python 워커가 이를 서브프로세스로 호출해 블로킹 대기한다.
  - **주의(실제로 겪은 버그)**: `docker stack ps`는 **이미 끝난 태스크도 이력으로 계속 표시**하므로, 단순히 출력 줄 수를 세면 평가가 끝나도 카운트가 줄지 않아 타임아웃까지 대기하게 된다(7분 만에 끝난 평가가 30분을 기다렸다). 평가 컨테이너는 `restart_policy: none`(`docker-compose-eval-swarm.yml`)이라 완료되면 DESIRED STATE가 `shutdown`으로 바뀌므로, **`--filter desired-state=running -q`로 아직 살아있는 태스크만** 세야 한다. 참고로 DRFC의 `utils/evaluate.sh`가 쓰는 단순 줄 수 세기는 "스택을 지운 뒤 사라졌는지" 확인용이라 목적이 다르다.
  - 시작 감지도 필요하다: 배포 직후엔 태스크가 아직 안 뜰 수 있으므로 일정 시간(기본 300초) 안에 running 태스크가 나타나는지 먼저 확인하고, 그 뒤에 0이 될 때까지 기다린다.
- **결과 조회**: 평가 결과는 `s3://{bucket}/{DR_LOCAL_S3_MODEL_PREFIX}/metrics/evaluation/evaluation-*.json`에 남는다. 실제 구조:
  ```json
  {"metrics": [{"trial": 1, "completion_percentage": 100, "elapsed_time_in_milliseconds": 36798, "off_track_count": 0, ...}, ...]}
  ```
  `trial` 1개 = 1바퀴이며 개수는 `DR_EVAL_NUMBER_OF_TRIALS`(온라인 평가는 3)로 결정된다. `required_laps`개의 trial이 모두 `completion_percentage == 100`이면 "완주"로 판정하고, 그 trial들의 `elapsed_time_in_milliseconds` 합(초 단위)을 랩타임으로 쓴다. 하나라도 미달이면 "미완주-타임아웃".
  파일시스템 관점에서 이 키는 실제 파일이 아니라 MinIO 오브젝트라서, 워커는 boto3로 **키에 `valuation`을 포함하고 `.json`으로 끝나는 오브젝트 중 LastModified 최신**을 찾아 다운로드 후 Python `json` 모듈로 파싱한다.
- **영상**: `s3://{bucket}/{DR_LOCAL_S3_MODEL_PREFIX}/mp4/camera-topview/0-video.mp4` 고정 키에 남는다. **이 키는 평가마다 덮어써진다** — 다음 팀 평가가 시작되기 전, 이번 평가 직후 반드시 영상을 내려받아 `storage/videos/`로 복사해야 한다. 워커가 한 번에 한 건씩 순차 처리하는 지금 설계에서는 자연스럽게 안전하다(§8 워커 풀 확장 시에는 이 가정이 깨지므로 별도 대응 필요 — multi-laptop-worker-pool.md 참고 대상에 추가).
- **MinIO 접속**: `DR_LOCAL_S3_ENDPOINT_URL`이 `localhost`를 가리키면 WSL2 환경에서 타임아웃이 발생한다(사용자가 직접 확인). 워커는 `ip route get 1.1.1.1`로 확인한 실제 WSL IP로 자동 대체한다.
- **DR 환경변수 소싱**: 워커(및 `run_evaluation.sh`)는 `~/deepracer-for-cloud/bin/activate.sh run.env`를 직접 source해서 `DR_*` 값을 얻는다 — 앱이 별도로 관리하지 않는다는 기존 결정(§1)과 일치. 단 `activate.sh`는 미설정 변수 참조·grep 비매치가 정상 동작에 포함되어 있어, source하는 구간에서는 `set -e -u -o pipefail`을 잠시 꺼야 한다.
- **로그 보존**: DRFC는 `DR_ROBOMAKER_MOUNT_LOGS=False`이면 시뮬레이션 로그를 디스크에 남기지 않는다. 로그는 Swarm 서비스가 살아있는 동안만 `docker service logs`로 접근 가능하고 `dr-stop-evaluation`으로 스택을 지우면 영구히 사라져, 평가 실패 원인을 추적할 수 없게 된다. 따라서 워커는 **스택을 내리기 직전에** robomaker/rl_coach 로그를 `storage/eval_logs/{제출ID}.log`로 받아둔다.
- **산출물 보관 위치**: 결과는 DB(`evaluation_results`), 영상은 `storage/videos/{시즌}/{팀}/{제출ID}.mp4`, 원본 metrics json 사본은 `storage/metrics/{시즌}/{팀}/{제출ID}.json`, 시뮬레이션 로그는 `storage/eval_logs/{제출ID}.log`. MinIO 쪽 원본은 다음 평가 때 덮어써질 수 있으므로 우리 `storage/`의 사본이 실제 보관본이다.

### 5.2 리더보드 정렬 규칙
- 정렬 기준: 완주한 팀 중 **최고 랩타임 오름차순**.
- 미완주 팀 표시 방식: 완주 팀 목록 아래에 "미완주"로 별도 구분해 노출 (순위 번호는 부여하지 않음).
- 동점(완전히 같은 랩타임) 처리: 먼저 그 기록을 세운(제출 시각이 빠른) 팀을 상위로 — 참가자에게도 이 규칙을 명시해 이의 제기를 방지한다.
- 실격 처리된 팀: 리더보드 쿼리 자체에서 제외 (실격 플래그가 있는 팀은 필터링).

### 5.3 하루 제출 한도 처리
- 팀별로 "오늘 제출 횟수"를 계산할 때는 **한국 시간(KST) 자정 기준**으로 리셋한다.
- 카운트 기준은 "잘 달렸는지"가 아니라 **"평가가 끝까지 실행되어 결과가 확정됐는지"** 다.
  - **카운트됨**: 모델이 정상적으로 업로드·실행되어 평가가 끝까지 돌아간 경우 — 3바퀴를 완주했든, 못 달려서 시간 초과(미완주)로 끝났든 상관없이 모두 카운트.
  - **카운트 안 됨**: 업로드 단계에서 파일 형식·손상 문제로 거부된 경우, 또는 DRFC 실행 자체가 인프라 문제로 비정상 종료(오류)된 경우.
- 남은 횟수를 제출 페이지에 항상 표시해 참가자가 미리 계획할 수 있게 한다.
- 이 규칙에서는 "모델이 못 달리게" 일부러 만들어서 카운트를 피하는 시도가 통하지 않는다 — 평가가 정상적으로 끝까지 실행되기만 하면(결과가 나쁘더라도) 카운트되기 때문이다.
- **동시 제출 제한(확정)**: 한 팀은 "대기" 또는 "평가중" 상태의 제출을 동시에 1건만 가질 수 있다. 새 모델을 업로드할 수 있는 유일한 상황은 자기 팀의 모델이 서버에 전혀 올라가 있지 않은 상태(=이전 제출이 "완료"되었거나 "오류"로 끝난 경우)뿐이다. 이 규칙 덕분에 한 팀이 대기열을 독점해 다른 팀의 대기 시간을 늘리는 문제도 자연스럽게 방지된다.
- 관리자는 테스트/운영 편의를 위해 팀의 "오늘 완료 카운트"를 수동으로 조정할 수 있다 (예: 한도 테스트 시 실제로 5번 제출하지 않고 카운트를 4로 맞춰 바로 5번째 동작을 확인) — tasks.md 참고.
  - **주의(검증 중 발견한 버그)**: 이 조정값은 **절대값이 아니라 실제 완료 건수에 더해지는 델타**로 저장해야 한다. 절대값으로 덮어쓰면 조정한 뒤에 완료되는 평가가 카운트에 반영되지 않아 하루 한도가 영영 걸리지 않는다. 관리자가 "4"를 지정하면 그 시점의 실제 완료 건수와의 차이를 델타로 저장하고, 이후 완료 건은 그대로 누적된다 (`teams.daily_count_adjustment`).

### 5.4 시즌 종료 처리 (아카이빙)
시즌이 끝나면(관리자가 "아카이브" 처리) 다음을 수행해 저장 공간을 아낀다:
1. 각 팀의 **최종 리더보드 항목**(팀명, 최고기록, 최고기록에 해당하는 영상)은 그대로 영구 보존한다 — STEP1의 "지난 시즌 기록도 조회 가능해야 한다"를 만족시키기 위함.
2. 최고기록이 아닌 나머지 제출들의 모델 파일·영상 원본은 삭제한다 (리더보드에는 어차피 최고기록만 노출되므로).
3. 팀 로그인 계정(`Account`)은 삭제하거나 비활성화한다 — 시즌이 끝나면 더 이상 로그인할 필요가 없기 때문.
4. 관전자용 리더보드 화면에서는 아카이브된 시즌도 계속 목록에 남아 조회 가능해야 한다 (기록·영상은 유지되므로 화면 자체는 그대로 동작).

## 6. 보안·검증 고려사항

- 업로드 파일은 확장자·용량 상한을 검증한다 (DRFC가 기대하는 모델 아카이브 형식에 맞는지).
- 평가는 격리된 Docker 컨테이너(DRFC 표준 방식)에서 실행되므로 임의 모델 파일이 호스트를 직접 침해할 위험은 DRFC의 격리 수준에 의존한다 — 이 부분은 DRFC 자체의 보안 모델을 신뢰하는 것을 전제로 한다.
- 관리자 페이지는 팀 계정과 분리된 별도 권한(관리자 계정)으로 접근한다.
- **공인 인터넷 노출에 따른 추가 조치** (2026-07-25, [deployment-public-access.md](deployment-public-access.md) 참고):
  - `SESSION_SECRET`은 기본값(`change-me-in-production`)을 절대 그대로 쓰지 않고, 운영 전 `.env`에 무작위 값을 설정한다.
  - 세션 쿠키의 HTTPS 강제 여부는 `SESSION_HTTPS_ONLY` 환경변수(기본 `false`)로 제어한다. 실제 대회를 Cloudflare Tunnel로 운영할 때는 `.env`에 `SESSION_HTTPS_ONLY=true`를 설정한다 — 단, 터널 없이 `http://localhost:8000`으로 직접 접속하는 로컬 테스트/관리 작업 중에는 `false`로 둬야 로그인이 정상 동작한다.
  - DB(PostgreSQL) 포트(5432)는 공인 인터넷에 노출하지 않는다 — Cloudflare Tunnel은 `web` 컨테이너의 HTTP 포트만 중계하고, DB는 계속 로컬(WSL 호스트)에서만 접근 가능하게 둔다.

## 7. 배포/운영 개요

- Docker Compose로 `웹 앱 컨테이너 + PostgreSQL 컨테이너`를 함께 기동한다. 평가 워커와 DRFC는 (기존 결정대로) 컨테이너가 아니라 WSL 호스트에서 직접 실행한다.
- 로그·모델 파일·영상은 모두 호스트에 볼륨 마운트해 컨테이너 재시작에도 유실되지 않도록 한다.
- **외부 접속**: 도메인을 별도로 구입하지 않는 한, `cloudflared`의 Quick Tunnel(`cloudflared tunnel --url http://localhost:8000`)로 `web` 컨테이너의 8000번 포트만 공인 인터넷에 노출한다. 공유기 포트포워딩이나 고정 공인 IP가 필요 없다. 절차는 [deployment-public-access.md](deployment-public-access.md) 참고. 노트북(WSL)과 `cloudflared` 프로세스가 대회 기간 내내 켜져 있어야 하며, 이는 평가 워커가 어차피 같은 노트북에서 상시 실행돼야 하는 것과 동일한 제약이다.
