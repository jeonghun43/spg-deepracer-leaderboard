# GPU 없는 노트북 여러 대로 평가 처리량 늘리기 (워커 풀 구성)

> GPU를 못 구했을 때, 보유 중인 여러 대의 GPU 없는 노트북을 "여러 대의 평가 서버"처럼 묶어서 쓸 수 있는지에 대한 조사·설계 문서. [gpu-server-migration.md](gpu-server-migration.md)(GPU 1대로 이전)와는 다른, **"1대를 더 세게" 대신 "여러 대를 병렬로"** 접근이다.

## 결론: 가능하다 — 단, DRFC 자체 기능이 아니라 우리 애플리케이션 레벨에서 구현해야 한다

공식 문서·저장소를 확인한 결과, DRFC(deepracer-for-cloud)는 **Docker Swarm 모드로 여러 대의 컴퓨터를 연결하는 기능을 이미 제공**한다. 하지만 이 기능의 목적은 우리가 원하는 것과 다르다.

- **DRFC의 Swarm 모드가 하는 일**: *하나의* 학습/평가 작업을 여러 대에 걸쳐 분산시켜 *그 작업 하나를* 더 빠르게 끝내는 것 (예: Sagemaker 1대 + Robomaker 여러 대를 여러 머신에 흩어 놓고, 한 번의 학습에 시뮬레이션 인스턴스를 N개 붙여 속도를 올림).
- **우리가 원하는 것**: 팀 A의 평가와 팀 B의 평가처럼 **서로 다른 여러 개의 독립적인 작업을 동시에** 처리하는 것 (노트북 1은 팀 A를, 노트북 2는 팀 B를 각각 평가).

즉 DRFC의 Swarm은 "한 작업을 여러 대가 나눠서 빨리 끝내기"이고, 우리에게 필요한 건 "여러 작업을 여러 대가 각자 하나씩 동시에 처리하기"다. 후자는 DRFC 자체 기능이 아니라, **우리 애플리케이션(plan.md에서 이미 설계한 "DB 테이블 기반 큐 + 워커")을 여러 대에서 각각 띄우는 방식**으로 구현하는 것이 맞다. 다행히 지금 설계가 정확히 이 확장에 맞는 구조다.

## 아키텍처

```
                      ┌───────────────────────────────┐
                      │   중앙 서버 (노트북 중 1대,      │
                      │   또는 별도의 상시 켜진 기기)     │
                      │                                 │
                      │  웹 애플리케이션 + PostgreSQL     │
                      │  (팀·시즌·제출·기록 메타데이터)    │
                      │  storage/ (모델 원본·영상)        │
                      └───────────────┬─────────────────┘
                                       │  같은 LAN(Wi-Fi/유선)
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
      [워커 노트북 1]            [워커 노트북 2]            [워커 노트북 3]
   자체 WSL2 Ubuntu + DRFC   자체 WSL2 Ubuntu + DRFC   자체 WSL2 Ubuntu + DRFC
   우리 워커 프로세스          우리 워커 프로세스          우리 워커 프로세스
```

- **중앙 서버**: 웹 앱, DB, 모델/영상 원본 저장소를 담당. 노트북 중 한 대가 겸해도 되고, 항상 켜둘 수 있는 별도 기기(미니PC 등)를 써도 된다.
- **워커 노트북들**: 각자 **독립적으로** WSL2 Ubuntu + DRFC를 설치한다 (지금 개발 중인 노트북과 완전히 동일한 방식으로, 노트북 대수만큼 반복). DRFC끼리는 서로 몰라도 된다 — 각자 자기 로컬 MinIO/S3에 결과를 남기는, 완전히 독립된 DRFC 인스턴스다.
- **우리 워커 프로세스**는 노트북마다 하나씩 실행되며, 모두 **같은 중앙 큐(DB)** 를 바라본다.

## 처리 흐름

1. 각 워커 노트북의 워커 프로세스가 중앙 DB에 "대기" 상태 제출이 있는지 주기적으로 확인한다.
2. 대기 건을 발견하면, **원자적으로(atomic)** 자기 것으로 확보(claim)한다 — `UPDATE ... SET 상태='평가중', worker_id=? WHERE id = (SELECT id FROM submission WHERE 상태='대기' ORDER BY 제출시각 LIMIT 1 FOR UPDATE SKIP LOCKED)` 같은 패턴. 이 부분이 기존 설계(plan.md §2)에서 **새로 추가해야 하는 부분**이다 — 워커가 1대뿐일 때는 경쟁(race condition) 걱정이 없었지만, 여러 대가 동시에 폴링하면 두 워커가 같은 건을 동시에 집어가지 않도록 반드시 원자적 claim이 필요하다.
3. 자기 것으로 확보한 워커는 모델 파일을 중앙 서버에서 **다운로드**한다 (웹 앱에 내부용 API 엔드포인트를 하나 추가: `GET /internal/submissions/{id}/model`).
4. 자기 로컬 DRFC로 `dr-start-evaluation`을 돌린다 (기존과 동일한 방식, 이 노트북 안에서만 실행됨).
5. 자기 로컬 MinIO/S3에서 metrics json과 영상을 가져와 파싱한다 (기존 §5.1과 동일한 로직).
6. 결과(EvaluationResult 데이터 + 영상 파일)를 중앙 서버로 **업로드**한다 (`POST /internal/submissions/{id}/result`).
7. 중앙 서버가 `Submission` 상태를 "완료"(또는 "오류")로 바꾸고, 이후 흐름은 기존과 동일 (리더보드 반영, 팀 재업로드 가능 등).

## 기존 설계에서 바뀌어야 하는 부분 (plan.md 기준)

| 항목 | 기존(워커 1대 전제) | 변경 필요 |
|---|---|---|
| 큐에서 작업 꺼내기 | 단순 `SELECT` 후 상태 변경 | **원자적 claim**(`FOR UPDATE SKIP LOCKED` 등)으로 경쟁 방지 |
| `Submission` 테이블 | 상태만 관리 | **`worker_id`(어느 노트북이 처리 중인지) 컬럼 추가** — 장애 시 어느 노트북을 확인해야 할지 알 수 있어야 함 |
| 모델 파일 접근 | 워커가 로컬 `storage/`를 직접 읽음 | 워커가 원격에 있으므로 **중앙 서버에서 다운로드하는 API** 필요 (또는 네트워크 파일 공유(SMB/NFS)로 대체 가능하지만, 이미 FastAPI를 쓰고 있으므로 API 방식이 더 일관적) |
| 결과 저장 | 워커가 로컬 `storage/`에 직접 씀 | 워커가 원격에 있으므로 **중앙 서버로 업로드하는 API** 필요 |
| DB 접근 | 로컬 접속 | Postgres가 **LAN의 다른 기기에서도 접속 가능**하도록 설정 (`listen_addresses`, `pg_hba.conf`, 방화벽 포트 5432 개방) |
| 좀비 작업 감지(T034) | "있으면 좋음" 정도 | **더 중요해짐** — 워커 노트북 1대가 꺼지거나 네트워크가 끊기면 그 작업만 "평가중"에 멈추고, 다른 워커들은 영향받지 않아야 하므로, 일정 시간(예: 평가 1건 평균 소요시간의 3배 이상) 이상 "평가중"에 머문 건은 다시 "대기"로 되돌리는 타임아웃 로직이 필요 |

## 처리량 효과

평가 1건당 소요 시간(약 10분)은 노트북 성능이 그대로이므로 **줄어들지 않는다** — 이게 GPU 서버 이전과의 핵심 차이다. 대신 **동시에 여러 건을 처리**할 수 있게 되어 전체 대기열이 빨리 빠진다.

- 노트북 1대: 하루 최악의 경우(10팀×5회=50건) 약 500분(8시간 20분)
- 노트북 3대(각자 독립적으로 병렬 처리): 이론상 약 1/3인 **170분(2시간 50분)**
- 실제로는 참가자들이 하루 3~5회 수준으로만 제출할 것으로 예상(plan.md §1)되므로, 노트북 2~3대만으로도 대기 체감은 크게 개선된다.

## 설정 절차 개요

1. **중앙 서버 준비**: 웹 앱 + Postgres + storage를 노트북 1대(또는 별도 상시 기기)에 기존 방식대로 설치. Postgres를 LAN에서 접속 가능하게 설정.
2. **워커 노트북마다 반복**:
   - WSL2 Ubuntu 설치 → DRFC 클론·설정 (지금 노트북에서 한 것과 동일)
   - `dr-start-evaluation` 단독 실행으로 이 노트북에서 정상 동작하는지 먼저 확인
   - 우리 워커 프로세스 코드를 배포하고, `DATABASE_URL`을 중앙 서버의 LAN 주소로, 모델 다운로드/결과 업로드 API 주소도 중앙 서버로 설정
3. **네트워크**: 모든 노트북이 같은 Wi-Fi/유선 네트워크에 있어야 하며, 고정 IP나 로컬 호스트명을 써서 중앙 서버 주소가 바뀌지 않게 해두는 것을 권장.
4. **검증**: 노트북 2대 이상에서 동시에 제출을 넣어, 서로 다른 노트북이 각각 다른 건을 동시에 처리하는지, 같은 건을 두 워커가 동시에 집어가지 않는지 확인 (tasks.md Phase 8 검증에 추가할 항목).

## 트레이드오프 (GPU 서버 이전과 비교)

| | 노트북 여러 대(워커 풀) | GPU 서버 1대 |
|---|---|---|
| 개별 평가 1건 속도 | 그대로(약 10분) | 빨라짐 |
| 동시 처리량 | 노트북 대수만큼 증가 | 1건씩(순차) — 단, 개별 속도가 빠르므로 결과적으로 대기시간은 비슷하게 줄어들 수 있음 |
| 구현 복잡도 | 원자적 claim, 파일 전송 API, 좀비 작업 감지 등 **추가 구현 필요** | 기존 설계 그대로, 인프라만 이전(코드 변경 없음) |
| 운영 부담 | 노트북 여러 대를 각각 관리(전원, 네트워크, DRFC 상태) | 서버 1대만 관리 |
| 비용 | 이미 보유한 노트북 재활용, 추가 비용 거의 없음 | GPU 서버 구매/대여 비용 필요 |

두 방법은 서로 배타적이지 않다 — 나중에 GPU 서버를 구하더라도, 그 GPU 서버를 워커 풀의 워커 노트북 중 하나(가장 빠른 워커)로 추가하는 식으로 함께 쓸 수 있다.

## 실제로 도입하기로 하면 tasks.md에 추가될 작업 (제안)

- 원자적 job claim 로직 구현 (`FOR UPDATE SKIP LOCKED`)
- `Submission.worker_id` 컬럼 추가 + 마이그레이션
- 모델 파일 다운로드 API / 평가 결과 업로드 API (`/internal/...`)
- 워커 프로세스를 "원격 모드"로 실행할 수 있도록 설정값 분리 (로컬 storage 직접 접근 모드 vs 원격 API 모드)
- 좀비 작업(타임아웃) 감지·재큐잉 로직
- Postgres 원격 접속 설정 문서화
- 워커 노트북 추가/제거 운영 가이드
