## 0. 한눈에 보기

```
           ┌──────────────── 웹 서버 (Lightsail) ───────────────┐
           │                                                    │
 참가자 ──▶│  web (기존)      관리자 페이지: 자동화 스위치·상태·기록  │
           │     │                                              │
           │     ▼                                              │
           │  db (기존) ◀──── autopilot (새 컨테이너, 1분마다)     │──▶ 디스코드 웹훅
           │     ▲              ├ 대기열·하트비트·스위치를 읽고     │
           │     │              ├ 필요하면 EC2 "시작" API 호출 ────│──▶ AWS EC2 API
           │     │              └ 쌓인 알림을 디스코드로 보낸다     │
           └─────│──────────────────────────────────────────────┘
                 │ Tailscale (기존)
           ┌─────│──────── 평가 서버 (EC2 온디맨드) ─────────────────┐
           │  drfc-worker (기존)                                    │
           │  drfc-autostop (새 systemd 타이머, 1분마다)              │
           │     ├ 스위치·대기열·평가 스택·SSH 접속을 확인하고          │
           │     ├ 30분 유휴면 DB에 "끕니다" 기록을 남긴 뒤             │
           │     └ 스스로 poweroff → 인스턴스 "중지"                    │
           └───────────────────────────────────────────────────────┘
```

**역할을 나눈 원칙: 켜기는 밖에서, 끄기는 안에서.**

- **켜기**는 꺼져 있는 서버가 스스로 할 수 없다. 그래서 늘 켜져 있는 웹 서버가 AWS API로 켠다.
- **끄기**는 서버 안에서 `poweroff`하면 된다. AWS 키가 필요 없다. 그래서 평가 서버에는 지금처럼
  **AWS 자격증명을 두지 않는다**(CLAUDE.md §4 규칙 유지).
- **알림은 웹 서버 한 곳에서만 보낸다.** 평가 서버는 "알릴 일"을 DB에 적기만 한다. 그래서 디스코드
  웹훅 주소가 웹 서버 `.env` 한 곳에만 있다.

## 1. 웹 서버 쪽 — `autopilot` 컨테이너

### 1.1 어디서 돌리나: compose의 새 서비스

`docker-compose.prod.yml`에 `autopilot` 서비스를 추가한다. 이미지는 `web`과 **같은 이미지**
(`build: .`)를 쓰고, 명령만 `python -m app.autopilot`으로 바꾼다.

| 검토한 방식 | 판단 |
|---|---|
| **compose 새 서비스** | **채택.** 배포(tar → `up -d --build`)에 그대로 실려 간다. 같은 이미지라 의존성(boto3, httpx, SQLAlchemy)이 이미 있다. `restart: unless-stopped`로 죽어도 다시 뜬다 |
| 서버 호스트의 cron | 호스트에 파이썬 환경이 없다. 코드는 tar로 오지만 실행 환경을 따로 관리해야 한다 |
| `web` 컨테이너 안의 백그라운드 스레드 | 웹 프로세스가 재시작·확장될 때 중복 실행되기 쉽다. 그리고 AWS 키를 `web`에 넣어야 한다 |
| AWS Lambda + EventBridge | 무료 한도 안이지만 구성 요소가 늘고, DB(Tailscale 안쪽)에 닿게 만드는 일이 크다 |

- **AWS 키와 디스코드 웹훅은 `autopilot` 서비스에만 넘긴다.** `web`에는 넘기지 않는다. 웹이
  털려도 AWS 키는 환경변수에 없다.
- 메모리 상한 `mem_limit: 150m`. 웹 서버는 2GB라 여유가 있다(web 900m, caddy 256m).
- DB 표는 `web`이 기동하면서 `alembic upgrade head`로 만든다. `autopilot`이 먼저 떠서 표가 없으면
  오류로 죽었다가 `restart`로 다시 뜬다. 별도 처리는 하지 않는다.

### 1.2 1분마다 하는 일

1분 주기는 S1(제출 후 2분 안에 켜기 요청)을 만족시키는 가장 긴 간격이다.

1. **스위치와 상태를 읽는다**(DB): 자동화 켜짐 여부, 대기 중 제출 수, 대상 워커의 마지막 생존 신호.
2. **인스턴스 상태를 읽는다**(AWS `DescribeInstances`): `stopped` / `pending` / `running` / `stopping` 등.
   결과를 DB에 저장해 관리자 페이지가 보여 준다. 관리자 페이지는 AWS를 직접 부르지 않는다(§1.1의 키 분리).
3. **판단한다**(아래 표).
4. **쌓인 알림을 보낸다**: 아직 안 보낸 이벤트(§3.2)를 디스코드로 보내고 "보냄"으로 표시한다.

#### 판단 표 — 스위치 "켜짐"일 때

| 대기 중 제출 | 대상 워커 | 인스턴스 | 행동 |
|---|---|---|---|
| 있음 | 살아 있지 않음 | `stopped` | **`StartInstances` 호출.** 이벤트 `start_requested` |
| 있음 | 살아 있지 않음 | `pending` / `running` | 기다린다. 마지막 켜기 요청 후 **10분**이 지났으면 이벤트 `start_timeout`(켜기 요청 1건당 1번만) |
| 있음 | 살아 있지 않음 | `stopping` | 기다린다. 다 꺼지면 다음 주기에 켠다(§2.4의 경합) |
| — | 살아 있음 | — | 할 일 없음 |
| 없음 | — | — | 할 일 없음(끄기는 평가 서버가 한다) |
| `StartInstances` 실패 | | | 이벤트 `start_failed`. 같은 오류는 **30분에 1번**만 |

#### 스위치 "꺼짐"일 때 (명세서 §3.4에서 STEP2로 넘긴 것)

- 켜지도 끄지도 않는다.
- 다만 **대기 중 제출이 있는데 대상 워커가 10분 넘게 살아 있지 않으면** 이벤트 `manual_attention`을
  한 번 남긴다. 대회 기간 외에는 제출이 없으니 울리지 않는다. 운영자가 스위치를 끄고 서버 켜는 것을
  잊은 경우에만 울린다. 워커가 살아나거나 대기열이 비면 다시 울릴 수 있는 상태로 돌아간다.

### 1.3 "대상 워커"를 어떻게 알아보나

워커 ID는 EC2 호스트 이름(`ip-172-31-34-7`)이다([worker/run.py](../../worker/run.py)의 `WORKER_ID`).
`autopilot`은 `DescribeInstances` 결과의 **사설 DNS 이름**(`ip-172-31-34-7.ap-northeast-2.compute.internal`)
앞부분을 잘라 대상 워커 ID로 쓴다.

- 설정에 워커 ID를 따로 적지 않아도 된다. **인스턴스 ID 하나만** 설정하면 된다.
- 사설 IP는 같은 인스턴스를 중지·시작해도 바뀌지 않는다. 인스턴스를 새로 만들면 인스턴스 ID 설정만 바꾸면 된다.
- 다른 기기의 워커(노트북 등)는 판단에 넣지 않는다(명세서 Q2).
- 기존 [app/worker_status.py](../../app/worker_status.py)의 `get_worker_status`는 **모든 워커 중
  최신**을 보므로 그대로 쓰지 않는다. 특정 워커 ID의 하트비트를 읽는 함수를 따로 둔다.
  "살아 있다"의 기준(3분, `worker_heartbeat_stale_minutes`)은 같은 값을 쓴다.

### 1.4 안전장치 — "종료 시 동작" 점검

`autopilot`은 기동할 때와 이후 **하루 1번**, 대상 인스턴스의 `InstanceInitiatedShutdownBehavior`를
읽는다(`DescribeInstanceAttribute`). `stop`이 아니면 이벤트 `misconfigured`를 남긴다.

**이유**: 평가 서버가 스스로 `poweroff`할 때 이 값이 `terminate`이면 **디스크째 사라진다**
(2026-10-01 사고와 같은 결과). 기본값은 `stop`이지만, 누가 바꾸거나 새 인스턴스를 잘못 만들면 첫
자동 끄기에서 사고가 난다. 그래서 끄기 전에 미리 경고한다.

## 2. 평가 서버 쪽 — `drfc-autostop` 타이머

### 2.1 구성

| 파일 | 내용 |
|---|---|
| `worker/autostop.py`(새 파일) | 1회 판단하고 끝나는 스크립트. 저장소의 `.venv`와 `.env`(`DATABASE_URL`)를 그대로 쓴다 |
| `/etc/systemd/system/drfc-autostop.service` | 위 스크립트를 **root로** 1번 실행한다(`poweroff`와 `docker` 조회에 필요) |
| `/etc/systemd/system/drfc-autostop.timer` | 부팅 5분 뒤부터 **1분마다** 서비스를 실행한다 |

유닛 파일 내용은 지금처럼 [worker-server-setup.md](../../docs/worker-server-setup.md)에 싣는다(§8.6과 같은 방식).

### 2.2 1분마다 하는 일

1. **스위치가 "꺼짐"이면** 유휴 기록을 지우고 끝낸다. 사람이 직접 관리하는 상태다.
2. **"바쁨" 조건 셋을 확인한다.** 하나라도 참이면 유휴 기록을 지우고 끝낸다.
   - DB: 대기(`queued`) 또는 평가중(`running`) 제출이 있다
   - `docker stack ls`에 `deepracer-eval-`로 시작하는 스택이 있다
3. **SSH 접속을 확인한다**(`who`의 결과가 비어 있지 않음).
   - 접속이 있으면 끄지 않는다. "SSH 때문에 못 끄는 중" 시작 시각을 기록한다.
   - 그 상태가 **60분**을 넘으면 이벤트 `ssh_blocking`을 한 번 남긴다.
4. **유휴 시작 시각을 기록하고**, **30분**이 지났으면 아래 순서로 끈다.
   1. 이벤트 `idle_stop`을 DB에 기록한다. 끄고 나면 알릴 수 없으니 **먼저** 남긴다. 웹 서버의 `autopilot`이 디스코드로 보낸다
   2. `systemctl stop drfc-worker`로 워커를 내린다
   3. **다시 확인한다.** 2-1과 2-2 사이에 워커가 제출을 집었을 수 있다. 이 서버의 워커 ID로
      `running`인 제출이 있으면 `queued`로 되돌린다(`recover_stale_running`과 같은 처리)
   4. `systemctl poweroff`

유휴·SSH 시작 시각은 **`/run/drfc-autostop/`** 에 파일로 둔다. `/run`은 재부팅하면 비워지므로,
켜질 때마다 유휴 시간이 0부터 다시 센다. 이것이 의도한 동작이다.

### 2.3 왜 이렇게 끄나

| 검토한 방식 | 판단 |
|---|---|
| **서버 안에서 `poweroff`** | **채택.** AWS 키가 필요 없다. 인스턴스의 "종료 시 동작"이 `stop`이면 중지 상태가 된다(§1.4에서 점검) |
| 웹 서버가 `StopInstances` 호출 | 웹 서버 키에 끄기 권한까지 줘야 한다(명세서 §3.1: 켜기만). 평가 중인지, SSH 접속이 있는지를 밖에서는 정확히 알 수 없다 |

#### 서버 안 `poweroff`와 콘솔 "중지"는 같은 결과인가 (2026-10-04 확인)

운영자가 "콘솔에서 중지를 누르는 것과 정말 같으냐"고 물어 AWS 문서로 확인했다.

- AWS 문서: *EBS 기반 인스턴스에서 `shutdown`·`poweroff` 같은 명령으로 종료를 시작하면 기본적으로
  인스턴스는 **중지**된다.* 이 동작은 `InstanceInitiatedShutdownBehavior` 속성으로 정하고, 기본값은 `stop`이다.
- 같은 문서: 이 속성은 **운영체제 안에서 끌 때에만** 적용된다. 콘솔이나 `StopInstances`로 끌 때는 적용되지 않는다.
- 콘솔 "중지"도 결국 운영체제에 ACPI 전원 버튼 신호를 보내 **정상 종료**시키는 것이다. 그러니 두 방식의
  차이는 "누가 전원 버튼을 눌렀나"뿐이고, 끝난 뒤 상태는 같다.

| | 콘솔 "중지" | 서버 안 `poweroff` ("종료 시 동작" = 중지일 때) |
|---|---|---|
| 끝난 상태 | `stopped` | `stopped` |
| EBS 디스크(DRFC, MinIO 이미지, `.env`, `eval_logs`) | 남는다 | 남는다 |
| 사설 IP(→ 워커 ID) | 그대로 | 그대로 |
| 공인 IP | 반납(다시 켜면 새 IP) | 반납(다시 켜면 새 IP) |
| 요금 | 인스턴스 요금이 멈춘다 | 인스턴스 요금이 멈춘다 |
| 상태 전환 사유(§8.11) | `Client.UserInitiatedShutdown` | `Client.InstanceInitiatedShutdown` |

**결과가 달라지는 경우는 두 가지뿐이다. 둘 다 이번 구성에는 해당하지 않게 막는다.**

| 경우 | 결과 | 이번 구성 |
|---|---|---|
| "종료 시 동작"이 `terminate`로 바뀌어 있다 | 서버 안에서 끄면 **디스크째 사라진다** | §1.4가 매일 점검한다. 배포 1단계에서 직접 확인한다 |
| 인스턴스 스토어 기반 AMI | 운영체제에서 끄면 항상 종료된다 | 우리는 EBS 기반이다 |

**2026-10-04 실측**: 온디맨드 평가 서버(`ip-172-31-61-59`)에서 `sudo poweroff`를 실행했다. SSH가
`closed by remote host`로 끊기고 잠시 뒤 콘솔에 **중지됨**이 떴다. 다시 켜니 사람이 아무것도 하지
않아도 `drfc-worker`가 `active (running)`으로 살아나 `워커 시작` 로그를 남겼다. 자동 끄기 → 자동 켜기
한 바퀴가 수동으로는 동작한다는 것을 확인했다.

2026-10-01 사고는 이것과 **다른 장치**였다. 그때는 **스팟 회수**의 "중단 동작"이 기본값(종료)이었다.
지금 대상은 온디맨드라 회수 자체가 없다. 나중에 이 기능을 스팟에 쓰려면 이 절을 다시 검토한다.

AWS의 개발자 글(*Auto-Stop EC2 instances when they finish a task*)도 같은 방식(서버 안에서
`shutdown -h now`)을 쓴다. 그 글이 경고한 함정은 **"스크립트가 잘못되면 들어가서 고치기 전에 서버가
꺼져 버린다"**이다. 이번 설계는 세 가지로 막는다.
- 부팅 5분 뒤부터 확인을 시작한다
- SSH로 접속해 있으면 끄지 않는다
- 관리자 페이지 스위치를 끄면 아무것도 끄지 않는다

### 2.4 경합 — 꺼지는 중에 새 제출이 오면

1. 평가 서버가 2-1~2-4로 꺼지는 중에 제출이 들어온다.
2. `autopilot`이 보면 인스턴스가 `stopping`이라 기다린다(§1.2 표).
3. 완전히 `stopped`가 된 다음 주기에 다시 켠다.

손실은 없고 지연만 몇 분 생긴다. 2-3의 재확인 덕분에 `평가중`에 갇히는 제출도 없다(S4).

### 3.1 `autopilot_state` — 한 줄짜리 설정·상태 표

| 열 | 쓰는 쪽 | 뜻 |
|---|---|---|
| `id` | — | 항상 1 |
| `enabled` | 관리자 페이지 | 자동화 스위치. **기본값 `false`.** 배포 직후 저절로 켜지지 않게 한다 |

| `last_start_requested_at` | `autopilot` | 마지막 켜기 요청. 10분 기동 실패 판단에 쓴다 |
| `target_worker_id` | `autopilot` | 사설 DNS 이름에서 얻은 대상 워커 ID(§1.3). 관리자 화면이 AWS 없이 하트비트를 보여 주려고 저장한다 *(STEP4 추가)* |
| `attention_since` | `autopilot` | "대기 제출 있음 + 대상 워커 죽음"이 처음 보인 시각. 풀리면 비운다. `manual_attention`·`start_timeout`의 "이번 사건"을 구분하는 기준 *(STEP4 추가)* |

스위치를 DB에 두면 **바꾸는 즉시 다음 주기에 반영된다.** 배포나 재시작이 필요 없다(S10).

### 3.2 `autopilot_events` — 사건 기록 겸 알림 대기열

| 열 | 뜻 |
|---|---|
| `id`, `created_at` | |
| `kind` | `start_requested` / `start_failed` / `start_timeout` / `idle_stop` / `ssh_blocking` / `manual_attention` / `misconfigured` / `switch_changed` |
| `source` | `web`(autopilot·관리자) 또는 평가 서버의 워커 ID |
| `message` | 사람이 읽는 한 줄. **참가자 정보와 비밀값을 넣지 않는다**(대기 건수·시각 정도) |
| `notified_at` | 디스코드로 보낸 시각. 비어 있으면 `autopilot`이 다음 주기에 보낸다 |

- **알림을 바로 보내지 않고 표에 먼저 적는 이유**: 평가 서버는 웹훅 주소를 모른다. 그리고 디스코드가
  잠깐 안 되더라도 다음 주기에 다시 보낼 수 있다.
- **중복 방지(S5)**는 이 표로 판단한다. 예: `start_timeout`은 마지막 `start_requested` 뒤에 이미
  있으면 다시 만들지 않는다.
- 관리자 페이지가 최근 기록(예: 20건)을 이 표에서 보여 준다.
- 오래된 행은 쌓여도 작다(하루 수십 줄). 정리는 이번 범위에 넣지 않는다.

## 5. 설정과 비밀값

### 5.1 웹 서버 `.env`에 추가하는 키

| 키 | 예 | 비밀값? | 넘기는 서비스 |
|---|---|---|---|
| `AUTOPILOT_INSTANCE_ID` | `i-0abc...` | 아니다 | `autopilot`, `web`(설정 여부 표시용) |
| `AUTOPILOT_REGION` | `ap-northeast-2` (기본값) | 아니다 | `autopilot` |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | 켜기 전용 IAM 사용자의 키 | **예** | **`autopilot`만** |
| `DISCORD_WEBHOOK_URL` | `https://discord.com/api/webhooks/...` | **예** | **`autopilot`만** |

- 값이 없으면 `autopilot`은 아무 일도 하지 않고 로그만 남긴다. 기존 배포가 깨지지 않는다.
- CLAUDE.md §2: `.env`는 tar 전송에서 빠지므로 **서버 `.env`를 먼저 고친 뒤** 배포한다.
- CLAUDE.md §4-1의 커밋 전 비밀값 검사 목록에 `DISCORD_WEBHOOK_URL=` 뒤의 실제 값과 `discord.com/api/webhooks/` 패턴을 추가한다.
- `.env.example`에 자리표시로 추가한다.
- 시간 값(10분, 30분, 60분)은 명세서 확정값이라 코드 기본값으로 두고 `.env`로 덮어쓸 수 있게만 한다(`DAILY_SUBMISSION_LIMIT`와 같은 방식).

### 5.2 평가 서버 `.env`

**추가하는 키가 없다.** `autostop.py`는 기존 `DATABASE_URL`만 쓴다. 유휴 시간을 바꿀 때를 위해
`AUTOSTOP_IDLE_MINUTES`를 선택값으로 읽게만 한다.

### 5.3 IAM — "그 인스턴스를 켜는 것"만

Lightsail에는 IAM 역할을 붙일 수 없어서 **IAM 사용자의 액세스 키**를 쓴다. 권한은 다음으로 좁힌다.

| 권한 | 대상 | 이유 |
|---|---|---|
| `ec2:StartInstances` | **대상 인스턴스 ARN 하나** | 명세서 §3.1의 유일한 쓰기 권한 |
| `ec2:DescribeInstances` | `*` | 상태 조회. 이 API는 대상을 좁힐 수 없다. 읽기 전용이다 |
| `ec2:DescribeInstanceAttribute` | 대상 인스턴스 | §1.4의 "종료 시 동작" 점검 |

- **2026-10-04 실제로 만들었다**(사용자 `drleader-autopilot`, 인라인 정책 `autopilot-start-eval-server`,
  액세스 키는 아직 발급하지 않음). 처음에는 정책 ARN의 리전을 `ap-nortease-2`로 잘못 적었다. 그래서
  정책 시뮬레이터에서 `StartInstances`만 거부되고(`DescribeInstances`는 `*`라 통과) 오타가 드러났다.
  ARN 한 줄로 좁힌 권한은 한 글자만 틀려도 조용히 거부되니, **키를 쓰기 전에 시뮬레이터 확인을 꼭 거친다.**
- `DescribeInstanceAttribute`가 대상 인스턴스 ARN으로 좁혀지는지는 STEP4에서 AWS 문서(Service
  Authorization Reference)와 IAM 정책 시뮬레이터로 확인한다. 좁혀지지 않으면 `*`로 둔다(읽기 전용).
- 끄기, 만들기, 지우기, 다른 서비스 권한은 **주지 않는다.** 키가 새도 최악의 결과는 "그 서버가 켜져서 요금이 나간다"이다.
- **root 계정의 키는 절대 쓰지 않는다.** 콘솔 작업도 가능하면 별도 IAM 사용자로 옮기는 것이 좋다(2026-10-04 CloudTrail 확인 때 root 사용을 확인함).
- IAM 사용자 생성과 정책 등록은 운영자가 콘솔에서 한다. STEP4에서 문서에 단계별로 싣는다.
- 키가 샜다고 의심되면: IAM에서 키 비활성화 → 새 키 발급 → 서버 `.env` 교체 → `up -d`.

## 6. 배포 순서

**스위치 기본값이 꺼짐이라 1~5 동안은 아무것도 자동으로 움직이지 않는다.** 6에서 처음 켠다.

1. **평가 서버**: "종료 시 동작"이 **중지**인지 확인하고, 실제로 한 번 시험한다
   - 콘솔: 인스턴스 → 작업 → 인스턴스 설정 → **종료 시 동작 변경**에서 `중지`인지 본다
   - **AMI부터 떠 둔다**(§8.5). 시험이 잘못되더라도 돌아갈 곳이 있어야 한다
   - 평가가 없을 때 서버 안에서 `sudo poweroff`를 한 번 실행한다. 콘솔에서 상태가 `stopped`가 되고
     상태 전환 사유가 `Client.InstanceInitiatedShutdown`인지 확인한다. 다시 켜서 워커가 저절로 살아나는지도 본다
2. **AWS 콘솔**: 켜기 전용 IAM 사용자·정책을 만들고 액세스 키를 발급한다
3. **디스코드**: 운영 채널에 웹훅을 만든다
4. **웹 서버**: `.env`에 §5.1 키를 넣고 → tar 배포 → `up -d --build`([server-access.md](../../docs/server-access.md) §5).
   `docker compose logs autopilot`으로 기동 로그를 확인한다. 디스코드로 시험 알림 1건을 보낸다
5. **평가 서버**: `git pull` → 타이머 유닛 2개 등록 → `systemctl list-timers`로 확인
6. **관리자 페이지**에서 스위치를 켜고 S1~S10을 차례로 확인한다(STEP3에서 확인 절차를 작업으로 쪼갠다)

**되돌리기**: 관리자 페이지에서 스위치를 끄면 즉시 멈춘다. 코드를 되돌리지 않아도 된다.

## 9. 확정된 결정 사항

| 항목 | 결정 |
|---|---|
| 켜기 주체 | 웹 서버의 `autopilot` 컨테이너(compose 새 서비스, `web`과 같은 이미지) |
| 끄기 주체 | 평가 서버 안의 systemd 타이머 + `poweroff`. 평가 서버에 AWS 키를 두지 않는다 |
| 알림 경로 | 모든 알림은 DB 이벤트 표를 거쳐 `autopilot`이 보낸다. 웹훅 주소는 웹 서버에만 있다 |
| 판단 주기 | 웹·평가 서버 모두 1분 |
| 스위치 저장 | DB 한 줄 표. 기본값 꺼짐 |
| 대상 워커 식별 | 인스턴스 ID → 사설 DNS 이름 → 워커 ID(자동) |

| P1 — AWS 키 위치 | 웹 서버(Lightsail) `.env`에 **켜기 전용 IAM 사용자의 액세스 키**를 둔다. `autopilot`에만 넘긴다. Lightsail에는 IAM 역할을 붙일 수 없고, 무료이면서 단순한 다른 방법이 없다 |
| P2 — 스위치 꺼짐 알림 | 보낸다. 대기 제출이 있는데 대상 워커가 10분 넘게 살아 있지 않으면 `manual_attention`을 한 번 보낸다. 스위치를 끈 채 서버 켜는 것을 잊은 경우를 잡는다 |
| P3 — 정상 기동 알림 | 보내지 않는다. 알림이 많아지면 중요한 알림을 놓친다. 관리자 페이지에서 볼 수 있다 |

## 10. STEP4 구현 중 정한 것 (2026-10-04)

tasks.md T4·T23에 따라 구현하면서 정하거나 계획과 다르게 한 것을 남긴다.

| 항목 | 결정 | 이유 |
|---|---|---|
| `manual_attention`의 "이번 사건" | 상태 표에 `attention_since` 열을 두고 기억한다(§3.1). 그 시각 이후에 같은 알림이 있으면 다시 만들지 않는다 | 이벤트 표만으로 판단하려면 "워커가 살아난 시각"을 따로 찾아야 해서 복잡하다. 열 하나가 가장 단순하다 |
| `start_timeout`의 기준 | 이번 사건 안에서 켜기 요청을 했으면 그 시각, 아니면 **사건이 시작된 시각**부터 10분 | §1.2 표는 "켜기 요청 후 10분"만 다룬다. 그런데 서버가 켜져 있는데 워커만 죽은 경우(사람이 켰거나 워커가 멈춤)에는 켜기 요청이 없어 **아무도 알리지 않는다.** 평가 서버는 대기열이 있으니 끄지도 않는다. 사람이 봐야 하는 같은 상황이라 같은 알림으로 잡는다 |
| EC2 조회 실패, 인스턴스 `terminated`/`shutting-down` | `start_failed`로 알린다(30분에 1번) | 켤 수 없는 상황이라 켜기 실패와 대응이 같다 |
| 켜기 실패 알림 문구 | AWS 오류 **코드만** 싣는다(`UnauthorizedOperation` 등) | AWS 오류 원문에는 계정 ID와 IAM 사용자 ARN이 들어 있다. 디스코드 채널에 그대로 올리지 않는다 |
| 평가 서버 SSH 접속 중 유휴 시간 | 유휴 기록을 **지운다.** 접속을 끊은 뒤 30분을 새로 센다 | 그대로 세면 작업을 마치고 접속을 끊는 순간(또는 잠깐 끊었다 다시 붙는 사이) 서버가 꺼진다. 30분 더 켜지는 비용(약 $0.12)보다 작업 중 꺼지는 위험이 크다 |
| SSH 접속 감지 | `who`와 `ss`(22번 포트 연결) **둘 다** 본다 | VS Code 원격 접속·scp처럼 터미널을 열지 않는 접속은 `who`에 보이지 않는다 |
| 끄기 중간 실패 | 워커 중지 실패 → 끄지 않는다. 제출 되돌리기 실패 → 워커를 다시 올리고 끄지 않는다 | 되돌리지 못한 채 끄면 제출이 `평가중`에 갇히고, 대기열이 비어 보여 아무도 서버를 다시 켜지 않는다(S4) |
| 판단 불확실 | DB 불통·docker 조회 실패면 끄지 않는다 | 켜져 있는 손해는 요금이고, 잘못 꺼서 생기는 손해는 평가 중단이다 |
| "종료 시 동작" 확인 실패 | 권한 부족 등으로 확인하지 못해도 `misconfigured`를 남긴다 | 확인하지 못한 채 조용히 넘어가면 이 안전장치가 있는 줄 알고 믿게 된다 |
| 늦게 설정한 웹훅 | 24시간 안의 미발송 알림만 보낸다. 한 주기 최대 10건 | 지난 일이 한꺼번에 쏟아져 지금 중요한 알림이 묻히지 않게 한다. 지난 기록은 관리자 화면에 있다 |
| 판단 함수의 출력 형태 | 행동 목록 대신 "새 상태 + 할 일" 데이터클래스(`Decision`, `AutostopDecision`) | 테스트가 상태 전이를 그대로 비교할 수 있다. 의미는 tasks.md의 행동 목록과 같다 |
