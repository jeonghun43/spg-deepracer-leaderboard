# STEP 1 — 명세서: 가상 트랙 기반 자동 평가 플랫폼

> 이 문서는 "무엇을, 왜 만드는가"에 집중한다. dr-start-evaluation 호출 방식, DB 스키마, 큐 구현 등 기술적 결정은 STEP2(기술 계획)에서 다룬다.

## 1. 개요

참가팀이 각자 학습(training)한 DeepRacer 모델 파일을 사이트에 제출하면, 운영 서버가 로컬에서 DRFC의 `dr-start-evaluation`을 실행해 자동으로 채점하고, 그 결과(랩타임·완주 여부·영상)를 리더보드에 반영하는 서비스.

## 2. 배경 / 왜 만드는가

- AWS DeepRacer 콘솔의 공식 대회 운영 방식을 쓰려면 참가자(또는 운영자)가 결제 이력이 있는 AWS 계정을 보유해야 하고, 학습·평가에 드는 비용을 사전에 정확히 예측할 수 없다. 소규모·교육 목적 대회에는 이 진입장벽과 비용 리스크가 크다.
- DRFC를 쓰면 학습부터 평가까지 로컬에서 재현 가능하다. 이 서비스는 그중 **평가(evaluation)** 를 운영자의 로컬 서버가 참가자 대신 실행해주는 대행 구조를 만들어, 참가자는 결제 계정 없이도 대회에 참가할 수 있고 운영자는 비용을 서버 한 대 수준으로 통제할 수 있다.
- 참가자는 모델 학습은 각자의 환경(개인 PC, 별도 인프라 등)에서 진행한다. 이 서비스가 다루는 참가자 경험은 "제출 → 평가 → 결과 확인 → 순위 경쟁"이다.

## 3. 페르소나

| 페르소나 | 설명 |
|---|---|
| **참가팀원 (Racer)** | 모델을 학습해 온 팀의 구성원. DeepRacer/강화학습 지식은 있지만 서버 운영 지식은 없다고 가정한다. |
| **대회 운영자 (Admin)** | 대회를 기획·운영하며 서버도 관리한다. 다수 팀의 제출을 감당하면서 공정성을 지켜야 한다. |
| **관전자 (Public Viewer)** | 계정 없이 링크로 접속하는 누구나. 순위·기록·영상만 본다. |

## 4. 사용자 여정

### 4.1 대회 운영자
1. 새 시즌/대회를 만든다 (대회명, 기간, 사용할 트랙, 예선 마감 시점 등).
2. 참가팀을 사전 등록한다 — 팀명, 팀원 정보, 접속 계정을 만들어 배포한다.
3. 대회를 오픈하고 참가팀에게 접속 정보를 안내한다.
4. 제출된 모델들이 쌓이는 평가 대기열을 모니터링한다.
5. 평가가 실패하거나 오류(모델 파일 손상, 형식 오류 등)가 나면 확인하고 필요 시 재시도/제외 처리한다.
6. 예선 마감 시점에 리더보드 기준으로 순위를 확정한다.
7. 상위 N팀을 "본선(오프라인) 진출팀"으로 확정해 공개한다.
8. 필요 시 특정 제출·팀을 부정 제출 등의 사유로 실격 처리한다. 실격된 제출/팀은 리더보드에서 조용히 사라지며, 사유는 별도로 공개 표시하지 않는다.

### 4.2 참가팀원
1. 안내받은 계정으로 로그인한다.
2. 참가 중인 대회 화면에서 트랙 정보, 제출 마감일, 제출 규칙(허용 파일 형식 등)을 확인한다.
3. 학습을 마친 모델 파일을 업로드해 제출한다. (하루 최대 5회까지 제출 가능하며, 제출 후에는 취소할 수 없다.)
4. 제출 직후 "대기 중" 상태와 대기열 내 자신의 순서(또는 예상 대기 시간)를 확인한다. **이 제출이 결과(완료 또는 오류)로 끝나기 전까지는 새 모델을 추가로 업로드할 수 없다** — 한 팀이 서버에 동시에 올려둘 수 있는 모델은 항상 최대 1개다.
5. 평가가 완료되어도 별도 알림은 오지 않으며, 참가자가 페이지를 새로고침해 결과(완주 여부, 랩타임, 트랙 이탈 여부 등)를 직접 확인한다.
6. 이번 기록이 팀의 기존 최고기록보다 좋으면 리더보드가 갱신된 것을 본다. (리더보드에는 항상 최고기록만 표시되며, 과거 제출 이력을 별도로 보여주는 기능은 없다.)
7. 결과가 나오면(완료든 오류든) 비로소 다시 새 모델을 업로드할 수 있다. 마감 전까지, 그리고 하루 제출 한도(5회) 내에서 이렇게 재도전(재제출)할 수 있다.
8. 리더보드에서 자기 팀 순위와 다른 팀의 기록·영상을 언제든 볼 수 있다.

### 4.3 관전자
1. 공개 링크로 접속한다 (로그인 불필요).
2. 시즌/대회를 선택한다.
3. 팀별 순위표(최고기록 기준)를 본다.
4. 관심 있는 팀의 최고기록 평가 영상을 재생한다.

## 5. 핵심 시나리오 & 예외 상황

- **미완주 처리**: 모델이 트랙을 완주하지 못했을 때 순위 산정에서 어떻게 다뤄지는지 참가자가 명확히 알 수 있어야 한다 (예: 완주율 표시, 미완주는 순위표 하단 배치 또는 별도 표시).
- **재제출과 제출 한도**: 여러 번 제출해도 리더보드에는 항상 "최고기록"만 남는다. 팀당 하루 최대 5회까지 제출할 수 있고, 제출 후 취소는 불가능하다. 과거 제출 이력을 보여주는 기능은 이번 범위에 포함하지 않는다. 또한 한 팀은 동시에 하나의 제출만 진행할 수 있다 — 이전 제출의 결과가 나오기 전까지는 새 모델을 올릴 수 없다.
- **대기열 체감**: 서버 한 대가 순차적으로 평가를 처리하므로, 참가자는 "내 앞에 몇 건 남았는지 / 대략 언제 결과가 나오는지"를 알 수 있어야 불안해하지 않는다.
- **동점 처리**: 랩타임이 완전히 같은 두 팀의 순위를 정하는 규칙이 필요하다 (예: 먼저 제출한 팀 우선 등).
- **평가 오류 vs 미완주**: 업로드 파일 자체가 잘못됐거나 시스템(DRFC) 실행이 비정상 종료된 "오류"는 하루 제출 한도에서 제외된다. 반면 모델이 정상적으로 평가는 받았지만 3바퀴를 다 돌지 못해 시간 초과로 끝난 "미완주"는 정상적으로 평가가 완료된 것이므로 한도에 포함된다. 참가자가 이 둘의 차이를 결과 화면에서 명확히 구분해서 볼 수 있어야 한다.
- **부정 제출 대응**: 운영자가 특정 제출/팀을 대회에서 제외(실격)할 수 있는 수단이 있어야 하며, 실격 시 해당 제출/팀은 리더보드에서 조용히 사라지고 사유는 표시되지 않는다.
- **일일 한도 초과**: 하루 5회를 모두 소진한 팀이 사이트에서 이를 명확히 인지할 수 있어야 한다 (예: 제출 버튼 비활성화 + 남은 횟수 표시).

## 6. 성공 기준

- 참가팀이 운영자의 개입 없이 "제출 → 결과 확인 → 리더보드 반영"까지 스스로 완결할 수 있다.
- 리더보드는 항상 각 팀의 "최고기록"만 보여주며, 새 최고기록이 나오면 곧바로(또는 짧은 지연 내) 순위에 반영된다.
- 운영자는 AWS 결제 계정 없이, 예측 가능한 비용(로컬 서버 운영비 수준)으로 대회를 운영할 수 있다.
- 관전자가 별도 계정 없이 순위와 영상을 열람할 수 있다.
- 지난 시즌/대회의 기록도 나중에 다시 조회할 수 있다.

## 7. 범위 밖 (Out of Scope)

- 모델 학습(training) 자체 — 참가자가 각자 환경에서 수행한다.
- 오프라인 실물 대회 진행 — [002-offline-vision-timer](../002-offline-vision-timer/spec.md) 참고.
- 결제·스폰서십 관리.
- 참가자 자율 회원가입 (사전 등록 방식으로 확정됨).

## 8. 확정된 결정 사항 (이번 논의 기준)

- 팀은 관리자가 사전 등록한다 (참가자 자율 가입 아님).
- 리더보드·기록·영상은 완전 공개다 (로그인 불필요).
- 대회는 시즌 개념으로 반복 운영되며, 과거 시즌도 조회 가능해야 한다.
- 온라인 평가는 오프라인 본선 진출자를 가리는 "예선" 역할을 겸한다. 물리 차량이 10대뿐이므로, 예선 통과팀 수가 이를 초과하면 상위팀 순으로 본선 참가 방식이 달라진다 (자세한 내용은 002 spec). 우선은 "상위 N팀이 본선에 진출한다"는 원칙만 확정되었고, N을 정하는 구체 규칙은 추가 논의가 필요하다.
- 팀당 하루 최대 **5회**까지 제출할 수 있다.
- 리더보드에는 팀별 **최고기록만** 표시되며, 과거 제출 이력을 보여주는 기능은 두지 않는다.
- 트랙은 **대회당 1개로 고정**된다.
- 평가 완료에 대한 별도 알림은 없다 — 참가자가 직접 페이지를 새로고침해 확인한다.
- 제출은 **취소할 수 없다**.
- 실격/부정 제출로 처리된 제출·팀은 리더보드에서 **조용히 사라지며 사유는 표시하지 않는다**.
- 온라인 평가 주행은 **3바퀴** 기준으로 진행한다 (참고: 오프라인 본선은 2바퀴로 별도 운영 — 002 spec).
- 하루 제출 한도(5회)는 "완주 성공 여부"가 아니라 "평가가 끝까지 실행됐는지"로 카운트한다. 모델이 정상적으로 업로드·실행되어 평가가 끝까지 돌아갔다면 완주했든 시간 초과로 미완주했든 모두 카운트된다. 업로드 자체가 잘못됐거나(파일 손상·형식 오류) DRFC 실행이 인프라 문제로 비정상 종료된 경우만 카운트에서 제외된다.
- 시즌은 매번 완전히 새로 열리며, 팀도 시즌마다 새로 등록한다(지난 시즌 팀을 이어받지 않음). 시즌이 끝나면 리더보드에 노출되는 내용(팀명·최고기록·영상)만 영구 보존하고, 계정 등 더 이상 필요 없는 정보는 삭제해 저장 공간을 아낀다.
- 한 팀은 동시에 "대기" 또는 "평가중" 상태의 제출을 1건만 가질 수 있다. 새 모델은 자기 팀의 이전 제출이 완료(기록 확정)되거나 오류(업로드 실패 등)로 끝나 서버에 자기 모델이 전혀 올라가 있지 않은 상태에서만 업로드할 수 있다.
- 공개 리더보드에는 팀명, (전체 누적) 제출 횟수, 최고기록, 최고기록 영상 링크가 표시된다. 참가자 본인만을 위한 별도의 "내 제출 이력" 페이지는 두지 않는다 — 필요한 정보는 리더보드 자체에 이미 포함된다.
- 관리자는 테스트·운영 편의를 위해 특정 팀의 "오늘 완료된 제출 횟수"를 수동으로 조정할 수 있다.
- 참가팀·관전자는 운영자와 **같은 LAN에 있지 않아도** 인터넷을 통해 리더보드/제출 화면에 접속할
  수 있어야 한다 (2026-07-25 결정). 노출 방법은 [deployment-public-access.md](deployment-public-access.md)
  참고 — 평가 실행(DRFC)은 여전히 운영자의 로컬 컴퓨터에서만 이뤄지므로, 이 결정은 "웹 화면
  접근성"에 대한 것이고 평가 인프라 자체를 옮기는 것은 아니다.

## 9. 열린 질문 (STEP3 전 확인 필요)

- [ ] 예선 통과 기준(N팀)을 정하는 구체적인 규칙 — "상위 N팀 진출" 원칙은 정해졌으나, N을 어떻게 산정할지(고정값 / 참가 규모에 따른 유동값 등)는 002(오프라인 서비스, 온라인 구현 이후로 순연)와 함께 추가 논의가 필요하다.
