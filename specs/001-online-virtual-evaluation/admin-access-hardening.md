# 관리자 접근 은닉 — 분석과 설계 (2026-08-03)

> 관리자 로그인 화면을 **공개 인터넷에서 보이지 않게** 하고, 관리자는 사전에 공유받은
> 비밀 경로로만 들어오게 한다. 여기에 무차별 대입 방어를 2차 방어선으로 얹는다.
>

## 1. 지금 무엇이 문제인가

서비스가 `https://spg-deepracer.doublejeong.com`으로 공개된 뒤, 관리자 진입점이 그대로 노출돼 있다.

| # | 문제 | 근거 |
|---|---|---|
| 1-1 | **모든 페이지 상단 메뉴에 "관리자" 링크가 있다** | `app/templates/base.html:15` — 리더보드를 구경하러 온 누구나 클릭 한 번으로 로그인 폼에 도달한다 |
| 1-2 | 로그인 폼 경로가 **누구나 짐작할 수 있는 `/admin/login`** | `app/routers/admin.py:46` |
| 1-3 | 미인증 상태로 `/admin`에 가면 **303 리다이렉트로 "여기 관리자 페이지가 있다"고 알려준다** | `app/deps.py:29` — 404였다면 존재 자체를 몰랐을 것 |
| 1-4 | 로그인 시도 횟수에 **아무 제한이 없다** | `admin.py:53` — 비밀번호를 무한정 대입할 수 있다 |
| 1-5 | 관리자 계정은 **하나뿐이고 시드로 만든 초기 비밀번호를 계속 쓰기 쉽다** | `app/seed.py` |

1-1~1-3이 겹치면 결과는 이렇다. **대회 참가자(고등학생·대학생)가 리더보드를 보다가 호기심에
"관리자" 링크를 누르고, 아이디를 몇 개 찍어본다.** 실제 침해까지 가지 않더라도, 진입점이
눈에 보인다는 것 자체가 시도를 유발한다. 공격은 "가능해서" 일어나는 게 아니라 "보여서" 일어난다.

### 왜 지금까지는 괜찮았나

이전에는 서비스가 LAN 안에서만 돌거나 임시 터널 주소로만 열려 있었다. 주소를 아는 사람이
곧 신뢰할 수 있는 사람이었다. 고정 도메인으로 상시 공개된 지금은 그 전제가 깨졌다.

## 2. 방향 결정

### 2.1 고른 방식 — 비밀 경로 + 무차별 대입 방어

`.env`의 `ADMIN_LOGIN_PATH`에 넣은 **추측 불가능한 경로에서만** 로그인 폼이 열린다.
그 외 `/admin` 이하 모든 경로는 미인증 상태에서 **404**를 돌려준다.

### 2.2 검토했으나 고르지 않은 것

| 대안 | 왜 안 골랐나 |
|---|---|
| **Tailscale/IP 허용목록** (Caddy에서 `/admin/*` 차단) | 보안은 가장 강하다. 그러나 관리자 PC에 Tailscale이 깔려 있어야만 접속되고, 대회 현장에서 휴대폰이나 빌린 노트북으로 급히 들어가야 할 때 방법이 없다. **매년 회장이 바뀌는 동아리**라는 조건에서 인수인계 난이도도 크게 올라간다 |
| **둘 다 적용** | 위 단점을 그대로 안는다. 장애 시 "경로가 틀린 건가 IP가 막힌 건가" 원인 파악도 복잡해진다 |
| **메뉴 링크만 제거** | `/admin/login`을 주소창에 치면 그대로 폼이 나온다. 1-2·1-3·1-4가 하나도 해결되지 않는다 |
| **관리자 계정에 2단계 인증(TOTP)** | 방어력은 높지만 관리자가 인증 앱을 잃어버리면 복구 절차가 필요하고, 그 절차를 만드는 것이 이번 작업보다 크다. 비밀 경로로 진입 자체가 막히면 실익이 적다 |

### 2.3 이 방식의 한계 — 솔직하게

**비밀 경로는 "숨기기"이지 "인증"이 아니다.** 다음 경우엔 뚫린다.

- 관리자가 공용 PC 브라우저 히스토리에 주소를 남기고 나감
- 관리자가 카카오톡 등으로 경로를 공유했다가 대화방이 유출됨
- Caddy 접근 로그(`/data/access.log`)를 볼 수 있는 사람 — **경로가 로그에 그대로 남는다**

그래서 **비밀번호가 진짜 방어선이고, 비밀 경로는 "시도조차 못 하게 하는" 앞단**이다.
1-4(무차별 대입 방어)를 함께 넣는 이유가 여기 있다. 경로가 유출돼도 비밀번호를 찍어볼 수 없다.

## 3. 설계

### 3.1 경로 구성

```
[변경 전]
  GET  /admin/login    로그인 폼      ← 누구나 접근
  POST /admin/login    로그인 처리
  GET  /admin/logout   로그아웃
  GET  /admin          대시보드       ← 미인증 시 303 → /admin/login
  GET  /admin/...      기타 관리 기능

[변경 후]
  GET  {ADMIN_LOGIN_PATH}    로그인 폼      ← 경로를 아는 사람만
  POST {ADMIN_LOGIN_PATH}    로그인 처리    ← 잠금 대상
  GET  /admin/logout         로그아웃       ← 인증된 세션만 의미 있음
  GET  /admin                대시보드       ← 미인증 시 404
  GET  /admin/...            기타 관리 기능 ← 미인증 시 404
  GET  /admin/login          **존재하지 않음** → 404
```

`ADMIN_LOGIN_PATH` 예시: `/_ops/k7f3q9x2p1`

- `/admin` 아래에 두지 **않는다**. `/admin/*`를 통째로 404로 만들 때 예외를 파지 않아도 되고,
  나중에 Caddy에서 `/admin/*`를 차단하는 선택지를 열어둔다.
- 로그인 라우트만 `prefix` 없는 별도 라우터에 등록하고, 나머지 관리 기능은 기존 `/admin` prefix 유지.

### 3.2 왜 리다이렉트가 아니라 404인가

미인증 요청에 `303 → 로그인 페이지`를 주면 **"이 경로에 뭔가 있다"는 사실이 확인된다.**
404를 주면 존재하지 않는 아무 경로(`/asdf`)와 응답이 구별되지 않는다.

**부작용: 관리자 세션이 만료된 뒤 `/admin`에 가면 로그인 화면이 아니라 404를 본다.**
이건 버그가 아니라 의도다. 관리자는 비밀 경로를 북마크해 두고 거기로 다시 들어와야 한다.
→ [handover.md](../../docs/handover.md)에 명시한다.

### 3.3 설정값 — `.env`

| 키 | 기본값 | 설명 |
|---|---|---|
| `ADMIN_LOGIN_PATH` | `/admin/login` | 관리자 로그인 폼 경로. **운영 서버에서는 반드시 무작위 값으로 바꾼다** |
| `ADMIN_LOGIN_MAX_ATTEMPTS` | `5` | 잠금까지 허용할 연속 실패 횟수 |
| `ADMIN_LOGIN_LOCKOUT_MINUTES` | `15` | 잠금 유지 시간(분) |

**기본값을 `/admin/login`으로 두는 이유**: 로컬 개발·테스트에서 매번 설정하지 않아도 되게 한다.
대신 **`docker-compose.prod.yml`에서 필수로 강제한다** — `${ADMIN_LOGIN_PATH:?...}` 형태로,
값이 없으면 컨테이너가 아예 뜨지 않는다. `SESSION_SECRET`·`POSTGRES_PASSWORD`와 같은 기존 패턴이다.

**경로 정규화**: 사람이 `.env`에 손으로 넣는 값이라 실수를 흡수한다.
- 앞에 `/`가 없으면 붙인다 (`_ops/abc` → `/_ops/abc`)
- 뒤의 `/`는 뗀다 (`/_ops/abc/` → `/_ops/abc`)
- 빈 문자열이면 기본값으로 되돌린다 (설정 실수로 `@app.get("")`이 되는 것을 막는다)

### 3.4 무차별 대입 방어

**IP 기준과 계정 기준을 둘 다 센다.**

| 기준 | 왜 필요한가 |
|---|---|
| IP | 한 곳에서 반복 시도하는 가장 흔한 형태를 막는다 |
| 로그인 아이디 | **IP는 위조할 수 있다.** 우리 앱은 Caddy 뒤에 있어 클라이언트 IP를 `X-Forwarded-For` 헤더에서 읽는데, 이 헤더는 요청자가 임의로 넣을 수 있다. 헤더를 바꿔가며 IP 잠금을 우회해도 계정 잠금에 걸린다 |

**동작**
- 실패할 때마다 두 카운터를 각각 +1. 어느 한쪽이라도 상한에 닿으면 잠근다.
- 로그인 **성공하면 두 카운터를 모두 지운다**.
- 잠긴 동안의 요청은 **비밀번호를 검사하지 않고** `429`와 함께 남은 시간을 안내한다.

**저장 위치: 프로세스 메모리**
- 운영 웹은 컨테이너 1개 · uvicorn 워커 1개로 돈다(`Dockerfile`의 `CMD`에 `--workers` 없음). 공유 저장소가 필요 없다.
- **재시작하면 카운터가 초기화된다.** 공격자가 우리 컨테이너를 재시작시킬 수단이 없으므로 허용 가능한 절충이다.
- 오히려 이게 **운영자의 탈출구**가 된다. 관리자가 자기 계정을 잠갔을 때 `docker compose restart web`으로 즉시 푼다. → [operations.md](../../docs/operations.md)에 적는다.
- 메모리 누수 방지: 항목을 넣을 때마다 만료된 항목을 함께 정리한다(항목 수가 수십 개 수준이라 별도 청소 스레드가 필요 없다).

**계정 잠금의 역설(DoS)**: 남이 일부러 실패시켜 관리자를 잠글 수 있다. 그러나 **비밀 경로를
모르면 POST 자체가 불가능**하고, 잠금은 15분이며 재시작으로 즉시 풀린다. 감수한다.

**하지 않는 것**: 존재하지 않는 아이디에도 bcrypt를 돌려 응답 시간을 맞추는 타이밍 공격 방어.
아이디 존재 여부가 새는 것은 인정하되, 비밀 경로 뒤라 실익이 없다.

### 3.5 메뉴(nav) 처리

`base.html`의 "관리자" 링크는 **관리자로 로그인한 세션에서만** 보인다.

```jinja
{% if request.session.get('admin_id') %}<a href="/admin">관리자</a>{% endif %}
```

- 관전자·참가자에게는 존재 자체가 보이지 않는다.
- 관리자는 로그인 후 매번 주소를 치지 않아도 된다(진입만 비밀 경로, 이후는 `/admin`).
- 세션을 갖고 있는 본인에게만 보이므로 정보 노출이 아니다.

### 3.6 로그인 화면 자체

- 폼 `action`을 `/admin/login` 하드코딩에서 **`{{ admin_login_path }}` 렌더**로 바꾼다.
- 로그아웃 후에는 비밀 경로가 아니라 **`/leaderboard`로 보낸다**. 비밀 경로를 화면에
  다시 띄우지 않고, 관리자가 아닌 사람이 그 화면을 보게 될 여지를 줄인다.
- 실패 메시지는 지금처럼 아이디/비밀번호를 구분하지 않는다("아이디 또는 비밀번호가 올바르지 않습니다").

### 3.7 접근 로그 주의

Caddy 접근 로그에 비밀 경로가 평문으로 남는다(`/data/access.log`). 서버에 SSH로 들어올 수 있는
사람은 이미 DB도 볼 수 있으므로 **새로 생기는 위험은 아니지만**, 로그를 외부에 공유하거나
캡처를 올릴 때는 경로를 가려야 한다. → [server-access.md](../../docs/server-access.md)에 주의 문구를 넣는다.

## 4. 범위 밖

- 2단계 인증(TOTP), 관리자 계정 다중화, 비밀번호 정책 강제
- IP 허용목록 / Caddy 레벨 차단 (§2.2에서 기각)
- 관리자 활동 감사 로그(누가 언제 무엇을 바꿨는지)
- 참가팀 로그인(`/login`)의 무차별 대입 방어 — **이번 범위 밖**이다. 팀 계정은 권한이 낮고
  (자기 팀 제출만 가능), 계정 잠금이 대회 중 참가자 민원으로 직결된다. 필요해지면 별도 Phase.

## 6. 배포 후 확인할 것

1. 서버 `.env`에 `ADMIN_LOGIN_PATH`를 넣었는가 — **넣지 않으면 `web` 컨테이너가 뜨지 않는다**
2. 새 경로로 로그인해 대시보드가 열리는가
3. `/admin/login`이 404인가
4. 관리자 비밀번호를 기본값에서 바꿨는가 (§1-5 — 이번 코드 변경과 별개인 운영 과제)
5. 비밀 경로를 다음 회장에게 어떻게 전달할지 정했는가 (인수인계 문서에 경로를 적어두지 말고,
   `.env`를 보라고만 적는다)
