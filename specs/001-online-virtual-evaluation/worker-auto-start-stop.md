## 1. 왜 만드는가

### 1.1 지금 상황

평가 서버(EC2)는 **스팟 → 온디맨드 → 다시 스팟**을 오가며 운영해 왔다. 두 방식 모두 문제가 있다.

| 방식 | 문제 | 실제로 겪은 일 |
|---|---|---|
| **스팟** | AWS가 언제든 회수한다. 서울 리전의 4vCPU/16GB 계열 스팟 배치 점수는 1~3점(10점 만점)이다(2026-09-30 조회) | 지난 대회 마지막 며칠에 회수가 반복돼 결국 온디맨드로 갈아탔다. 2026-10-01에는 만든 지 몇 시간 만에 회수(`BidEvictedEvent`)돼, 일회성·종료 기본값 탓에 디스크째 사라졌다 |
| **온디맨드 24시간** | 회수는 없지만 비싸다. m7i.xlarge 서울 시간당 $0.2478 → **2주 약 $89(약 12.8만 원)** | — |

그런데 평가 서버는 **대부분의 시간을 놀고 있다.** 평가 1건이 약 8분이고, 제출은 하루 종일 고르게
오지 않는다. 켜져 있는 시간의 대부분이 대기열이 빈 채로 요금만 나가는 시간이다.

### 1.2 만들려는 것

**온디맨드 서버를 평소에는 꺼 두고, 제출이 들어오면 켜고, 할 일이 없어지면 다시 끈다.**
그리고 그 과정을 운영자가 휴대폰(디스코드)으로 알 수 있게 한다.

- 온디맨드라 **회수가 없다.** 스팟의 불안정성을 피한다.
- 켜져 있는 시간만 과금되므로 **비용이 스팟에 가까워진다.** 하루 8시간 켜진다고 가정하면 2주
  인스턴스 요금이 약 $28이다(24시간 온디맨드 약 $83, 24시간 스팟 약 $23).
- 자동화 자체에는 **추가 요금이 없다**(2026-10-04 검토: 디스코드 웹훅, EC2 API 호출, IAM, 서버 내부
  스케줄러 모두 무료).

### 1.3 검토했으나 고르지 않은 것

| 대안 | 고르지 않은 이유 |
|---|---|
| 스팟 24시간 | 가장 싸지만 회수가 잦다. 회수되면 복귀할 때까지 평가가 통째로 멈춘다 |
| 온디맨드 24시간 | 안정적이지만 요금이 세 배 이상이다 |
| 알림만 받고 사람이 켜기 | 운영자가 항상 휴대폰을 보고 있을 수 없다. 밤이나 수업 중에 들어온 제출이 몇 시간씩 밀린다 |
| 스팟 + 온디맨드 예비를 함께 운영 | 같은 AMI에서 나온 두 서버는 Tailscale 신원이 같아, 동시에 켜지면 둘 다 DB에 붙지 못한다(worker-server-setup.md §8.12). 신원을 분리하는 추가 작업이 필요하다. 이번에는 **온디맨드 1대만** 쓴다 |

## 2. 사용자와 여정

### 2.1 참가자

1. 평소처럼 모델을 제출한다. **참가자가 할 일은 달라지지 않는다.**
2. 평가 서버가 꺼져 있었다면 **몇 분 안에 자동으로 켜지고** 평가가 시작된다.
3. 서버가 켜지는 동안 화면에는 "평가 서버가 재개된 뒤 순서대로 처리됩니다"(현재 문구)가 보인다.
   제출은 대기열에서 기다리며 사라지지 않는다.
4. 평가가 끝나면 지금과 똑같이 결과가 리더보드에 뜬다.

참가자가 느끼는 차이는 **"서버가 꺼져 있던 경우 첫 평가가 몇 분 늦게 시작된다"** 하나뿐이어야 한다.

### 2.2 운영자

1. 대회 기간에는 아무것도 하지 않아도 서버가 알아서 켜지고 꺼진다.
2. 디스코드 채널에서 **서버가 켜졌다 / 꺼졌다 / 뭔가 잘못됐다**를 알 수 있다.
3. 평가 서버에 SSH로 접속해 작업(코드 갱신, 설정 변경)하는 동안에는 서버가 **저절로 꺼지지 않는다.**
   운영자가 따로 표시할 필요 없이, 접속해 있다는 것 자체로 판단한다.
4. **관리자 페이지에서 자동화를 켜고 끈다.** 같은 화면에서 지금 서버가 켜져 있는지와 최근
   켜기·끄기 기록을 본다.
   - 대회가 아닌 기간: 서버를 꺼 두고 자동화를 끈다. 제출이 들어와도 켜지지 않는다.
   - 마감 직전처럼 몰릴 때: 서버를 켜 두고 자동화를 끈다. 30분 유휴 규칙으로 꺼지지 않는다.
5. 언제든 지금처럼 **콘솔에서 직접 켜고 끌 수 있다.** 자동화가 사람의 조작을 막지 않는다.

## 3. 동작 요구사항

### 3.1 자동 켜기

- **켜는 조건**: 대기 중인 제출이 있는데, **대상 EC2 서버의 워커**가 살아 있지 않을 때.
  - "살아 있다"의 기준은 지금 화면이 쓰는 기준(워커 생존 신호가 3분 안에 있었는가)과 같다.
  - **다른 기기의 워커는 판단에 넣지 않는다.** 운영자 노트북을 예비 워커로 쓰지 않기로 했기 때문이다
    (2026-10-04 결정. worker-server-setup.md §8.8의 2026-08-01 결정을 대체한다). 노트북에서 워커가
    살아 있더라도 EC2는 켠다.
- **켜는 대상**: 미리 정한 **평가 서버 인스턴스 1대만.** 새 인스턴스를 만들지 않는다.
- 이미 켜지는 중이거나 켜져 있으면 다시 켜라고 하지 않는다.
- 웹 서버가 가진 AWS 권한은 **"그 인스턴스 하나를 켜는 것"만** 할 수 있어야 한다. 권한이 새더라도
  할 수 있는 최악의 일이 "서버를 켜서 요금이 나가는 것"에 그쳐야 한다. 만들기·지우기·끄기 권한은 주지 않는다.

### 3.2 자동 끄기

- **끄는 조건**: 다음이 **30분 동안 계속** 참일 때.
  - 대기 중인 제출이 없다
  - 평가 중인 제출이 없다
  - 이 서버에서 평가 스택이 돌고 있지 않다
- 끄는 방식은 **"중지"여야 한다. 절대 "종료"가 되면 안 된다.** 종료되면 디스크째 사라진다
  (2026-10-01 사고). 서버 설정의 "종료 시 동작"이 "중지"인지가 이 기능의 전제 조건이다.
- 평가 도중에는 어떤 경우에도 끄지 않는다.
- **누군가 SSH로 접속해 있으면 끄지 않는다**(2.2의 3번).
  - 접속 창을 열어 둔 채 잊으면 서버가 계속 켜져 있게 된다. 그래서 **SSH 접속 때문에 1시간 이상
    끄지 못하고 있으면 디스코드로 알린다.**
- 관리자 페이지의 **"제출 일시중지"와는 연결하지 않는다.** 제출을 막는 것은 "새 제출을 받지 않는다"는
  뜻일 뿐 서버 작업 중이라는 뜻이 아니다. 밤새 막아 두면 서버가 밤새 켜져 요금만 나간다. 일시중지
  전에 들어온 제출은 대기·평가 중이므로 원래 규칙에 따라 끝까지 처리된다.

### 3.3 디스코드 알림

| 언제 | 왜 알아야 하나 |
|---|---|
| 자동으로 켜라고 요청했을 때 | 서버가 움직이기 시작했다는 것을 안다 |
| 켜라고 했는데 일정 시간이 지나도 워커가 살아나지 않을 때 | **가장 중요하다.** 사람이 개입해야 하는 유일한 상황이다(부팅 실패, 워커 오류, Tailscale 문제 등) |
| 켜기 요청 자체가 실패했을 때 | 권한 문제, AWS 용량 부족 등. 사람이 직접 켜야 한다 |
| 유휴로 자동으로 꺼졌을 때 | 비용이 멈췄다는 것을 안다 |
| SSH 접속 때문에 1시간 이상 끄지 못하고 있을 때 | 접속 창을 열어 둔 채 잊었을 수 있다 |

- **같은 일로 알림이 반복해서 오면 안 된다.** 한 번의 "서버 꺼짐 → 켜짐" 사건에는 알림이 한 번씩만 온다.
- 알림에는 **참가자 개인정보나 비밀값을 넣지 않는다.** 대기 건수, 시각 정도만 넣는다.
- 디스코드 웹훅 주소는 비밀값으로 다룬다. 알면 누구나 그 채널에 글을 쓸 수 있기 때문이다.

### 3.4 켜고 끄는 스위치 — 관리자 페이지

- 관리자 페이지에 **"평가 서버 자동화: 켜짐 / 꺼짐"** 스위치를 둔다.
- **"꺼짐"은 "사람이 직접 관리한다"는 뜻이다.** 자동으로 켜지도 끄지도 않고, 운영자가 둔 상태
  그대로 둔다. 그래서 스위치 하나로 두 상황을 모두 다룬다.
  - 대회 기간 외: 서버를 꺼 두고 스위치를 끈다
  - 마감 직전: 서버를 켜 두고 스위치를 끈다
- 스위치를 바꾸는 데 코드 배포나 서버 재시작이 필요 없어야 한다. 마감 직전에 급하게 바꾸는 일이기 때문이다.
- 같은 화면에 **현재 서버 상태**(켜짐/꺼짐/켜지는 중)와 **최근 켜기·끄기 기록**을 보여 준다.
- 디스코드 알림은 스위치와 상관없이 "켜기 요청이 실패했다"처럼 사람이 알아야 하는 일에 대해 계속 보낸다.
  스위치가 꺼져 있을 때 무엇을 알릴지는 STEP2에서 정한다.

## 4. 범위 밖 (이번에 하지 않는 것)

- 스팟 인스턴스 자동 운영, 스팟과 온디맨드를 섞는 구성
- 평가 서버 여러 대를 자동으로 늘리고 줄이는 것(오토스케일링)
- 참가자 화면 문구 변경. 현재 문구("평가 서버가 재개된 뒤 순서대로 처리됩니다")도 사실과 맞다(Q4)
- 마감 직전처럼 몰릴 때의 별도 규칙. 운영자가 스위치를 끄고 서버를 켜 두면 된다(Q6)
- 운영자 노트북 예비 워커(Q2에서 쓰지 않기로 함)
- 디스코드 외 알림 채널(문자, 이메일)
- 웹 서버(Lightsail) 자체가 죽었을 때의 알림. 그때는 이 자동화도 같이 죽는다

## 5. 성공 기준

| # | 기준 |
|---|---|
| S1 | 서버가 꺼진 상태에서 제출이 들어오면, **제출 후 2분 안에** 켜기 요청과 디스코드 알림이 나간다 |
| S2 | 서버가 꺼진 상태에서 들어온 제출의 평가가 **제출 후 10분 안에** 시작된다(부팅·도커·워커 기동 포함) |
| S3 | 대기·평가가 없는 상태가 30분 이어지면 서버가 **중지** 상태가 된다. 종료되는 일은 없다 |
| S4 | 평가 도중에 서버가 꺼지는 일이 없다. 자동 끄기 때문에 `평가중`에 갇히는 제출이 없다 |
| S5 | 한 사건에 같은 알림이 두 번 이상 오지 않는다 |
| S6 | 켜기 요청 후 정해진 시간 안에 워커가 살아나지 않으면 반드시 알림이 온다 |
| S7 | 자동화를 끈 상태에서는 제출이 들어와도 서버가 켜지지 않고, 켜져 있는 서버가 유휴로 꺼지지도 않는다 |
| S9 | SSH로 접속해 작업하는 동안에는 대기열이 30분 넘게 비어도 서버가 꺼지지 않는다 |
| S10 | 관리자 페이지에서 스위치를 바꾸면 배포나 재시작 없이 다음 판단부터 반영된다 |
| S8 | 2주 대회 기간의 인스턴스 요금이 24시간 온디맨드($83)보다 확실히 낮다. 실제 값을 대회 후 기록한다 |

## 6. 확정된 결정 사항 (2026-10-04 운영자)

| 항목 | 결정 |
|---|---|
| 자동화 범위 | **알림 + 자동 켜기 + 자동 끄기** 세 가지 모두 |
| 알림 채널 | **디스코드**(웹훅) |
| 유휴 판정 시간 | **30분** |
| 대상 서버 | **온디맨드 1대**(m7i.xlarge, 서울). 스팟은 이번 구성에 넣지 않는다 |
| 비용 원칙 | 자동화 자체에 추가 요금이 드는 방법은 쓰지 않는다(SMS, CloudWatch 경보, 탄력적 IP 등) |
| Q1 — 기동 실패 알림 | 켜기 요청 후 **10분** 안에 워커가 살아나지 않으면 알린다. 평소 부팅부터 워커 기동까지 몇 분이 걸려서, 더 짧으면 오경보가 난다 |
| Q2 — 다른 워커 | **운영자 노트북을 예비 워커로 쓰지 않는다.** 켜기 판단은 대상 EC2의 워커만 본다(§3.1) |
| Q4 — 참가자 문구 | **바꾸지 않는다.** 지금 문구도 사실과 맞다 |
| Q5 — 스위치 위치 | **관리자 페이지.** 마감 직전에 자주, 급하게 바꿀 값이라 SSH로 설정 파일을 고치는 것보다 쉽고 실수가 적다. 다만 구현량이 늘어난다(DB 항목, 관리자 화면, 테스트). "꺼짐"은 "사람이 직접 관리"라는 뜻이다(§3.4) |
| Q6 — 마감 직전 규칙 | **별도 규칙을 두지 않는다.** 몰릴 것 같으면 운영자가 서버를 켜 두고 스위치를 끈다 |
| Q3 — 서버 작업 중 보호 | **SSH 접속이 있으면 끄지 않고, 그 상태가 1시간 넘게 이어지면 알린다**(§3.2). 운영자가 따로 표시할 필요가 없다. 처음 검토한 "서버 안에 표시 파일을 만들어 두는 방식"은 직관적이지 않고 지우는 것을 잊기 쉬워 고르지 않았다. 관리자 페이지의 "제출 일시중지"와는 연결하지 않는다 |
