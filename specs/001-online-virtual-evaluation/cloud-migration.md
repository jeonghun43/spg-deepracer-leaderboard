# 웹 서버 상시 운영 — 클라우드 이관 설계

> ## 갱신 안내 (2026-08-01)
>
> 이 문서의 **"평가는 노트북에 남긴다"는 전제는 이후 뒤집혔다.** 평가 워커와 DRFC도
> **AWS EC2 스팟 인스턴스**로 옮겼다 — 절차는
> **[worker-server-setup.md](../../docs/worker-server-setup.md)**.
>
> 다만 이 문서에서 결정한 **연결 구조는 그대로 유효하고 실제로 재사용됐다** — Tailscale 사설망으로
> DB에 붙고(§3), 모델·영상은 토큰 인증 HTTPS 엔드포인트로 주고받는다(§4). EC2 워커도 노트북 워커와
> 똑같은 방식으로 붙기 때문에 이관에 코드 변경이 거의 필요 없었다.
>
> §1의 "RunPod은 Docker를 못 돌린다 / 평가에 GPU가 필요 없다"는 판단은 **여전히 맞다.**
> 그래서 EC2에서도 GPU 인스턴스가 아니라 CPU 인스턴스(m7i.xlarge)를 골랐다.

> 노트북이 꺼져도 리더보드·로그인·제출이 24시간 살아있게 만든다. 평가(DRFC)는 GPU/Docker가 필요해
> 무료 티어로는 못 돌리므로 **노트북에 남기고, 웹 + DB만 클라우드로 옮긴다.**
>
> 작성일: 2026-07-27 · 작업 목록은 [tasks.md](tasks.md) Phase 10

## 1. 목표와 전제

**목표**: 노트북 전원 상태와 무관하게 다음이 항상 동작한다.
- 리더보드 조회(로그인 불필요), 팀·관리자 로그인, 모델 제출 접수

**전제**
- 평가는 노트북에서 계속 돈다. 노트북이 꺼져 있으면 제출은 **접수되어 대기열에 쌓이고**, 노트북이 켜지면 순차 처리된다.
- 결정 사항 (2026-07-27 운영자):
  - 접속 주소는 **도메인을 구매**해 고정 + 정식 HTTPS로 간다.
  - 호스팅은 Oracle 무료 / 유료 VPS 둘 다 비교만 해두고 선택은 보류 — **코드 작업은 어느 쪽이든 동일**하다.
  - 이관 시점은 "지금 바로". 단 계정·도메인 준비가 선행되어야 한다(§7).

**하지 않는 것**
- 평가 서버의 클라우드 이전. RunPod은 Pod 내부에서 Docker를 못 돌려 DRFC가 아예 시작되지 않고, 우리 평가는 애초에 GPU가 필요 없다(노트북 CPU로 10분/건). GPU 시간당 과금을 낼 이유가 없다.
- 참가자용 알림 기능. 지금처럼 새로고침으로 확인한다(spec.md 확정).

## 2. 구조 변경

```
현재
  [노트북] 웹(컨테이너) ── 같은 storage/ ── 워커 ── localhost:5432 DB(컨테이너)
                                                    ↑ cloudflared quick tunnel (임시 주소)

이후
  [클라우드 VM]  웹 + DB + storage/          ←── HTTPS(도메인) ── 참가자
        ↑
        └── Tailscale 사설망 ──→ [노트북] 워커 + DRFC + MinIO
                                  (모델 내려받기 / 영상 올리기 / DB 접속)
```

지금 구조는 **웹과 워커가 같은 디스크와 같은 localhost DB를 공유**해서 성립한다. 분리되면 세 가지가 끊긴다.

## 3. 문제 1 — 워커가 DB에 접속하는 경로

| 방식 | 평가 |
|---|---|
| Postgres 포트를 공개 인터넷에 열기 | ❌ 5432는 상시 스캔 대상이다. 비밀번호 하나에 대회 데이터 전부가 걸린다 |
| SSH 터널 | △ 되지만 끊기면 워커가 조용히 멈춘다. 재연결 관리를 따로 만들어야 함 |
| **Tailscale 사설망 (채택)** | ✅ 두 기기를 WireGuard 기반 사설망으로 묶는다. 무료(개인 100대), NAT 통과 자동, 끊겨도 자동 재연결. **DB 포트를 공개 인터넷에 전혀 열지 않는다** |
| 워커를 REST API로 전환 | 나중 선택지. DB 의존을 없애 가장 깨끗하지만 워커·큐 로직을 전부 다시 써야 한다 |

**설계**
- 클라우드 VM과 노트북에 Tailscale을 설치해 같은 tailnet에 넣는다.
- `docker-compose.yml`의 db 포트 매핑을 **tailnet 주소에만 바인딩**한다 (`"100.x.y.z:5432:5432"`). 공개 IP로는 접근 불가.
- 워커의 `DATABASE_URL` 호스트를 클라우드 VM의 tailnet 주소로 바꾼다. **코드 변경 없음 — 환경변수만 바뀐다.**
- 방화벽(보안 그룹)에서는 80/443만 연다.

## 4. 문제 2 — 모델 파일과 영상을 주고받는 경로

업로드된 모델(약 250MB)은 클라우드 VM 디스크에 저장되는데, 평가는 노트북에서 돈다.

| 방식 | 평가 |
|---|---|
| Cloudflare R2 등 오브젝트 스토리지 경유 | △ 동작하지만 계정·키 관리가 늘고 무료 10GB 한도가 붙는다. 보존 정책 덕에 우리 저장량은 시즌당 약 2.6GB라 **얻는 게 없다** |
| 네트워크 파일시스템(NFS/SMB) 마운트 | ❌ 연결이 끊기면 평가가 통째로 멈추고 진단이 어렵다 |
| **웹앱에 워커 전용 엔드포인트 추가 (채택)** | ✅ 이미 있는 웹앱을 그대로 쓴다. 외부 서비스 0개, tailnet 안에서만 오간다 |

**설계** — 엔드포인트 2개를 새로 만든다.

| 경로 | 용도 |
|---|---|
| `GET /internal/submissions/{id}/model` | 워커가 평가할 모델 아카이브를 스트리밍으로 내려받는다 |
| `POST /internal/submissions/{id}/video` | 평가가 끝난 뒤 결과 영상을 올린다 |

- **인증**: `X-Worker-Token` 헤더와 서버의 `WORKER_TOKEN`을 **상수 시간 비교**(`secrets.compare_digest`)한다. 토큰이 없거나 틀리면 404를 준다 — 존재 여부조차 알려주지 않기 위해서다.
- 이 경로는 tailnet 안에서만 접근하는 것이 정상이지만, **토큰이 1차 방어선**이다. 사설망을 유일한 방어선으로 삼지 않는다.
- 워커는 모델을 자기 로컬 임시 디렉터리로 받아 평가하고, 끝나면 지운다. 노트북에는 영구 저장하지 않는다.
- 영상은 워커가 업로드하고, 서버가 `storage/videos/`에 저장한 뒤 `EvaluationResult.video_path`를 채운다.
- **보존 정책(Phase 9-5)은 서버 쪽에서 그대로 동작한다** — 파일이 서버에 있기 때문이다.

## 5. 문제 3 — 노트북이 꺼져 있을 때의 화면

지금은 워커가 죽어도 참가자 화면에 아무 표시가 없다. 제출은 접수되지만 결과가 안 나오니 "고장 났나?"로 보인다.

**설계**
- `worker_heartbeats` 테이블 신설 (`worker_id` PK, `last_seen_at`). 워커가 폴링 루프마다 갱신한다. → **마이그레이션 1건 필요**
- 최근 N분(기본 3분) 안에 갱신된 워커가 하나도 없으면 "평가 서버 대기 중"으로 본다.
- 제출 화면과 리더보드 상단에 안내를 띄운다:
  > 평가 서버가 잠시 중지되어 있습니다. 제출은 정상 접수되며, 서버가 재개되면 순서대로 처리됩니다. (마지막 응답: N분 전)
- 예상 대기 시간 표시도 이 상태에서는 "재개 후 처리"로 바꾼다 — 지금 계산식(대기건수 × 10분)은 워커가 살아있다는 가정이라 거짓말이 된다.
- **제출 자체는 계속 받는다.** 참가자가 모델을 올려두고 퇴근할 수 있어야 한다.

## 6. 호스팅 비교 (선택 보류)

| | Oracle Cloud Always Free | 유료 VPS (Hetzner CX22 등) |
|---|---|---|
| 비용 | 0원 | 월 약 €4 (6천원 수준) |
| 사양 | ARM 2 OCPU / 12GB RAM / 200GB | x86 2 vCPU / 4GB RAM / 40GB |
| 아키텍처 | ARM64 — 우리 이미지(`python:3.12-slim`, `postgres:16`)는 arm64 지원, 문제 없음 | x86 — 지금 노트북과 동일 |
| 위험 | 가입 시 카드 인증 까다로움, ARM 재고 부족(Out of capacity) 빈번, **2026-06-15에 예고 없이 사양 반토막(4 OCPU/24GB → 2/12)** | 없음 |
| 적합성 | 우리 부하(10팀, 동시접속 소수)엔 2 OCPU도 충분 | 동일 |

**둘 다 코드 변경은 동일하다.** 어느 쪽을 고르든 §3~§5 작업은 그대로 쓰이므로, 계정 준비와 무관하게 코드부터 진행한다.

**주소·HTTPS**: 도메인을 구매해(연 1만원선) A 레코드를 VM 공인 IP로 연결하고, Caddy 또는 nginx + Let's Encrypt로 인증서를 자동 발급받는다. 이 시점에 `cloudflared` quick tunnel은 역할이 끝나므로 정리한다. `SESSION_HTTPS_ONLY=true`로 전환한다.

## 7. 운영자가 직접 해야 하는 것 (대행 불가)

계정 생성과 결제수단 등록은 대신할 수 없다. 아래는 직접 진행해야 한다.

1. 클라우드 계정 생성 (Oracle 또는 VPS 업체) + 카드 인증
2. 도메인 구매 및 DNS 관리 접근
3. Tailscale 계정 생성 (GitHub/Google 로그인으로 가입 가능)

준비되면 알려주시면, VM 세팅부터 이관·검증까지는 제가 진행한다.

## 8. 이관 절차와 위험

**절차**
1. VM 프로비저닝 → Docker 설치 → Tailscale 연결
2. 리포지토리 배포, `.env` 구성(새 `SESSION_SECRET`, `WORKER_TOKEN`), 도메인·HTTPS 설정
3. 데이터 이전: `pg_dump`로 DB 덤프 + `storage/` 전송 → VM에서 복원
4. 노트북 워커의 `DATABASE_URL`·`WEB_BASE_URL`·`WORKER_TOKEN`을 새 서버로 변경, 재시작
5. 스모크 체크 후 참가자에게 새 주소 공지, 기존 터널 종료

**위험과 대응**

| 위험 | 대응 |
|---|---|
| 공유한 터널 주소가 죽는다 | 도메인으로 바뀌므로 **재공지가 반드시 필요**하다. 전환 시점을 사전 공지한다 |
| 이관 중 다운타임 (수십 분) | 대기열이 빈 시점에, 가능하면 참가자 활동이 적은 시간대에 한다 |
| 데이터 이전 중 유실 | 덤프는 **복사**다. 이관 성공을 확인할 때까지 노트북의 원본 DB·storage를 지우지 않는다 |
| 새 서버가 불안정 | 롤백: 노트북 웹 컨테이너를 다시 띄우고 `cloudflared`를 재실행하면 원상 복귀(주소는 새로 발급) |
| `SESSION_SECRET` 변경 | 접속 중인 사용자가 전부 로그아웃된다. 재로그인 안내 필요 |
