# 제출 업로드 진행 상황 표시 — UX 분석과 설계

> 참가자가 모델 파일을 고르고 "제출하기"를 누르면 **20~30초 동안 브라우저 기본 스피너만 돌고 화면이 아무 말도 하지 않는다.** 참가자는 서비스가 멈춘 것으로 받아들인다.
>
> 작성일: 2026-07-30 · 작업 목록: [tasks.md](tasks.md) **Phase 13**

---

## 0. 먼저: 이 문제는 해결 가능한가?

**질문을 둘로 쪼개야 답이 나온다.**

| 질문 | 답 |
|---|---|
| ① 20~30초를 더 짧게 만들 수 있나? | **거의 불가능하다.** 그 시간은 대부분 실제 바이트 전송 시간이다. |
| ② 그 20~30초를 "먹통"이 아니게 만들 수 있나? | **완전히 가능하다. 그리고 이게 진짜 문제다.** |

### ①이 불가능한 이유

모델 아카이브는 실측 **약 250MB**([ux-improvements.md](ux-improvements.md) §2-5-2)다. 업로드 시간은 참가자 회선의 **업로드** 속도가 결정한다.

| 참가자 회선(업로드) | 250MB 전송 시간 |
|---|---|
| 기가 인터넷·학교망 (약 100Mbps) | **약 20초** ← 지금 관측된 20~30초가 여기 |
| 일반 가정 (약 40Mbps) | 약 50초 |
| 공유기 혼잡·와이파이 (약 10Mbps) | **약 3분 20초** |
| LTE 테더링 (약 5Mbps) | 약 6분 40초 |

서버를 아무리 키워도 이 표는 바뀌지 않는다. 병목은 서버가 아니라 **참가자 집의 업링크**다. 서버 쪽에서 손댈 수 있는 것(파일을 스트리밍으로 디스크에 쓰기, 프록시 타임아웃 30분)은 이미 되어 있고, 압축률을 높이는 건 참가자가 만드는 파일이라 우리가 개입할 수 없다.

> 즉 **"기다리는 시간을 없애달라"는 요구는 들어줄 수 없다.** 오히려 회선이 느린 참가자에게는 지금보다 훨씬 오래(수 분) 걸린다는 사실이 숨겨져 있다 — 지금 화면은 그 사람에게 "5분간 완전한 침묵"을 준다. **이쪽이 훨씬 심각한 상황이고, 대회가 커지면 반드시 터진다.**

### ②가 진짜 문제인 이유

응답 시간에 대한 고전적 기준(Nielsen, *Response Times: The 3 Important Limits*)은 이렇게 나뉜다.

| 구간 | 사용자 인지 | 필요한 것 |
|---|---|---|
| ~0.1초 | 즉각적 | 아무것도 필요 없음 |
| ~1초 | 흐름은 유지, 지연은 느낌 | 최소한의 표시 |
| ~10초 | **주의력이 끊긴다. 다른 일을 하러 간다** | 여기까지가 단순 스피너의 한계 |
| 10초 초과 | **"고장 났다"고 판단한다** | **퍼센트 진행률 + 남은 시간**이 필수 |

우리는 **20~30초, 느린 회선이면 수 분**이다. 마지막 칸에 해당한다. 그런데 지금 쓰는 건 첫 칸용 도구(브라우저 기본 스피너)다. **도구 선택이 한 단계가 아니라 두 단계 틀렸다.**

핵심은 이것이다 — **불확실한 기다림은 같은 길이의 확실한 기다림보다 훨씬 길게 느껴진다.** 진행률 표시는 시간을 줄이지 않지만 체감 시간을 줄이고, 무엇보다 **"고장 났다"는 오판을 막는다.**

## 1. 지금 화면의 진단 (UX 관점)

`submit.html`의 제출 폼은 파일 입력 하나와 버튼 하나뿐인 평범한 `multipart/form-data` POST다. 여기서 발생하는 문제를 심각한 순서로 정리한다.

### 1-1. [치명] 시스템 상태가 보이지 않는다
브라우저 탭의 회전 아이콘은 "무언가 진행 중"만 말할 뿐 **무엇이·얼마나·언제까지**를 말하지 못한다. 참가자에게 주어진 정보가 0비트다.

### 1-2. [치명] 클릭이 접수됐다는 신호가 없다
버튼을 눌러도 버튼 모양이 그대로다. 사용자는 "안 눌렸나?" 하고 **다시 누른다.** 서버는 중복 제출을 막지만(동시 1건 제한), 참가자 눈에는 여전히 아무 반응이 없다.

### 1-3. [높음] 30초를 기다린 뒤에야 "형식이 틀렸다"고 알려준다
확장자와 용량 검사는 **전부 서버에서** 한다. `.rar`을 올린 참가자는 파일을 통째로 전송한 다음에야 거절당한다. 이건 **알 수 있었던 실패를 가장 비싼 시점까지 미룬 것**이다.

### 1-4. [높음] 실패하면 처음부터 다시 해야 한다
현재 오류 처리는 `RedirectResponse("/submit?error=...")`다. 페이지가 새로 뜨면 **`<input type="file">`에 골라둔 파일이 사라진다.** 참가자는 파일 탐색기를 다시 열어 파일을 다시 찾아야 한다.

### 1-5. [중간] 취소할 방법이 없다
파일을 잘못 골랐다는 걸 업로드 시작 후에 깨달아도 멈출 수단이 없다. 탭을 닫는 게 유일한 방법이고, 그러면 서버에는 절반짜리 파일이 남는다.

### 1-6. [중간] 실수로 페이지를 벗어나도 경고가 없다
업로드 중 새로고침·뒤로가기 한 번에 전송이 날아간다.

### 1-7. [중간] 전송이 끝난 뒤에도 잠깐의 공백이 있다
바이트가 다 올라간 뒤 서버가 파일 검증·DB 커밋을 하고 리다이렉트를 돌려준다. 진행률만 붙이면 이 구간에서 **막대가 100%에 멈춰 있는데 화면이 안 넘어가는** 새로운 불안이 생긴다. 설계에서 미리 처리해야 한다.

## 2. 설계 — 화면 상태 전이

핵심 원칙: **모든 순간에 "지금 무엇이 일어나는 중이고, 내가 무엇을 할 수 있는지"가 화면에 있어야 한다.**

```
[대기]   파일 선택 전 — 안내 문구로 미리 기대치를 설정
   │        "모델 파일은 보통 250MB 안팎입니다. 회선에 따라 20초~수 분 걸립니다."
   ▼ 파일 선택
[검증]   즉시(0.1초 안에) 파일명·크기 표시 + 확장자/용량 검사
   │        ✗ 걸리면 여기서 바로 거절 — 전송하지 않는다 (1-3 해결)
   ▼ 제출하기
[전송중] ████████░░░░ 62%   155.0MB / 250.4MB · 8.2MB/s · 약 12초 남음
   │        버튼 → 비활성 + "업로드 중…"      [취소] 버튼 노출
   │        페이지 이탈 시 브라우저 경고
   ▼ 100%
[확인중] 진행률 대신 "서버에서 파일을 확인하는 중…" (1-7 해결)
   ▼
[완료]   제출 접수 → 대기열 화면으로 이동
[실패]   폼 자리에 한국어 오류 + [다시 시도] — 고른 파일은 그대로 유지 (1-4 해결)
```

### 2-1. 왜 XMLHttpRequest인가 (fetch가 아니라)

업로드 진행률을 얻는 표준 수단은 `XMLHttpRequest`의 `upload.onprogress` 이벤트뿐이다. `fetch()`는 **응답** 스트림은 읽을 수 있어도 **요청 본문의 전송 진행률을 알려주지 않는다.** (`ReadableStream`을 요청 본문으로 넘기는 방식이 있지만 HTTP/2 이상 + `duplex` 옵션이 필요하고 브라우저 지원이 고르지 않다.) 새 기술이 아니라 **이 목적에 맞는 유일한 표준 API**라서 고른 것이다.

### 2-2. 진행률의 정확도 — 정직하게 다룬다

브라우저가 보고하는 `loaded` 바이트는 **OS 소켓 버퍼에 넘긴 양**이지 서버가 실제로 받은 양이 아니다. 그래서 진행률은 실제보다 **약간 앞서 간다**. 특히 회선이 느리면 막대가 100%에 도달하고도 실제 전송이 남아 있을 수 있다.

- 그래서 100% 도달 = "완료"가 아니라 **[확인중] 상태로 전환**한다. 거짓말을 하지 않는 설계다.
- 남은 시간은 첫 1초 동안은 표시하지 않는다(초기 표본이 튀어서 "약 4시간 남음" 같은 값이 나온다). 이후에는 최근 속도에 가중치를 준 이동평균으로 계산하고, 값은 "약 N초/N분"으로 뭉뚱그린다.
- 참고: 우리 Caddy는 요청 본문을 버퍼링하지 않고 그대로 흘려보내므로(`reverse_proxy` 기본 동작), 프록시가 진행률을 크게 왜곡하지는 않는다.

### 2-3. JS가 없거나 실패해도 제출은 된다 (Progressive Enhancement)

기존 `<form method="post" enctype="multipart/form-data">`를 **그대로 둔다.** 스크립트는 `submit` 이벤트를 가로채는 방식으로만 동작하므로, JS가 꺼져 있거나 스크립트 로딩이 실패하면 지금과 똑같이 폼이 전송된다. **진행률 표시 때문에 제출 자체가 불가능해지는 상황을 원천적으로 만들지 않는다.** 대회 중에 참가자의 제출 경로를 새 코드에 통째로 의존시키는 건 감당할 수 없는 위험이다.

### 2-4. 서버 변경은 최소로

업로드 처리 로직(검증 순서·한도·동시 제출 제한·저장 경로)은 **한 줄도 건드리지 않는다.** 응답 형식만 요청에 따라 갈라진다.

| 요청 | 응답 |
|---|---|
| 일반 폼 전송 (지금) | `303 → /submit` 또는 `303 → /submit?error=...` — **기존과 완전히 동일** |
| `Accept: application/json` (새 스크립트) | `{"ok": true, "redirect": "/submit"}` 또는 `400 {"ok": false, "error": "..."}` |

JSON 분기를 두는 이유는 두 가지다. 첫째, 리다이렉트를 따라가면 XHR이 **제출 페이지 전체를 한 번 더 내려받고** 브라우저가 또 한 번 GET 하게 되어 낭비다. 둘째, 오류 메시지를 URL이 아니라 응답 본문으로 받아야 **페이지를 새로 띄우지 않고** 그 자리에서 안내할 수 있다(1-4 해결).

### 2-5. 클라이언트 검증 규칙은 서버에서 내려보낸다

허용 확장자와 용량 상한을 JS에 다시 적어넣으면 `config.py`와 어긋나는 순간 조용히 틀린 안내를 하게 된다. 템플릿이 `settings.model_upload_allowed_extensions` / `model_upload_max_bytes`를 `data-*` 속성으로 렌더하고 스크립트가 그것을 읽는다. **규칙의 출처는 계속 `config.py` 하나다.**

클라이언트 검사는 어디까지나 **빠른 안내용**이고, 서버 검증은 그대로 남는다(스크립트를 우회한 요청도 막아야 한다).

### 2-6. 접근성

- 진행 막대는 `role="progressbar"` + `aria-valuenow/valuemin/valuemax`.
- 상태 문구 영역은 `aria-live="polite"` — 스크린 리더가 진행 상황과 오류를 읽어준다.
- 색만으로 상태를 구분하지 않는다(문구를 항상 함께 쓴다).

## 3. 범위 밖 (이번에 하지 않는 것)

| 항목 | 이유 |
|---|---|
| **이어올리기(resumable/tus·청크 업로드)** | 끊긴 업로드를 이어받으려면 청크 저장소·조립·만료 정리가 필요하다. 20~30초짜리 업로드에 이 복잡도는 과하다. 회선이 매우 나쁜 참가자가 실제로 실패를 겪으면 그때 재검토한다. |
| **평가 결과 자동 갱신(폴링)** | "제출 후 새로고침해서 확인" 문제는 별개의 UX 과제다. 이번 작업은 **업로드 구간**에 한정한다. |
| **업로드 속도 자체 개선** | §0에서 확인했듯 우리가 손댈 수 있는 대상이 아니다. |
| **드래그 앤 드롭 업로드** | 있으면 좋지만 지금 문제(피드백 부재)와 무관하다. |

## 4. 성공 기준

- 제출하기를 누른 뒤 **0.1초 안에** 화면이 반응한다(버튼 비활성 + 상태 문구).
- 업로드 내내 **퍼센트·전송량·남은 시간**이 갱신되어 보인다.
- 잘못된 확장자·초과 용량 파일은 **전송을 시작하지 않고** 즉시 거절된다.
- 전송이 100%에 닿은 뒤에는 문구가 "서버에서 확인 중"으로 바뀌어, 멈춘 것처럼 보이지 않는다.
- 실패해도 **고른 파일이 유지되고** 버튼 한 번으로 재시도된다.
- 업로드 중 취소할 수 있고, 실수로 페이지를 벗어나려 하면 경고가 뜬다.
- **JS를 끈 브라우저에서도 제출이 정상 동작한다.**
- 서버의 업로드 검증 규칙·한도·저장 방식은 변경 전과 동일하다(회귀 없음).

## 5. 배포 후 확인 항목

1. 실제 250MB 모델로 제출 → 진행률이 0%부터 매끄럽게 오르고 100% 후 "확인 중"을 거쳐 대기열 화면으로 넘어간다.
2. 개발자도구 네트워크 탭에서 **속도를 제한(throttling)** 하고 반복 → 남은 시간 추정이 터무니없는 값을 내지 않는다.
3. `.rar` 등 잘못된 파일 → 전송 없이 즉시 거절(네트워크 탭에 요청이 아예 안 생겨야 한다).
4. 업로드 중 취소 → 서버에 부분 파일이 남지 않는다.
5. JS 비활성 상태로 제출 → 기존 방식으로 정상 접수.
6. 하루 한도 초과·동시 제출 상태에서 제출 → 오류 문구가 화면 안에서 표시된다.
