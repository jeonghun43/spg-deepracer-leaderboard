# STEP 3 — 작업 분해: 가상 트랙 기반 자동 평가 플랫폼

> [plan.md](plan.md)(STEP2)의 아키텍처·데이터 모델을 실행 가능한 작업 단위로 쪼갠다. STEP4(구현)에서 이 목록을 순서대로 처리한다. `[P]` 표시는 서로 다른 파일을 건드리고 의존성이 없어 병렬로 진행해도 되는 작업.

## 진행 순서 (Phase)

```
Phase 0 프로젝트 셋업
   └─▶ Phase 1 데이터 모델 & DB
         └─▶ Phase 2 인증 · 계정
               └─▶ Phase 3 관리자 기능 ──┐
               └─▶ Phase 4 제출 & 큐 ────┼─▶ Phase 5 평가 워커 ──▶ Phase 6 리더보드 & 참가자 화면 ──▶ Phase 7 배포/운영 ──▶ Phase 8 검증
```
Phase 3과 4는 Phase 2 완료 후 병렬 진행 가능. Phase 5는 Phase 4(큐/데이터 모델)가 끝나야 시작 가능.

### 검증 방법과 결과 (2026-07-25)

- **실환경 DRFC 평가**: 제출 4번으로 업로드 → 큐 → `dr-start-evaluation` → metrics 파싱 → 결과 저장까지 실제로 1회 완주 검증 (`finished`, 109.801초, 이탈 0회). metrics JSON·시뮬레이션 로그·영상이 모두 `storage/` 아래에 남는 것까지 확인.
- **T043~T047**: [tests/verify_phase8.py](../../tests/verify_phase8.py)로 기동 중인 웹앱에 실제 HTTP 요청을 보내 재현 — **36개 항목 전부 통과**. 평가 자체는 위에서 이미 실환경 검증이 끝났으므로, 이 스크립트는 워커를 끈 채로 평가 결과만 워커와 동일한 형태로 채워 넣고 그 뒤 로직(카운트·동시제출·리더보드·아카이브)을 검증한다.
  - 실행: 워커를 정지한 뒤 `PYTHONPATH=. .venv/bin/python -m tests.verify_phase8`
  - 검증용 시즌이 하나 생성되므로, 끝난 뒤 해당 시즌은 삭제하고 워커를 다시 켠다.

### 설계 결정

- **저장 위치**: 기본값 `/mnt/c/Users/jjh03/drleader-backup` (Windows에서는 `C:\Users\jjh03\drleader-backup`). 환경변수 `BACKUP_DIR`로 바꿀 수 있다.
  - OneDrive는 용량이 차서 사용할 수 없다(2026-07-27 확인).
  - **Google Drive 가상 드라이브(G:)에는 직접 쓸 수 없다** — 실제 볼륨이 아니라 Drive 앱이 만든 가상 파일시스템이라 WSL에서 `/mnt/g`로 마운트되지 않는다(확인 완료). 그래서 **스크립트는 평범한 로컬 폴더에 쓰고, Google Drive 데스크톱의 "내 컴퓨터 폴더 백업" 기능으로 그 폴더를 Drive에 올린다.** 방향을 뒤집는 것이 가상 드라이브 문제를 피하는 가장 단순한 방법이다.
  - 대안으로 `rclone`을 써서 WSL에서 Drive API로 직접 올릴 수도 있지만, OAuth 인증과 토큰 관리가 추가되어 인수인계 난이도가 올라간다. 채택하지 않는다.
- **모델 파일은 기본 제외**. 건당 250MB(현재 2.5GB)라 매일 담으면 C 드라이브(여유 30GB)와 OneDrive 용량이 금방 찬다. 모델은 참가자 본인이 원본을 갖고 있어 재업로드가 가능하고, 보존 정책상 최고기록 것만 남는다. `BACKUP_INCLUDE_MODELS=true`로 켤 수 있게 한다.
- **담는 것**: DB 덤프(gzip) + `storage/videos`·`metrics`·`eval_logs`. 영상은 재생성이 불가능하고(평가 때만 만들어짐) 용량도 팀당 14MB 수준이라 포함한다.
- **주기·보관**: 하루 1회, 최근 14벌 유지 후 오래된 것부터 삭제. 최악의 경우 하루치 제출만 다시 받으면 된다.
- **스케줄러**: cron이 아니라 **systemd 타이머**(이 WSL은 systemd가 돌고 있다). `Persistent=true`로 두어 노트북이 꺼져 있어 걸렀던 실행을 다음 부팅 때 따라잡게 한다 — 매일 켜져 있지 않은 노트북이라 이 옵션이 핵심이다.
- **검증까지 포함**: 백업은 복원이 되어야 백업이다. 덤프가 비어 있지 않은지, gzip이 온전한지 매번 확인하고 결과를 로그에 남긴다.

- **평가되는 체크포인트는 `last_checkpoint`다**: DRFC의 `DR_EVAL_CHECKPOINT=last` 설정(기본값)에 따라, 참가자 압축 파일 안 `deepracer_checkpoints.json`의 `last_checkpoint`가 평가된다. 제출 19의 경우 `best_checkpoint`(4_Step-2337, avg_eval_metric 100)가 `last_checkpoint`(5_Step-3241, 85.8)보다 학습 중 성적이 좋았는데도 후자가 평가됐다. **참가자에게 "마지막 체크포인트가 평가된다"고 안내하거나, 규칙을 `best`로 바꿀지 결정해야 한다.**
- **같은 모델도 결과가 달라진다**: 제출 18과 19는 바이트 단위로 동일한 파일인데 18은 67.8%에서 멈췄고(immobilized) 19는 완주했다. 시뮬레이션 편차이며 플랫폼 결함이 아니다.

### 12-2. 평가 체크포인트 규칙을 `best`로 변경 (2026-07-30)

> 참가자 압축 파일에는 체크포인트가 여러 개 들어 있고, DRFC는 `DR_EVAL_CHECKPOINT`가 지정한 것만 평가한다. 기본값 `last` 때문에 **학습을 더 돌렸다가 성적이 나빠진 마지막 체크포인트로 채점되고 있었다**(제출 19: best 100점 vs last 85.8점). 운영자 결정으로 `best`로 바꾼다.

### 13-1 검증 기록 (2026-07-30)

**운영 DB를 건드리지 않고 검증했다.** 노트북 `.env`의 `DATABASE_URL`은 이제 **클라우드 운영 DB**(Tailscale)를 가리키므로, 그대로 웹을 띄우면 테스트 제출이 운영 데이터에 들어간다. 로컬 postgres에 별도 데이터베이스(`uxtest`)를 만들고 거기에만 시즌·팀을 하나 넣어 검증한 뒤 삭제했다.

| 확인 항목 | 결과 |
|---|---|
| pytest | **98개 통과** (기존 89 + 응답 분기 9) |
| 클릭 즉시 반응 | 버튼 비활성 + "업로드 중…", 취소 버튼 노출, 파일 입력 잠금 — 전부 동기적으로 발생 |
| 진행률 갱신 | `0% → 16% → 32% → 48% → 63% → 80% → 94% → 99%` + 전송량/속도(`31.7MB/s`)/남은 시간, `aria-valuenow`도 함께 갱신 |
| 100% 이후 | `서버에서 파일을 확인하는 중…` → `제출이 접수되었습니다` → 대기열 화면으로 이동 (제출 레코드 `queued` 생성 확인) |
| 잘못된 확장자(`.rar`) | 즉시 거절, **네트워크 요청 0건**(`performance` 리소스 항목으로 확인), 페이지 전환 없음 |
| 용량 초과(600MB) | `파일 용량이 너무 큽니다 (최대 500.0MB). 선택한 파일은 600.0MB입니다.` — 역시 전송 없음 |
| 업로드 중 취소 | 원상복구 + 안내 문구, **고른 파일 유지**, 서버에 부분 파일이 남지 않음(디렉터리 확인) |
| 오류 응답(동시 제출) | `400 {"ok":false,"error":"이전 제출의 결과가…"}` — 화면 전환 없이 그 자리 표시 |
| **JS 없는 경로** | curl 폼 전송 → 정상 시 `303 → /submit`, 오류 시 `303 → /submit?error=...` — **기존과 동일** |

- 남은 시간 추정은 시작 후 1초가 지나야 표시된다. 로컬 검증은 전송이 1.3초 만에 끝나 마지막 구간에서만 나타났고, 실제 회선(수십 초~수 분)에서는 처음부터 표시된다.
- 취소 시 서버 쪽 `ClientDisconnect` 처리로 절반짜리 파일(최대 250MB)을 지운다.

## Phase 14 — 관리자 진입점 은닉 (2026-08-03)

### 14-1 검증 기록 (2026-08-03)

**운영 DB를 건드리지 않고 검증했다.** 노트북 `.env`의 `DATABASE_URL`이 클라우드 운영 DB를
가리키므로(Phase 13-1과 같은 이유), 로컬 postgres에 임시 DB `admintest`를 만들어 마이그레이션과
관리자 시드만 넣고 거기에만 붙여 검증한 뒤 삭제했다. 검증 중 워커는 건드리지 않았다.

| 확인 항목 | 결과 |
|---|---|
| pytest | **123개 통과** (기존 98 + 신규 25) |
| 옛 경로 `/admin/login` | GET·POST 모두 **404** |

**검증 중 발견해 고친 것**

- `include_in_schema=False`를 빼면 **FastAPI가 `/docs`와 `/openapi.json`에 비밀 경로를 그대로
  실어 보낸다.** 숨긴 주소가 공개 문서로 새는 경로라 등록 시점에 막고 테스트로 고정했다.
- **`docker-compose.prod.yml`이 통째로 파싱 실패했다.** 처음 쓴 안내 문구
  `${ADMIN_LOGIN_PATH:?... (예: /_ops/...)}`의 **`예: ` 안에 있는 콜론+공백을 YAML이 매핑으로
  읽어버려** 파일 전체가 깨졌다. 값을 큰따옴표로 감싸고 문구를 `예) `로 바꿔 해결했다.
  **`docker compose config`를 실제로 돌려보지 않았으면 배포 시점에야 발견했을 문제다.**
- 처음 만든 검증 스크립트에서 "다른 아이디는 따로 카운트"가 실패했는데, **코드가 아니라 기대값이
  틀렸다.** 같은 IP(127.0.0.1)가 이미 잠긴 상태라 아이디를 바꿔도 IP 카운터에 걸린 것으로,
  의도한 동작이다. `X-Forwarded-For`로 IP를 분리해 다시 검증했다.

**검증 중 발견했으나 이번 범위 밖인 것**

- **`tests/verify_phase8.py`가 팀 등록 단계에서 깨져 있다 — Phase 14와 무관한 기존 문제다.**
  팀 등록이 예전에는 발급 계정을 URL 쿼리(`?new_login=...&new_password=...`)로 넘겼는데
  `ux-improvements.md §2-2`에서 **응답 본문으로 바뀌었고**(비밀번호를 URL에 싣지 않기 위해),
  폼 필드명도 `team_name` → `team_names`(일괄 등록)로 바뀌었다. 그때 이 스크립트가 갱신되지 않았다.
  Phase 14 검증은 현재 API에 맞춘 별도 스크립트로 수행했고, 관리자 기능은 전부 정상임을 확인했다.
  이 스크립트 자체의 보수는 별도 과제다.
