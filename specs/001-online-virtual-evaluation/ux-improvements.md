## 0. [P0] 업로드 모델 파일 경로가 워커에서 안 잡히는 문제

### 증상 (2026-07-26 13:37 KST, submission 16)
```
예상치 못한 오류: [Errno 2] No such file or directory:
  '/app/storage/models/1/6/20260726T043712_my_deepracer_model.tar.gz'
```
팀 "안녕하세요"의 제출이 평가되지 못하고 `error`로 끝났다. **지금 상태로는 임원진의 모든 제출이 같은 이유로 실패한다.**

### 원인
`Submission.model_path`에 **절대 경로**를 저장하는데, 그 경로를 쓰는 주체가 서로 다른 파일시스템 네임스페이스에 있다.

| | 실행 위치 | `storage/` 절대 경로 |
|---|---|---|
| 웹(업로드, 경로 기록) | `web` 컨테이너 | `/app/storage/...` |
| 워커(경로 읽어서 평가) | WSL 호스트 프로세스 | `/mnt/c/Users/jjh03/spg_deepracer_leaderboard/storage/...` |

둘은 같은 디렉터리를 bind mount로 공유하므로 **파일 자체는 정상적으로 저장돼 있고**, 어긋난 것은 DB에 적힌 경로 문자열뿐이다. 어제(7/25)까지는 웹을 호스트에서 uvicorn으로 직접 띄웠기 때문에 양쪽 절대 경로가 우연히 일치했고, 웹을 컨테이너로 올린 시점부터 깨졌다. 즉 **환경 구성 변경으로 드러난 잠재 버그**다.

### 해결 방침
경로를 "저장 루트 기준 상대 경로"로 다루고, 읽는 쪽이 자기 환경의 `settings.storage_dir`에 붙여 해석한다.

- **저장(웹)**: `models/{season}/{team}/{파일명}` 처럼 `storage_dir` 기준 상대 경로로 기록한다.
- **해석(워커)**: `resolve_storage_path()` 유틸을 통해 읽는다.
  1. 상대 경로 → `settings.storage_dir / 경로`
  2. 절대 경로 → 그대로 존재하면 사용 (**7/25 이전에 쌓인 기존 레코드 호환**)
  3. 절대 경로인데 없으면 → 경로 안의 `storage/` 이후 부분을 잘라 내 `settings.storage_dir` 아래로 다시 붙인다 (`/app/storage/models/...` → 호스트의 `storage/models/...`). **이미 error로 끝난 submission 16도 재큐잉하면 이 규칙으로 살아난다.**
- 마이그레이션 없음 — 기존 행을 고치지 않고 읽는 쪽에서 흡수한다. 운영 중 배포라 DB를 건드리는 작업은 최소화한다.

### 성공 기준
- 웹(컨테이너)에서 올린 모델을 호스트 워커가 찾아 평가를 시작한다.
- 7/25 이전에 저장된 절대 경로 레코드도 그대로 동작한다(회귀 없음).
- 이 규칙이 단위 테스트로 고정된다.

## 1. 무엇을 / 왜 (Spec)

### 1-1. 리더보드는 "지금 열려있는 대회"로 바로 들어가진다

**현재**: `/leaderboard`로 들어가면 항상 시즌 목록이 먼저 뜨고, 거기서 진행중인 시즌을 한 번 더 골라야 리더보드를 본다. 대회 기간 동안 참가자·운영자 모두 매번 같은 시즌을 반복해서 클릭하고 있다.

**바뀌는 것**: 진행중(`active`) 시즌이 있으면 `/leaderboard` 접속 시 그 시즌 리더보드로 곧장 들어간다. 과거 시즌은 리더보드 화면의 "다른 시즌 보기" 링크로 계속 볼 수 있다.

**성공 기준**
- 대회 기간 중 상단 네비게이션의 "리더보드"를 누르면 클릭 한 번으로 순위표가 보인다.
- 진행중 시즌이 없으면(전부 준비중/마감/아카이브) 지금처럼 시즌 목록이 보인다. — *확정 (2026-07-26, 사용자)*
- 아카이브된 과거 시즌 리더보드는 여전히 조회 가능하고, 링크(`/leaderboard/{id}`)도 그대로 동작한다.

### 1-2. 팀 계정을 한 번에 여러 개 만들고 한 번에 받아본다

**현재**: 팀 이름 하나 입력 → 등록 → 아이디/비밀번호 한 쌍 확인 → 다시 입력… 을 팀 수만큼 반복해야 한다. 게다가 발급 정보가 리다이렉트 URL의 쿼리 파라미터로 노출된다(브라우저 히스토리·로그에 비밀번호가 남는다).

**바뀌는 것**: 팀 이름을 여러 줄로 한 번에 붙여넣고 "일괄 등록"하면, 생성된 팀 전체의 아이디/비밀번호가 한 화면에 표로 뜬다. CSV로도 내려받을 수 있다.

**성공 기준**
- 팀 이름 10개를 붙여넣고 한 번 제출하면 팀 10개 + 계정 10개가 생성되고, 10줄짜리 발급 표가 화면에 보인다. — *입력 방식·표시 방식 확정 (2026-07-26, 사용자)*
- 표에서 CSV 다운로드 버튼으로 `팀명,아이디,비밀번호` 파일을 받을 수 있다.
- 이미 있는 팀 이름이나 빈 줄이 섞여 있어도 전체가 실패하지 않는다 — 유효한 것만 만들고 건너뛴 이름을 이유와 함께 알려준다.
- 비밀번호가 URL에 남지 않는다.

### 범위 밖
- 팀 계정 비밀번호 재발급/초기화 기능 (필요하면 별도 작업으로).
- 팀 이름 수정·삭제 기능.

## 2. 기술 계획 (Plan)

### 2-1. 리더보드 라우팅

기존 라우트 3개(`/`, `/leaderboard`, `/leaderboard/{season_id}`)를 다음처럼 정리한다.

| 경로 | 지금 | 바뀐 뒤 |
|---|---|---|
| `/` | `/leaderboard`로 리다이렉트 | 그대로 |
| `/leaderboard` | 시즌 목록 렌더 | 진행중 시즌이 **1개 이상**이면 가장 최근 시작한 진행중 시즌의 `/leaderboard/{id}`로 303 리다이렉트, 없으면 시즌 목록 렌더 |
| `/leaderboard/seasons` | (없음) | 시즌 목록 렌더 — 자동 진입을 우회하는 고정 경로 |
| `/leaderboard/{season_id}` | 시즌 리더보드 | 그대로 |

- **라우트 선언 순서**: FastAPI는 선언 순서대로 매칭하므로 `/leaderboard/seasons`를 `/leaderboard/{season_id}`(int)보다 **먼저** 선언해야 한다. 그렇지 않으면 `seasons`가 int로 파싱되며 422가 난다.
- **진행중 시즌 선정**: `status == ACTIVE` 중 `start_date` 내림차순 첫 번째. 운영상 진행중 시즌은 하나지만, 실수로 둘이 되어도 화면이 깨지지 않게 결정적(deterministic) 규칙을 둔다.
- 리다이렉트는 303(See Other) — 기존 `index()`와 동일하게 캐시되지 않는 리다이렉트를 쓴다.

**템플릿 변경**
- `leaderboard.html`의 "← 다른 시즌 보기" 링크를 `/leaderboard` → `/leaderboard/seasons`로 바꾼다. (안 바꾸면 진행중 시즌으로 되돌아와 목록에 못 간다.)
- `leaderboard_seasons.html`에 진행중 시즌 표시(배지)를 유지하고, 각 시즌 링크는 그대로 `/leaderboard/{id}`.
- `base.html`의 네비게이션 "리더보드"는 `/leaderboard` 그대로 두면 자동으로 새 동작을 탄다.

### 2-2. 팀 계정 일괄 발급

**입력** — `admin/season_detail.html`의 팀 등록 폼을 `<input type="text">` 하나에서 `<textarea name="team_names">`로 교체.
- 구분자: 줄바꿈 우선, 각 줄 안의 쉼표도 구분자로 인정(엑셀 복사 대응). 앞뒤 공백 제거, 빈 줄 무시.
- 입력 안에서 중복된 이름은 첫 번째만 사용.

**처리** — `POST /admin/seasons/{season_id}/teams/new` 를 일괄 처리로 변경.
```
이름 목록 파싱
 └─ 각 이름마다:
     ├─ 빈 문자열 / 입력 내 중복      → 건너뜀
     ├─ 시즌 내 기존 팀명과 중복       → 건너뜀 + 사유 기록
     └─ Team 생성 → flush → login_id = "{season.id}-{team.id}" → 비밀번호 생성 → Account 생성
 └─ 전부 처리 후 commit 1회
```
- 팀명 중복은 `UniqueConstraint("season_id", "name")`에 걸리므로, **DB 예외에 기대지 않고** 기존 팀명 집합을 먼저 조회해 사전 검사한다. 한 건 실패로 트랜잭션 전체가 깨지는 걸 막기 위함이다.
- `login_id`는 지금과 동일하게 `{season_id}-{team_id}` 규칙을 유지한다(기존 계정과 형식 일관).

**발급 결과 전달** — 쿼리 파라미터를 버리고, POST 응답에서 **결과 페이지를 직접 렌더**한다(리다이렉트 없음).

검토한 세 방식과 선택 이유:

| 방식 | 문제 |
|---|---|
| 지금처럼 쿼리 파라미터 | 비밀번호가 URL·브라우저 히스토리·프록시 로그에 남는다. 팀이 여러 개면 URL도 감당 안 된다. |
| 세션 flash 후 리다이렉트(PRG) | 세션은 **서명된 쿠키**라 팀 수가 늘면 4KB 쿠키 한계를 넘고, 넘는 순간 브라우저가 쿠키를 통째로 버려 **관리자가 로그아웃된다**. 게다가 리다이렉트 사이에 프로세스가 재시작되면 비밀번호는 bcrypt로만 남아 **영구 복구 불가**. |
| **POST 응답에 직접 렌더 (채택)** | 계정을 만든 바로 그 응답에 비밀번호가 실려 나가므로 중간 유실 지점이 없다. URL에도 남지 않는다. |

- 새로고침 시 브라우저가 재전송을 물어보는데, **팀명 중복은 건너뛰므로 재전송해도 새로 만들어지는 팀이 없다**(전부 "이미 존재" 처리). 운영상 안전하다.
- 화면 문구는 지금과 같이 "지금 바로 저장/전달해주세요 — 다시 표시되지 않습니다"를 유지한다.
- 한 번에 처리하는 팀 수는 **50개로 제한**한다(실수로 대량 붙여넣기 방지). 초과 시 아무것도 만들지 않고 오류 메시지를 보여준다.

**표시** — `season_detail.html`의 발급 카드를 표로 교체.
- 열: 팀명 / 아이디 / 비밀번호. 건너뛴 이름은 표 아래 회색 문구로.
- **CSV 다운로드**: 표 데이터를 JS로 Blob 만들어 `download` 속성으로 내려받는다(서버 왕복 없음 — 비밀번호를 다시 서버에 보내지 않기 위함). 파일명 `{시즌명}_teams.csv`, 엑셀 한글 깨짐 방지를 위해 UTF-8 BOM 포함.

- 팀 로그인·제출·워커·아카이브 로직은 건드리지 않는다.

## 2-4. 팀 비밀번호 재발급 (Phase 9-4, 2026-07-26 추가)

### 왜 필요한가
비밀번호는 bcrypt 해시로만 저장되므로 **발급 시점을 놓치면 누구도 원문을 볼 수 없다**(관리자도, DB를 직접 열어도). 이건 공개 인터넷에 노출된 서비스에서 지켜야 할 성질이라 그대로 두고, 대신 분실 상황을 "재발급"으로 해소한다. 일괄 등록 이전에 만들어진 기존 7팀은 CSV 보관 수단이 없었으므로 실제로 이 경로가 필요하다.

### 동작
- 시즌 관리 화면의 팀 목록 각 행에 **"비밀번호 재발급"** 버튼을 둔다. 누르면 확인창을 거쳐 새 비밀번호를 만들고, **기존 발급 결과 표(팀명/아이디/비밀번호 + CSV 다운로드)를 그대로 재사용**해 화면에 한 번만 표시한다.
- 기존 비밀번호는 그 즉시 무효가 된다. 문구로 명확히 알린다.
- 권한: `/admin/*` 라우터는 이미 전부 `get_current_admin` 의존성을 거치므로, 관리자 세션이 없으면 이 요청도 로그인 화면으로 돌아간다. 팀 계정 세션으로는 접근할 수 없다.

### 결정 사항
- **팀별 단건 버튼**으로 만든다(일괄 재발급 아님) — 분실은 한 팀씩 발생하고, 전체 재발급은 실수로 누르면 전 팀 로그인이 한 번에 끊기는 위험한 동작이다.
- **아이디 컬럼은 추가하지 않는다.** 아이디가 필요한 유일한 경우("팀이 아이디를 잊음")는 재발급 결과 표가 아이디를 함께 보여주므로 이미 해결된다 (2026-07-26 사용자 확인).
- 아카이브된 시즌은 계정이 삭제되므로(plan.md §5.4) 재발급 대상이 없다 — 계정이 없는 팀은 버튼을 숨기고, 요청이 들어와도 안내 메시지로 거절한다.

### 알려진 한계
- 재발급해도 **그 팀이 이미 로그인해 둔 세션은 유지된다**. 세션은 서명된 쿠키라 서버가 개별 세션을 무효화할 수단이 없기 때문이다. 비밀번호 분실 대응에는 문제가 없고, 계정 탈취 대응이 필요해지면 그때 세션 저장소 도입을 검토한다.

### 2-5-1. [원인 정정] 영상이 261바이트였던 진짜 이유

tasks.md Phase 8에 "DRFC의 `agents_video_editor` 문제(DRFC 이슈 #67)"로 기록했던 진단은 **틀렸다.**
실제 MinIO 버킷을 조회하니 카메라 앵글이 세 개 있고, 그중 우리가 받던 것만 깨져 있었다.

```
rl-deepracer-sagemaker/mp4/camera-45degree/0-video.mp4   13.8 MiB   정상
rl-deepracer-sagemaker/mp4/camera-pip/0-video.mp4        13.8 MiB   정상 (운영자가 직접 확인)
rl-deepracer-sagemaker/mp4/camera-topview/0-video.mp4    261 Bytes  깨짐 ← worker/drfc.py가 받던 키
```

즉 다운로드 경로는 처음부터 정상이었고, **하드코딩된 카메라 앵글 하나만 잘못 골랐던** 것이다.

**해결**: 후보 앵글을 우선순위대로 두고(`camera-pip` → `camera-45degree` → `camera-topview`),
오브젝트 크기가 유효한(수 KB 이상) 첫 번째를 내려받는다. 특정 앵글이 깨져도 자동으로 다음을 쓴다.

### 2-5-2. 저장 용량 — 실측과 판단

| 항목 | 1건 크기 | 시즌 추정(10팀 × 5회/일 × 14일 = 700건) |
|---|---|---|
| 모델 아카이브 | 약 250 MB | **약 175 GB** |
| 평가 영상 | 13.8 MB | 약 9.7 GB |

`storage/`가 `/mnt/c`(여유 33GB)에 있어 **현행 유지 시 며칠 안에 디스크가 찬다.** 병목은 영상이 아니라 모델이다.

**해결**: 보존 정책을 시즌 종료(아카이브) 시점에서 **평가 완료 직후**로 앞당긴다. 팀의 최고기록이 아닌
제출의 모델·영상 파일을 그 자리에서 지운다. 그러면 시즌 내내 팀당 1건씩만 남아 **약 2.6GB**로 수렴한다.

- 삭제 대상은 **파일뿐**이고 DB 레코드(제출 이력·랩타임)는 남긴다 — 리더보드의 "제출 횟수"와 이력이 그대로 유지돼야 한다.
- `queued`/`running` 상태 제출의 모델 파일은 **절대 지우지 않는다**(평가에 쓰이는 중).
- 기존 `season_archive.archive_season()`과 같은 규칙이므로 삭제 로직을 공용 모듈로 뽑아 양쪽이 함께 쓴다.

### 2-5-3. [버그] 상대 경로 전환으로 아카이브 삭제가 조용히 실패

Phase 9-0에서 `model_path`를 상대 경로로 바꿨는데, `season_archive._remove_file_if_exists()`는
`Path(path_str)`을 그대로 쓴다. 상대 경로는 **프로세스의 CWD 기준**(웹 컨테이너는 `/app`)으로 해석되므로
존재하지 않는 경로가 되고, `unlink(missing_ok=True)` 때문에 **에러 없이 조용히 아무것도 지우지 않는다.**
→ `resolve_storage_path()`로 해석하도록 고친다.

### 2-5-4. `storage/`를 WSL ext4로 옮기는 건 (보류)

`/mnt/c`(여유 33GB) 대신 WSL 내부 ext4(여유 933GB)로 옮기는 선택지는 §2-5-2를 적용하면
급하지 않다. 장단점과 판단은 [operations.md](../../docs/operations.md)의 "저장 위치" 절에 정리한다.
**대회 기간에는 현행 유지**하고, 시즌 종료 후 재검토한다 — 경로 변경은 웹·워커·compose 볼륨을
동시에 맞춰야 하고 서비스 중단이 필요하기 때문이다.

## 5. 운영 중 배포 제약 (2026-07-26)

임원진이 실제로 접속·업로드하는 중에 배포하므로 다음을 지킨다.

**건드리지 않는 것**
- `cloudflared` 프로세스 — **절대 재시작하지 않는다.** 재시작하면 `*.trycloudflare.com` 주소가 바뀌어 공유한 링크가 죽는다. 웹 컨테이너만 갈아끼우면 터널은 그대로 유지된다.
- `db` 컨테이너, `storage/` 디렉터리, 기존 시즌·팀·제출 데이터.
- 제출 업로드 로직(검증 순서, 한도, 동시 제출 제한) — 경로 저장 형식 외에는 손대지 않는다.
- `SESSION_SECRET`(.env) — 바꾸면 접속 중인 임원진·관리자가 전부 로그아웃된다.

**깨지면 안 되는 것**
- 이미 공유된 URL: `/`, `/leaderboard`, `/leaderboard/{id}`, `/submit`, `/login` 전부 계속 동작해야 한다. 이번 변경은 `/leaderboard`의 **동작만** 바꾸고 경로를 없애지 않는다.
- 스키마 변경 없음 → 컨테이너 기동 시 도는 `alembic upgrade head`는 no-op이다.

**배포 순서 (다운타임 최소화)**
1. 대기열이 빈 것을 확인한다 (`queued`/`running` 제출 0건).
2. `docker compose build web` — **이미지 빌드 중에는 기존 컨테이너가 계속 서비스한다(무중단)**.
3. `docker compose up -d web` — 교체는 수 초. 이 순간의 업로드 1건만 실패할 수 있으므로 대기열이 빈 시점에 한다.
4. 워커 재시작 (`worker.run`) — 경로 해석 코드가 바뀌므로 필요. 평가가 돌고 있지 않을 때만.
5. 스모크 체크: `/healthz`, `/leaderboard`(진행중 시즌으로 리다이렉트), `/leaderboard/seasons`, 관리자 로그인 → 팀 일괄 등록 화면.

**검증에서 제외한 것**
- `tests/verify_phase8.py`는 **운영 DB에 검증용 시즌·팀·제출을 만들고 워커 중지를 요구**한다. 임원진이 쓰는 중이므로 이번엔 실행하지 않는다. 대신 DB를 건드리지 않는 pytest 단위 테스트로 회귀를 확인하고, 나머지는 배포 후 스모크 체크로 대신한다.
